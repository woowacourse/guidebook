# 새 실험 로그 추가

> 팀원이 새 실험 로그를 쓸 때 첫 번째로 치는 커맨드. 원본 자료만 넘기면 슬러그·제목·요약·MDX 본문·`logs.ts`·`updates.ts`·브랜치·PR을 한 번에 만든다.

## 진행 안내 (커맨드를 받은 즉시 가장 먼저 출력)

```
실험 로그 추가는 5단계로 진행합니다.

[1/5] 의도와 원본 자료 받기              ← 지금 여기
[2/5] 정리 방식 선택 (분석 / 요약 / 종합)
[3/5] 슬러그·제목·요약·단계·트랙 자동 추천 확인
[4/5] 브랜치 생성 · MDX·logs.ts·updates.ts 작성
[5/5] 커밋 · 푸시 · PR 등록 (@wmakerjun 멘션)
```

각 단계로 넘어갈 때마다 `[N/5] {단계 이름}` 한 줄을 다시 출력해 어디까지 왔는지 보여줍니다.

---

## Step 1: 의도와 원본 받기

다음 문구로 시작합니다.

> **어떤 자산을 추가하고 싶으신가요?**
>
> 예시:
> - 페어 프로그래밍 회고 5회 누적 패턴
> - 안드로이드 레벨2 강의형→참여형 전환 실험
> - 레벨3 데모데이 회고 시리즈
>
> 간단한 의도와 어떤 내용인지 1~2줄, 그리고 **원본 자료**(슬랙 로그, 문서 링크, GitHub 토론, 메모, 슬라이드 등)를 함께 붙여주세요. 나머지는 제가 알아서 정리합니다.

사용자의 답변에서 다음 두 가지를 확보합니다.

- **의도** — 1~2줄짜리 한 줄짜리 설명
- **원본** — 본문 인용, 링크, 첨부 텍스트 중 하나 이상

둘 중 하나라도 비어 있으면 한 번 더 가볍게 보충 요청합니다. 강제하지는 않습니다 (사용자가 "원본 없이 진행"이라고 답하면 그대로 진행).

---

## Step 2: 정리 방식 선택

`AskUserQuestion` 도구로 한 번에 묻습니다. multiSelect는 false.

옵션:

1. **종합** *(권장)* — 요약 + 잘 작동한 것 / 아쉬운 것 / 다음 실험까지 함께 정리
2. **요약** — 핵심 사실과 흐름만 압축. 가장 짧다
3. **분석** — 패턴·인과·맥락까지 깊게 해석. 가장 길다

사용자가 텍스트로 직접 답한 경우(예: "그냥 요약만") 위 셋 중 하나로 매핑합니다.

---

## Step 3: 메타데이터 자동 추천 + 확인

원본·의도·정리 방식을 바탕으로 다음 메타데이터를 LLM이 직접 추론하고, 표 형태로 한 번에 확인을 받습니다.

추천할 필드:

- **슬러그** — 영문 소문자와 하이픈만 사용. 원본의 핵심 키워드 2~4개를 조합. 예: `pair-programming-retro`. `content/education/logs/{슬러그}.mdx` 존재 여부를 확인하고, 충돌이면 `-2`, `-3`을 자동으로 붙여 회피한 뒤 그 결과를 추천 값으로 사용.
- **제목** — 한국어. 원본에 등장한 명사구를 우선 활용. 너무 추상적이지 않게.
- **한 줄 요약 (description)** — 한 문장. "무엇을 / 누구를 대상으로 / 어떤 결과였는지" 압축.
- **phases** — 원본에서 추론. `온보딩`, `레벨0` ~ `레벨5` 중 명시되었거나 강하게 시사된 단계만 채움. 추론 근거가 약하면 `[]`.
- **tracks** — 원본 내용에서 추론. 추론 규칙:
  - 특정 기술(React, Spring, Compose 등)이나 트랙 키워드가 강하게 등장 → 해당 트랙 단일 (`['웹 프론트엔드']` 등)
  - 여러 트랙 기술이 동등하게 등장 → 복수 (`['웹 백엔드', '웹 프론트엔드']`)
  - 트랙 무관한 활동(이력서·온보딩·연극·UX·자기소개·팀빌딩 등) → `[...ALL_TRACKS]`로 자동 채움 ("공통" 의미)
  - 추론 근거가 약하면 `[]`
- **themes** — 원본에서 추론.
  - 회고·신뢰·정체성·취약함·협업·소프트스킬 키워드 → `['소프트스킬']`
  - 코치·코치훈련·표준화 크루·코칭 워크숍 → `['코치훈련']` (이 경우 `tracks: []`로 둠)
  - 둘 다 아니면 생략

추천 결과 출력 형식 예시:

```
[3/5] 메타데이터 자동 추천 확인

| 필드        | 추천 값                                  |
| ----------- | ---------------------------------------- |
| 슬러그      | pair-programming-retro                   |
| 제목        | 페어 프로그래밍 회고 5회 누적 패턴       |
| 한 줄 요약  | 레벨1 페어 회고 5회를 거쳐 굳어진 ...     |
| phases      | [레벨1]                                  |
| tracks      | [웹 백엔드, 웹 프론트엔드, 모바일] (공통) |
| themes      | [소프트스킬]                             |

이대로 진행할까요? (Y / 수정)
```

`tracks`가 전 트랙이면 옆에 `(공통)`을 함께 표시해 사용자가 의미를 한눈에 알도록 합니다.

`수정`이면 어떤 필드를 어떻게 바꿀지 자유 텍스트로 받고, 받은 즉시 표를 다시 출력해 재확인합니다.

> **사람에게 직접 묻는 건 의도+원본과 정리 방식 두 가지뿐입니다.** 나머지는 모두 자동 추론 + 한 번의 확인.

---

## Step 4: 브랜치 생성 · 파일 작성

확인이 끝나면 아래 순서로 실행합니다.

### 4-1. 브랜치 생성

```bash
git checkout -b log/{슬러그}
```

같은 이름 브랜치가 이미 있으면 `log/{슬러그}-2` 식으로 자동 회피. 현재 워킹 트리에 다른 변경이 있어도 그대로 새 브랜치로 옮깁니다 (stash 사용 안 함).

### 4-2. MDX 스켈레톤 생성

`content/education/logs/{슬러그}.mdx`를 Write 도구로 생성합니다. **Step 2에서 선택한 정리 방식**에 따라 본문 구조를 다르게 채웁니다.

**공통 frontmatter + 헤더:**

```mdx
---
title: {제목}
description: {한 줄 요약}
---

import { Callout } from 'nextra/components'

# {제목}

<Callout>
**대상**: (추론된 트랙·단계로 자동 채움)
**맥락**: (사용자 의도 1~2줄을 그대로 사용)
**핵심 질문**: (원본에서 추론. 없으면 비워둠)
</Callout>
```

**"종합" 모드 본문 (기본):**

```mdx
## 맥락

(왜 이 실험이 필요했는지)

## 시도한 것

(구체적 운영 방식. 타임라인·팀 구성·템플릿 등)

## 관찰

(수치·인용 중심의 사실)

## 반성

**잘 작동한 것**
- (구체적 근거)

**개선이 필요한 것**
- (구체적 근거)

## 다음 실험

(연속선상의 다음 단계)

## 원본 자료

(첨부 링크 또는 인용 원문)
```

**"요약" 모드 본문:**

```mdx
## 핵심 요약

(원본의 사실과 흐름을 5~10줄로 압축)

## 원본 자료

(첨부 링크 또는 인용 원문)
```

**"분석" 모드 본문:**

```mdx
## 맥락

(배경)

## 시도한 것

(운영 방식)

## 관찰

(수치·인용 중심의 사실)

## 해석

(왜 그렇게 되었는지에 대한 분석. 인과·패턴·맥락)

## 다음 실험

(연속선상의 다음 단계)

## 원본 자료

(첨부 링크 또는 인용 원문)
```

본문은 원본 자료를 토대로 LLM이 직접 채웁니다. 빈 섹션을 그대로 두지 않습니다. 정보가 부족하면 `(원본에 명시 없음)`이라고 적습니다.

### 4-3. `content/logs.ts` 갱신

Edit 도구로 `const logs: Log[] = [` 바로 다음 줄에 새 항목을 삽입합니다 (배열 맨 위).

```ts
  {
    slug: '{슬러그}',
    title: '{제목}',
    description: '{한 줄 요약}',
    href: '/education/logs/{슬러그}',
    date: '{오늘 YYYY-MM-DD}',
    phases: [{추론된 phases}],
    tracks: [{선택된 tracks}],
{themes가 있으면: `    themes: [{themes}],`}
  },
```

날짜는 `date +%Y-%m-%d` Bash로 구합니다.

### 4-4. `content/updates.ts` 갱신 (항상 실행)

랜딩 타임라인에는 모든 실험 로그를 자동으로 노출합니다. 사용자에게 따로 묻지 않습니다.

`content/updates.ts`의 `const updates: Update[] = [` 바로 다음 줄에 다음 항목을 삽입:

```ts
  {
    date: '{기존 최상단 date 라벨을 그대로 재사용}',
    title: '{제목}',
    description: '{한 줄 요약}',
    href: '/education/logs/{슬러그}',
    status: 'active',
  },
```

`date` 라벨은 `content/updates.ts` 첫 항목의 `date` 값을 Read로 읽어 그대로 씁니다. 라벨을 임의로 새로 만들거나 바꾸지 않습니다.

## Step 5: 커밋 · 푸시 · PR 등록

### 5-1. 커밋

```bash
git add content/education/logs/{슬러그}.mdx content/logs.ts content/updates.ts
git commit -m "$(cat <<'EOF'
add experiment log: {제목}

{한 줄 요약}

Co-Authored-By: Claude Opus 4.7 <noreply@anthropic.com>
EOF
)"
```

### 5-2. 푸시

```bash
git push -u origin log/{슬러그}
```

### 5-3. PR 생성

```bash
gh pr create --title "add: {제목}" --body "$(cat <<'EOF'
## 요약
- {한 줄 요약}

## 정리 방식
- {분석 / 요약 / 종합 중 선택한 값}

## 변경 파일
- `content/education/logs/{슬러그}.mdx` (신규)
- `content/logs.ts` (logs 배열 최상단 추가)
- `content/updates.ts` (랜딩 타임라인 자동 노출)

## 검토 요청
@wmakerjun 본문 정리 방향과 메타데이터 한 번 봐주세요.

🤖 Generated with [Claude Code](https://claude.com/claude-code)
EOF
)"
```

PR URL을 결과 보고에 포함시킵니다.

## 제약

- **사람에게 묻는 건 2가지뿐.** 의도+원본, 정리 방식. 슬러그·제목·요약·phases·tracks·themes는 모두 LLM이 원본에서 자동 추론하고 한 번의 확인 단계에서 처리합니다.
- **phases·tracks·themes 질문을 만들지 않습니다.** 모두 원본 추론 결과만 확인 단계에서 노출. 틀렸으면 `수정`으로 한 번에 고칩니다.
- **`tracks: [...ALL_TRACKS]`는 "공통" 의미로 사용합니다.** 트랙 무관한 활동(이력서·온보딩·연극·UX·자기소개·팀빌딩 등)은 전 트랙으로 자동 채웁니다.
- **`코치훈련` 테마는 코치 대상 활동에만 부여**하고, 그 경우 `tracks: []`로 둡니다.
- **랜딩 타임라인은 항상 자동 노출합니다.** 옵션을 묻지 않습니다.
- **본문은 비워두지 않습니다.** 정보가 부족하면 원본 인용 또는 `(원본에 명시 없음)`을 명시.
- **슬러그 중복은 자동 회피.** `-2`, `-3` 자동 부여. 사용자에게 다시 묻지 않습니다.
- **브랜치는 항상 새로 따고 PR까지 보냅니다.** main에 직접 커밋하지 않습니다. PR 본문에 `@wmakerjun`을 멘션합니다.
- `content/logs.ts`·`content/updates.ts`의 들여쓰기(2칸)와 작은따옴표 스타일을 기존 항목과 일치시킵니다.
- 사용자에게 보여주는 모든 안내 문구는 합니다체로 작성합니다.
