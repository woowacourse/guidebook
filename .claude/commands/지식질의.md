# 지식 질의 (query)

> 위키에 질문을 던지면, **index.md 라우팅 테이블을 먼저 읽고** 관련 wiki 노트 2~5개를 통째로 열어 인용과 함께 답한다. 카파시 LLM Wiki 패턴의 핵심 작동 원리(RAG 없는 질의응답)를 그대로 구현.

> **반드시 `llm-wiki` 스킬을 먼저 로드한다.** 모든 규약은 거기 있다.

> 이 커맨드는 **에이전트에 위임하지 않는다.** 질의응답은 사용자와의 대화이므로 메인 컨텍스트에서 직접 처리해 추론 과정을 투명하게 보여준다.

## 인자

| 인자 | 동작 |
|---|---|
| 질문 텍스트 | 인자로 받은 질문 즉시 처리 (예: `/지식질의 피드백 트리거가 뭐야`) |
| (없음) | 사용자에게 질문을 받는 인터랙티브 모드 |
| `--no-log` | 이번 질의를 log.md 에 기록하지 않음 (가벼운 조회용) |

## 진입 시 첫 출력 (체크리스트)

```
지식 질의는 4단계로 진행합니다.

[ ] 1. 질문 받기 + 위키 상태 확인                          ← 진행 중
[ ] 2. index.md 통째 읽기 → 관련 노트 라우팅 결정
[ ] 3. 선택한 wiki 노트 2~5개 읽고 답변 구성
[ ] 4. 인용과 함께 답변 + log.md 에 한 줄 기록
```

## Step 1: 질문 받기

- 인자로 질문이 들어왔으면 그대로 사용.
- 없으면 사용자에게 "질문 주세요" 라고 묻고 답을 기다림.

**위키 상태 빠르게 확인:**
- `llm-wiki/wiki/` 가 비어 있으면: "위키가 비어 있습니다. `/지식정제` 부터 실행해야 답할 수 있습니다." 출력 후 종료.
- 그 외 정상 진행.

## Step 2: index.md 라우팅

**카파시 정통의 핵심**: 모든 wiki 를 읽지 않는다. **index.md 만 통째로 읽고** 어느 노트 2~5개를 열지 결정한다.

1. `llm-wiki/index.md` 를 Read 로 통째 로드.
2. 질문과 각 라인의 한 줄 요약을 매칭.
3. 우선순위:
   - **직접 매칭**: 질문의 핵심 단어가 슬러그·요약·태그에 직접 등장하는 노트
   - **개념 매칭**: 같은 개념을 다루는 다른 노트 (예: "피드백" → feedback-trigger-recognition, feedback-request-direct)
   - **그래프 매칭**: 직접 매칭된 노트의 `links:` 가 가리키는 인접 노트
4. **2~5개 선택**. 너무 적으면 답 부족, 너무 많으면 컨텍스트 낭비.

**라우팅 결정을 사용자에게 투명하게 보여준다**:

```
질문: "..."
라우팅 결정:
- wiki/feedback-trigger-recognition.md  (직접 매칭: "피드백" + "트리거")
- wiki/feedback-request-direct.md       (개념 매칭: 같은 워크숍 패턴)
- wiki/implementation-intention.md      (그래프 매칭: feedback-request-direct.links)
```

## Step 3: 선택한 노트 읽기 + 답변 구성

1. 선택한 wiki 노트 2~5개를 **통째로** Read (청크 X).
2. 노트의 `sources:` 에서 raw 파일도 필요하면 인용용으로 Read.
3. 답변 구성 원칙:
   - **위키에 있는 내용만 답한다**. 추측·추론·일반 지식 금지.
   - **답에 자기 언어 통합**. 노트 본문 복붙 금지.
   - **모든 주장에 인용을 단다** — `[[slug]]` 또는 `(wiki/slug.md)` 형식.
   - **raw 출처를 끝에 같이 표시** — `근거 raw: raw/...`
   - **위키가 답하기에 부족하면 솔직히 인정** — "위키에 다음 부분이 부족합니다…" + 어떤 raw 흡수가 필요한지 제안.

## Step 4: 답변 출력 + 로그 기록

답변 포맷:

```
## 답변

(자기 언어로 작성한 답변, 곳곳에 [slug] 인용)

## 근거

- `wiki/<slug-1>.md` — 핵심 인용 한 줄
- `wiki/<slug-2>.md` — 핵심 인용 한 줄

원본 raw: `raw/<...>`, `raw/<...>`

## 한계

- (위키에 부족한 부분이 있으면 명시)
- (관련 보류 항목 또는 다음 흡수 권장)
```

**`--no-log` 가 아니면** `llm-wiki/log.md` 맨 위에 한 줄 추가:

```markdown
## [YYYY-MM-DD] query | "질문 요약"
답변에 사용한 노트: slug-1, slug-2, slug-3.
```

## 절대 금지

- ❌ index.md 를 건너뛰고 wiki 전체를 읽기 (RAG 대체의 본질을 깨뜨림)
- ❌ 위키 밖 일반 지식으로 답하기 (있더라도 위키에 없으면 솔직히 인정)
- ❌ 노트 본문 복붙 (답은 자기 언어 통합)
- ❌ 인용 없는 주장
- ❌ wiki·index·log 어떤 파일도 수정 (log.md 한 줄 추가 외)
- ❌ 5개 초과 노트 로드 (컨텍스트 낭비)
- ❌ 답이 명확치 않을 때 추측으로 메우기

## 빈도 권장

- 호출 주기: 자유 — 위키가 살아있는 이유는 질의를 받기 위함.
- 답이 부족하다 느낄 때마다 어떤 raw 가 추가되어야 하는지 메모해두면 다음 `/지식흡수` 가 표적화된다.

## 예시

```
사용자: /지식질의 피드백을 잘 받는 방법이 뭐야?

LLM:    [Step 1] 질문 받음. 위키 상태: wiki 10개, index 등록 OK.

        [Step 2] index.md 로드 → 라우팅 결정:
        - wiki/feedback-trigger-recognition.md  (직접 매칭: 피드백)
        - wiki/feedback-request-direct.md       (개념 매칭: 피드백 받기)
        - wiki/implementation-intention.md      (그래프 매칭: 약속 카드)

        [Step 3 + 4 답변]

        ## 답변

        피드백을 잘 받는다는 건 두 가지를 동시에 해내는 일이다.
        **자기 안에서 발동하는 방어 반응을 인지**하는 것
        ([feedback-trigger-recognition](wiki/feedback-trigger-recognition.md))
        과, **회피하던 사람에게 직접 묻는 행위**
        ([feedback-request-direct](wiki/feedback-request-direct.md))로 뒤집는 것.

        Stone & Heen 은 방어 반응을 세 트리거 — 사실·관계·정체성 — 로 분류한다.
        ...

        ## 근거

        - `wiki/feedback-trigger-recognition.md` — "차이를 만드는 것은 메시지가 아니라 듣는 사람 안의 반응"
        - `wiki/feedback-request-direct.md` — "SSCC + 페어 증인 + 7일 약속"
        - `wiki/implementation-intention.md` — "if-then 약속은 실행률 ~2.5배"

        원본 raw: `raw/2026-05-19-thanks-feedback-workshop.md`

        ## 한계

        - 위키는 워크숍 설계 시점의 기록이다. 실제 운영 결과는 아직 raw 에 없음.
        - 다음 흡수 권장: 워크숍 1회 운영 후 회고 (참가자 반응·약속 카드 7일 후 데이터)

        [log.md 갱신: query 한 줄 기록]
```
