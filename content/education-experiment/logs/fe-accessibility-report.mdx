# FE 접근성 리포트: 자기 서비스를 진단하는 6기·7기 반복 실험

<Callout>
**대상**: FE 레벨4에서 접근성 학습을 설계하려는 코치

**맥락**: 6기 (2024.10.24) · 7기 (2025.10.23) FE 레벨4 팀 프로젝트 후반부

**핵심 질문**: 접근성을 "체크리스트로 점검하는 것"이 아니라 "자기 서비스의 사용자 경험으로 발견하는 것"으로 만들 수 있을까?
</Callout>

## 배경과 문제

접근성은 가르치기 어려운 주제다. 이론적으로는 WAI-ARIA 스펙과 WCAG 가이드라인이 명확하지만, 크루들이 "이걸 왜 지켜야 하는가"를 체감하기 어렵다. 시각 장애나 운동 장애를 직접 경험해본 적이 없는 개발자에게 접근성은 추상적인 의무로만 다가온다.

기존 강의식 접근의 한계는 두 가지였다.

1. **추상적 지식의 휘발성**: 강의로 들은 ARIA 속성은 1주일이면 잊혀진다.
2. **자기 서비스와의 단절**: 일반적인 사례는 "그래서 우리 서비스는?"으로 이어지지 않는다.

성능 리포트와 같은 구조 — **자기 서비스를 직접 진단하고 개선하는 리포트** — 를 접근성에도 적용한 것이 이 실험이다.

## 설계

### 핵심 원리

성능 리포트와 동일한 3단계 구조를 차용했다.

1. **측정** — 자기 팀 서비스를 접근성 가이드라인에 따라 진단
2. **개선** — 발견한 문제를 실제로 수정
3. **공유** — 디스커션에 개선 과정을 리포트로 남기고 다른 팀과 피드백

### 6기 → 7기로의 변화

7기 디스커션에는 **"6기 참고 링크"** 가 명시적으로 포함되었다. 선배 기수의 리포트를 처음부터 참고 자료로 제공한 것이다. 이는 단순한 자료 공유가 아니라, "이 활동은 누적되는 자산"이라는 메시지를 크루에게 전달한다.

## 결과

6기 12팀, 7기 9팀의 리포트에서 반복적으로 등장한 패턴은 다음과 같습니다.

### 1. 스크린리더 정보 통합 — 가장 빈번한 패턴

크루들이 가장 많이 발견한 문제는 "복합 컴포넌트가 스크린리더에서 끊겨 읽히는" 것이었습니다.

- **6기 행동대장팀**: `Top` 컴포넌트 children을 순회해 텍스트를 모은 뒤 부모에 `aria-label={childrenTexts.join(' ')} tabIndex={0}` 를 부여하고, 자식엔 `aria-hidden="true"`. 끊어 읽히던 문장을 한 호흡으로 만들었습니다.

  > "기존의 Top 컴포넌트의 text는 끊어서 읽혔습니다. … 스크린리더 사용자에게 혼동과 불편함을 주게 될 것입니다." — 행동대장/소하

- **6기 모우다·코레아팀**: `aria-labelledby` / `aria-describedby` 로 카드 내부 정보(label·placeholder·validation)를 한 호흡에 묶어 읽게 처리.
- **6기 땅콩팀**: `aria-live` 로 닉네임 입력 상태 안내, 라운드 제한시간 알림에 `role="alert"` 를 적용하면서 "처음 시작 / 절반 / 5초 남았을 때 3번으로 나눠 안내"하는 시나리오를 직접 설계.

### 2. 포커스/키보드 내비게이션 트랩

- **6기 투룻팀**: 모든 모달·드로어에 focus trap을 적용하고, IntersectionObserver 무한스크롤이 키보드 사용자를 가두는 문제를 "여행기 더보기" 버튼으로 보완.
- **6기 코드잽팀**: `FocusTrap` 공통 컴포넌트를 신설.
- **7기 모아온팀**: 수백 개 아티클 카드에서 Tab 탈출 불가 문제를 "Tab 키 꾹 누름 → 탈출 버튼으로 포커스 연결"로 해결.

  > "적게는 수십, 많으면 수백 개의 아티클 카드 리스트에서 Tab 키로 포커스를 탈출하기 위해서는 모든 아티클 카드를 통과해야 했음." — 모아온/잭슨

### 3. 시맨틱·이미지·명도비

- **6기 방끗팀**: `FormField` 공통 컴포넌트에 `label htmlFor` 연결, 장식 이미지 `alt=""`, **NVDA + VoiceOver 양쪽 검증** (교차 검증을 명시한 유일한 팀).
- **6기 크루루팀**: WCAG 2.1 AA 명암비(4.5:1)에 맞춰 `#777676` 색상 도입. **WCAG 레벨을 명시적으로 인용한 유일한 팀**.

### 4. 노이즈 제거 — 7기에서 새로 등장한 결

7기 포게더팀은 6기에는 없던 관점을 발견했습니다.

> "선택모드가 아닐 때에도 '선택되지 않음, 선택됨' 등의 label이 출력됨. 단순히 이미지를 탐색 중일 때도 불필요한 정보가 함께 읽히게 됨." — 포게더/루나

"무엇을 추가할 것인가"에서 "무엇을 줄일 것인가"로 관점이 이동한 사례입니다.

### 5. 메타 회고

> "처음에는 단순한 시각적 요소만을 고려했지만, 키보드 사용자, 시각 장애인 등 여러 환경에 처한 사용자들의 요구를 동등하게 반영해야 할 필요성을 느낄 수 있었습니다. 접근성 향상은 단지 특정 사용자를 위한 것이 아니라, 전체적인 사용자 경험을 개선하는 효과가 있다는 것을 느끼기도 했습니다." — 데벨업/Parkhanyoung

## 교훈

**잘 작동한 것**

- **성능 리포트와의 평행 구조**: 크루들이 이미 성능 리포트로 익숙해진 "측정 → 개선 → 공유" 흐름을 그대로 활용해 학습 비용이 낮았습니다.
- **자기 서비스 진단**: 일반론이 아닌 자기 코드를 다루기 때문에 발견 즉시 코드베이스에 반영되었습니다. 6기 12팀, 7기 9팀이 모두 자기 서비스 코드 변경 사례를 첨부했습니다.
- **누적되는 패턴 학습**: 7기가 6기를 명시적으로 인용한 흔적은 없지만, `aria-label` 정보 통합·focus trap·tabIndex 패턴이 7기 4팀에서 모두 다시 등장했습니다. 디스커션이 암묵적 자료실로 작동했습니다.

**개선이 필요한 것**

- **6기 → 7기 깊이 후퇴**: 6기는 12팀 중 11팀이 디스커션 본문에 코드·스크린샷·영상을 인라인으로 작성(투룻 11,461자 / 행동대장 5,123자 / 코딩해듀오는 46개 체크박스 점검)한 반면, **7기 9팀 중 6팀이 본문에 한두 줄만 적고 노션 링크로 외부화**(150~160자대)했습니다. 디스커션의 누적 자산 가치가 7기에서 약화됐습니다. 차기에는 "본문 인라인 작성"을 명시 제약으로 둘 필요가 있습니다.
- **자동화 도구 부재**: 21개 팀 전체에서 axe·Lighthouse·WAVE를 명시적으로 호출한 팀이 **0**이었습니다. 검증은 대부분 수동 스크린리더(Chrome Screen Reader 확장, NVDA, VoiceOver) 1~2개에 의존. 자동화 + 수동의 이중 검증을 권장 워크플로우로 박을 필요가 있습니다.
- **WCAG 기준 부재**: 명시적으로 WCAG 레벨(AA 4.5:1)을 인용한 팀이 크루루 1팀뿐. 나머지는 "스크린리더가 읽는다 / 안 읽는다"의 이진 판단에 머물렀습니다.
- **회고가 거의 없음**: 리포트 형식이 '문제→해결' 표 위주라, 학습 회고를 남긴 팀은 데벨업 1팀뿐. "무엇을 배웠는가"가 아닌 "무엇을 고쳤는가"만 기록되었습니다.
- **사용자 검증 부재**: 리포트는 작성하지만, 실제 보조기기 사용자에게 검증받는 단계가 없습니다. 차기에는 [UX 리서치 3단계 훈련](/education-experiment/logs/ux-research-training) 의 UT 절차와 결합할 가치가 있습니다.
