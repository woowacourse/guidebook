# FE 레벨2 16단계 학습 체계: 점진적 깊이로 리액트를 체화하기

<Callout>
**대상**: FE 레벨2 커리큘럼을 설계하려는 코치

**맥락**: 7기 FE 레벨2 · 페이먼츠 → 장바구니 미션 전 과정

**핵심 질문**: 리액트를 "알겠다"에서 "체화했다"로 옮기려면 어떤 순서와 제약이 필요한가?
</Callout>

## 배경과 문제

레벨2에서 크루들은 리액트를 처음 만납니다. 공식 문서를 읽고, 컴포넌트를 만들고, 상태를 관리하는 법을 배웁니다. 그런데 "공식 문서를 읽었다"와 "내 코드에 적용할 수 있다" 사이에는 큰 간극이 있습니다.

기존 방식의 문제는 세 가지였습니다.

| 문제 | 증상 |
|------|------|
| **읽기만 하고 적용하지 못함** | 공식 문서를 통독했지만 미션 코드에서 어디에 써야 할지 모름 |
| **피드백이 일방적** | 리뷰어의 코멘트를 수용하지만 "왜 그런지" 근거를 스스로 설명하지 못함 |
| **설계 관점 부재** | 코드가 동작하면 끝이라 생각하고, 구조적 판단 기준이 없음 |

이 문제를 해결하기 위해, 레벨2 전체를 **16단계 점진적 학습 체계**로 설계했습니다. 매 단계마다 의도적 제약을 두어 크루가 "적게 읽되 깊이 사고하고, 거꾸로 만들어보며, 관점을 전환"하는 경험을 반복하도록 했습니다.

## 설계

### 핵심 원리: 세 가지 의도적 제약

| 원리 | 설명 | 적용 예시 |
|------|------|-----------|
| **적게 읽기** | 전체를 훑는 대신 핵심만 뽑아 내 코드에 연결 | Step 2: 공식 문서를 AI와 대화하며 핵심 포인트 3개만 추출 |
| **거꾸로 만들기** | 완성 코드를 보는 대신, 결과에서 역추적 | Step 5: 요구사항을 읽고 TDD적 사고로 커밋 로그를 먼저 설계 |
| **관점 전환** | 작성자가 아닌 리뷰어/설계자 시점으로 코드를 바라봄 | Step 4: 공식 문서 근거를 들어 동료 코드 리뷰 |

### 16단계 전체 구조

페이먼츠 미션(1단계~2단계)과 장바구니 미션을 관통하는 16개 스텝입니다. AI 도구(NotebookLM, Cursor)를 학습 보조 도구로 적극 활용합니다.

| Step | 제목 | 핵심 활동 | 제약/도구 |
|------|------|-----------|-----------|
| 1 | 스토리북 적게 읽고, 더 많이 배우기 | 스토리북 핵심 키워드를 종이에 정리 | 종이 기반, 키워드 압축 |
| 2 | 리액트 공식 문서 적게 읽기 | NotebookLM과 대화하며 내 코드에 적용할 핵심 포인트 추출 | NotebookLM |
| 3 | 커스텀 훅 다양한 관점으로 읽기 | 여러 관점(실천/정리/설계자)으로 커스텀 훅을 읽고 Step 2 훅 초안 설계 | NotebookLM, Cursor |
| 4 | 근거 기반 리뷰 남기기 | 공식 문서를 근거로 동료 PR에 리뷰 | 공식 문서 인용 필수 |
| 5 | TDD적 사고로 커밋 로그 거꾸로 만들기 | 요구사항을 읽고 커밋 로그를 먼저 설계 | 실습지 기반, 역순 설계 |
| 6 | 책임 중심으로 코드 바라보기 | 기존 코드에서 책임을 분석하고 개선점 논의 | 페어 토론 |
| 7 | AI에게 코드 분석 요청하기 | AI가 지적한 안티패턴에서 나만의 개선 포인트 도출 | Cursor |
| 8 | 나만의 리액트 기준 만들기 | AI 피드백과 공식 문서를 종합해 PR 체크리스트 작성 | 개인 체크리스트 |
| 9 | 페이먼츠 모듈 1단계 | 커스텀 훅 설계 + 스토리북 활용 구현 | 미션 수행 |
| 10 | 페이먼츠 모듈 2단계 | 상태 관리 + 컴포넌트 설계 심화 | 미션 수행 |
| 11 | 장바구니 공식 문서 학습 | Context API, data fetching 패턴 학습 | NotebookLM |
| 12 | 장바구니 1단계 | 상태 관리 전략 실전 적용 | 미션 수행 |
| 13 | RFC 워크숍 | Data Fetching Hook 설계 문서 작성 | RFC 템플릿 |
| 14 | 장바구니 2단계 | RFC에서 설계한 구조를 실제 코드에 적용 | 미션 수행 |
| 15 | 레벨2 돌아보기 | 개인 탐구 주제를 정해 깊이 파고들기 | 자유 주제 탐구 |
| 16 | 공유회 | 탐구 결과를 크루들과 공유 | 발표 + 문서 공유 |

### AI 도구의 역할

AI를 "답을 주는 도구"가 아닌 **"사고를 확장하는 대화 상대"**로 위치시켰습니다.

| 도구 | 활용 방식 | 주의점 |
|------|-----------|--------|
| **NotebookLM** | 공식 문서를 소스로 업로드하고, 내 코드 맥락에서 질문 | "통째로 읽기" 대신 "질문하며 읽기" 유도 |
| **Cursor** | 내 코드베이스를 분석하여 안티패턴 발견, 리팩터링 제안 | AI의 제안을 그대로 수용하지 않고 근거 확인 |

### RFC 워크숍 (Step 13): 설계자로 사고하기

16단계 중 가장 독특한 실험은 **RFC(Request for Comments) 워크숍**이었습니다. 크루들이 "Data Fetching Hook을 어떻게 설계할 것인가"라는 주제로 설계 문서를 작성했습니다.

RFC 템플릿 구조:

1. **배경/문제 인식** — 왜 도입하는가?
2. **제안하는 설계 구조** — 타입스크립트 인터페이스와 예시 코드
3. **장점** — 이 구조의 이점
4. **고려한 trade-off** — 어떤 선택을 고민했는가?
5. **다른 사람에게 묻고 싶은 질문**

이 활동이 의미 있었던 이유는, 크루가 처음으로 **"코드를 짜는 사람"이 아닌 "구조를 설계하는 사람"**의 시점을 경험했기 때문입니다.

## 결과

### Step 1~2. 적게 읽기의 효과

Step 1에서 크루들이 스토리북을 종이에 정리한 핵심 키워드를 보면, "독립적", "견고한 UI", "워크숍", "테스트", "문서화"로 수렴했습니다. 전체를 읽지 않아도 핵심을 잡아낼 수 있다는 것을 체험한 순간입니다.

Step 2에서 NotebookLM과 대화한 크루들의 반응:

> "컴포넌트를 구성하는 기준점으로 UI의 기능적 분리, 시각적 분리, 반복되는 UI 패턴, 데이터 의존성을 생각해볼 수 있다는 걸 알게 됐다."

> "입력 값과 카드 프리뷰의 동기화를 위해 상태를 전역에 선언하고 props로 넘기는 방식의 단점을 공식 문서 기반으로 이해할 수 있었다. Prop Drilling, 불필요한 리렌더링 문제를 구체적으로 인식했다."

### Step 3. 커스텀 훅 설계 초안

크루들이 설계한 훅 초안에서 공통 패턴이 나타났습니다.

| 훅 이름 | 핵심 책임 | 빈도 |
|---------|-----------|------|
| `useForm` / `useFormValidation` | 폼 상태 관리 + 유효성 검사 | 높음 |
| `useControlledCardNumber` | 특정 입력 필드의 상태와 유효성 | 중간 |
| `useTotalInputValidation` | 전체 폼의 제출 가능 여부 판단 | 중간 |
| `useNextInputSection` | 입력 완료 시 다음 섹션 노출 | 낮음 |

주목할 점은, 대부분의 크루가 **"재사용 가능한 추상적인 훅"과 "미션에 특화된 구체적인 훅" 사이에서 고민**했다는 것입니다.

> "처음에는 useForm이라는 범용 훅을 만들려 했는데, 재사용 안 되는 구조로 작성할 것 같아서 input은 없을 것 같습니다."

### Step 4. 근거 기반 리뷰에서 나타난 성장

크루들이 남기려 한 리뷰 포인트와 받은 리뷰 중 인상 깊었던 것의 차이가 흥미롭습니다.

**남기려 한 리뷰 포인트 (자기 수준)**

- 컴포넌트 분리가 적절한가
- 상태 관리 방식이 맞는가
- 코드 가독성과 재사용성

**받은 리뷰 중 인상적이었던 것 (i+1 지점)**

- "하위 컴포넌트에 setter 함수를 직접 전달하면 컴포넌트의 의존성을 높이고 재사용성을 낮춘다"
- "에러 타입은 입력값으로부터 파생될 수 있는 정보인데, 별도 상태로 관리할 필요가 있는가?"
- "useReducer를 활용한 중앙 집중식 관리"

### Step 8. 나만의 리액트 기준

크루들이 만든 PR 체크리스트에서 반복적으로 등장한 기준입니다.

> "선언형으로 코드를 작성하였는가? 명령형으로 코드를 작성하지 않았는가?"

> "변화에 유연한 코드인지 — 조건부 흐름, 스텝 건너뛰기, UI 비즈니스에 따른 흐름 분기에 얼마나 잘 견디느냐"

> "useMemo, useCallback을 적극적으로 사용해보자"

> "불필요한 상태 관리를 하고 있지 않은가"

<Toggle title="Step 8에서 발견된 대표적인 안티패턴">

한 크루가 Cursor를 활용해 자신의 코드에서 발견한 반복 안티패턴:

**일관성 없는 함수 메모이제이션 패턴**

- `validateCardNumber`(메모이제이션 O)와 `handleChange`(메모이제이션 X)가 같은 훅 안에 공존
- 이벤트 핸들러에 대해 언제 메모이제이션이 필요한지 일관된 기준이 없었음
- 원인: "이 함수는 의존성이 적으니 필요하고, 저 함수는 매번 다른 로직을 실행하니 필요 없을 것"이라는 직관에 의존

이 발견은 Step 8에서 "나만의 기준"을 세우는 데 직접적인 근거가 되었습니다.

</Toggle>

### Step 13. RFC 워크숍 결과

크루들이 작성한 RFC에서 공통적으로 다룬 문제는 **Provider Hell**이었습니다.

<Toggle title="RFC에서 제안된 설계 패턴들">

| 접근 방식 | 핵심 아이디어 | Trade-off |
|-----------|--------------|-----------|
| **제네릭 Context 생성 함수** | `createDataContext<T>(getApi)` — 데이터 타입만 바꾸면 재사용 | 컨텍스트에 의존, isLoading/error 구현 필요 |
| **커스텀 훅 추상화** | `useRequest({method, requestData})` — HTTP 메서드별 로직 통합 | 확장성은 좋지만 복잡한 케이스에 대응 어려움 |
| **단일 Provider 통합** | `AllProvider` — Products와 CartItems를 하나의 Provider에서 관리 | Provider Hell 해결, 그러나 관심사 분리 약화 |
| **옵저버 패턴 도입** | Subject/Observer 인터페이스로 상태 변화 구독 | 선언적이지만 React 패러다임과의 충돌 가능 |

크루들의 설계에서 공통적으로 포함된 인터페이스:

```typescript
interface DataContextType<T> {
  data: T[];
  error: Error | null;
  isLoading: boolean;
  refetch?: () => Promise<void>;
}
```

</Toggle>

### Step 15~16. 레벨2 돌아보기

레벨2 마지막에 크루들이 자유 주제로 탐구한 내용이 16단계의 학습 궤적을 보여줍니다.

| 탐구 주제 | 연결되는 Step |
|-----------|--------------|
| MSW를 활용한 테스트 전략 | Step 1(스토리북) → Step 5(TDD적 사고) |
| 번들러 에러 디버깅 | Step 7(AI 코드 분석) |
| SSOT 원칙과 파생 상태 | Step 6(책임 중심) → Step 8(나만의 기준) |
| 모달 컴포넌트 Compound Pattern | Step 3(커스텀 훅) → Step 4(근거 기반 리뷰) |
| Reducer와 Flux 패턴 | Step 13(RFC) → Step 14(장바구니 2단계) |
| 낙관적 업데이트 | Step 13(RFC) → 실전 적용 |
| 객체지향 SOLID 원칙 | Step 6(책임 중심) |

크루들의 회고:

> "AI의 피드백에 의존하면서, 객체지향 설계원칙의 기본 개념을 익혀 스스로 코드를 읽고 판단하지 못하는 점에 아쉬움을 느꼈다."

> "중앙화된 상태 관리가 자동 동기화를 보장하지 않으며, 기술적 완벽함보다 사용자가 느끼는 경험을 우선시하는 것이 중요하다."

## 교훈

**잘 작동한 것**

- **"적게 읽기" 제약의 효과**: 공식 문서를 통독하게 하는 대신 NotebookLM과 대화하며 핵심 포인트 3개만 뽑게 한 구조가, "읽었는데 모르겠다"를 "이것만큼은 내 코드에 써먹겠다"로 전환시켰습니다.
- **거꾸로 만들기의 인지적 효과**: Step 5에서 커밋 로그를 먼저 설계하게 한 것이 TDD를 "테스트 코드 먼저 짜기"가 아닌 "결과에서 역추적하는 사고방식"으로 이해하게 만들었습니다.
- **RFC 워크숍**: 코드를 짜기 전에 설계 문서를 쓰는 경험이, 크루들에게 "왜 이 구조인가"를 설명하는 능력을 키웠습니다. Provider Hell이라는 공통 문제에 대해 각자 다른 해법을 제시하고 비교한 과정이 특히 효과적이었습니다.
- **AI 도구의 위치 설정**: NotebookLM과 Cursor를 "답을 주는 도구"가 아닌 "질문을 깊게 하는 도구"로 프레이밍한 것이 크루들의 주체적 학습을 유지하는 데 도움이 되었습니다.

**개선이 필요한 것**

- **Step 간 연결의 명시성 부족**: 16단계가 하나의 흐름이라는 것을 크루들이 체감하기 어려웠습니다. 각 Step이 이전 Step의 어떤 학습 위에 쌓이는지 시각적으로 보여주는 장치가 필요합니다.
- **AI 의존도 관리**: Step 7~8에서 AI에게 코드 분석을 맡긴 후, 일부 크루는 AI의 제안을 비판 없이 수용하는 경향이 나타났습니다. "AI가 왜 이렇게 제안했는지 공식 문서에서 근거 찾기"를 필수 단계로 추가해야 합니다.
- **Step 5(커밋 로그 역설계)의 난이도**: 실습지 기반 활동이었는데, 사진으로만 기록이 남아 사후 분석이 어려웠습니다. 디지털 도구로 전환하거나, 대표 사례를 아카이빙하는 구조가 필요합니다.
- **RFC에서 실제 코드로의 전이**: Step 13에서 좋은 설계 문서를 작성한 크루도 Step 14에서 실제 구현할 때 설계와 다르게 코딩하는 경우가 있었습니다. RFC와 구현 사이의 간극을 줄이는 중간 점검 장치가 필요합니다.
