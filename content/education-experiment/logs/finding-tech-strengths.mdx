# 나만의 기술적 강점 찾기: 정체성 선언 기반 딥다이브 학습

<Callout>
**대상**: 크루의 자기주도 딥다이브를 설계하는 코치

**맥락**: 레벨4 FE · 7기 (2024-10, 레벨4 후반부 개인 딥다이브)

**핵심 질문**: "나는 __에 강점이 있는 개발자입니다"라는 정체성 선언 형식이, 단순한 기술 주제 배정보다 더 깊은 학습 동기와 몰입을 만들 수 있을까?
</Callout>

## 배경과 문제

레벨4 후반부, 크루들은 프로젝트를 마무리하며 다음 단계를 준비합니다. 이 시점에서 흔히 발생하는 문제가 있습니다.

- **기술 학습의 분산**: 이것저것 조금씩 해보지만 깊이가 없음
- **동기의 외부 의존**: "과제니까", "면접에 나오니까" 학습하는 패턴
- **강점 인식 부재**: 자신이 어떤 영역에 강한지 스스로 언어화하지 못함
- **학습 결과의 개인 소비**: 공부해도 문서화하거나 공유하지 않아 지식이 흩어짐

코치가 "관심 있는 기술 주제를 정해서 공부하세요"라고 하면, 대부분은 면접 빈출 주제를 선택하거나 이미 아는 것을 조금 더 정리하는 수준에 머뭅니다. 학습의 깊이를 끌어올리려면 주제 선택의 프레임 자체를 바꿔야 했습니다.

## 설계

### 핵심 메커니즘: 정체성 선언

이 실험의 핵심은 템플릿 한 줄입니다.

> **"나는 __에 강점이 있는 개발자입니다."**

빈칸을 채우는 순간 크루는 단순한 학습자가 아니라, **특정 영역의 전문가로서 자기 정체성을 선언하는 사람**이 됩니다. 이 프레이밍의 차이는 학습의 방향과 깊이를 바꿉니다.

| 일반적 과제 | 정체성 선언 |
|-------------|-------------|
| "캐싱에 대해 조사하세요" | "나는 캐싱 전략에 강점이 있는 개발자입니다" |
| 외부 동기 (과제 완료) | 내부 동기 (정체성 일치) |
| 넓고 얕은 조사 | 좁고 깊은 탐구 |
| 과제 제출로 종료 | 문서화 + 공유로 확장 |

### 활동 구조

| 단계 | 활동 | 산출물 |
|------|------|--------|
| 1단계: 선언 | "나는 __에 강점이 있는 개발자입니다" 빈칸 채우기 | 정체성 선언문 |
| 2단계: 딥다이브 | 선언한 영역에 대한 깊이 있는 학습 | 기술 문서 (블로그, 노션, GitHub) |
| 3단계: 요약 공유 | 주요 내용 요약과 문서 링크를 디스커션에 공유 | 크루 전체 접근 가능한 지식 베이스 |

### 설계 원칙

| 원칙 | 설명 |
|------|------|
| 정체성 프레이밍 | "공부해야 할 것"이 아니라 "나를 정의하는 것"으로 주제를 선택 |
| 완전한 자율 | 주제 제한 없음. 프로젝트에서 발견한 문제든, 순수한 호기심이든 무관 |
| 공유 의무 | 학습 결과를 반드시 문서화하고 공유. 개인 소비로 끝나지 않음 |
| 동료 학습 | 다른 크루의 선언과 문서를 통해 자신이 탐구하지 않은 영역도 간접 학습 |

## 결과

### 48개의 기술적 정체성

48명의 크루가 각자의 기술적 강점을 선언하고 딥다이브 문서를 작성했습니다. 주제의 다양성이 이 실험의 가장 큰 성과입니다.

<Toggle title="렌더링과 Hydration 심화 (7건)">
가장 많은 크루가 선택한 영역입니다. 같은 키워드지만 탐구 각도가 모두 달랐습니다.

- **renderToString** — React 컴포넌트를 HTML로 변환할 때 useEffect, useState, onClick 등 중 무엇이 채택되고 무엇이 버려지는지 추적
- **Hydration 내부 메커니즘** — React의 Fiber를 중심으로 hydration이 6단계로 동작하는 과정 분석
- **Selective Hydration** — React 18의 Selective Hydration과 미스매치 오류 원인·종류·예방법 정리
- **CSR 초기 렌더링 병목** — 스크립트 평가가 병목으로 작용해 LCP가 나빠지는 원인 분석
</Toggle>

<Toggle title="성능 최적화: 이미지·폰트·캐싱 (12건)">
프로젝트에서 직접 겪은 성능 문제에서 출발한 딥다이브가 많았습니다.

- **이미지 최적화를 통한 LCP 개선** — 왜 이것이 성능 최적화를 만드는지, 다른 방법은 없는지 탐구
- **이미지 압축의 원리** — 무손실/손실 압축의 차이를 원리 수준에서 파악
- **웹 폰트 최적화** — 폰트 용량 축소, 리소스 요청 우선순위 조정, FOIT/FOUT 문제 해결까지 전체 과정
- **CDN 기반 캐싱 전략** — CORS 오류가 브라우저 캐싱에서 비롯된 문제임을 발견하고 CDN 응답 헤더 정책으로 해결
- **캐싱 전략 설계** — Lighthouse에서 TTL none인데 CloudFront에서 HIT으로 표시되는 현상 추적 및 해결
</Toggle>

<Toggle title="빌드와 번들링 (3건)">
- **Tree Shaking** — package.json의 sideEffects 설정에서 왜 CSS 파일만 들어가는지를 출발점으로 AST 파싱과 의존성 그래프 구축 과정 분석
- **Webpack 빌드 파이프라인** — 코드 변환·번들링·캐싱 등 빌드 흐름 전반을 처음부터 끝까지 분석
- **트리셰이킹 트러블슈팅** — sideEffects 설정 오류로 인한 문제를 프로젝트에서 직접 발견하고 해결
</Toggle>

<Toggle title="애니메이션과 렌더링 파이프라인 (3건)">
- **애니메이션 최적화** — 바텀시트 스크롤 애니메이션에서 프레임 드랍 원인을 개발자 도구로 직접 관찰하며 해결
- **paint → composite 단계 전환** — paint 단계에 있었던 애니메이션을 composite 단계로 옮긴 최적화 사례
- **transform의 렌더링 최적화 원리** — transform 속성이 렌더링 성능을 최적화하는 원리 탐구
</Toggle>

<Toggle title="접근성·UX·기타 (6건+)">
- **웹 접근성** — 접근성이 장애인만을 위한 것인지, 개발자에게 어떤 이점이 있는지를 중심으로 정리
- **CSR 환경에서 동적 OG 메타태그** — CloudFront + Lambda@Edge를 활용해 S3 정적 HTML에서 OG 메타태그를 실시간 수정하는 구조 탐구
- **쌓임맥락(Stacking Context)** — 버튼 클릭 시 배경 애니메이션 구현 중 z-index만으로 해결 안 되는 문제를 isolation: isolate로 해결
- **useSyncExternalStore** — Context API의 렌더링 문제와 provider hell을 개선하고, zustand 코드를 분석하며 selector 패턴 학습
- **메모이제이션** — React.memo를 제대로 이해하지 못한 채 사용하던 것을 바로잡고 올바른 사용법 정리
- **비동기와 동시성** — 서버(node)와 클라이언트(브라우저) 환경에서 비동기 처리 방법과 최신 웹 렌더링 전략과의 연결
</Toggle>

### 주제 선택의 패턴

크루들의 주제 선택에서 두 가지 뚜렷한 패턴이 관찰됩니다.

**패턴 1: 프로젝트 기반 출발**
> "저희 서비스의 바텀시트 상하 스크롤 애니메이션을 최적화하는 과정에서 렌더링 성능과 프레임 드랍의 원인을 깊이 있게 탐구했습니다."

> "간헐적으로 발생하던 CORS 오류가 브라우저 캐싱에서 비롯된 문제임을 확인하고, CDN의 응답 헤더 정책과 캐싱 전략을 통해 해결한 과정을 담았습니다."

프로젝트에서 직접 겪은 문제가 딥다이브의 출발점이 됩니다. "공부해야 하는 것"이 아니라 "해결해야 하는 것"이기 때문에 동기가 강합니다.

**패턴 2: 호기심 기반 출발**
> "package.json의 sideEffects 설정을 보고 '왜 CSS 파일만 여기 들어갈까?'라는 의문에서 시작했습니다."

> "10월 27일 렌더링 베이스캠프 마지막 수업 중 나왔던 질문에 대해 살펴봤습니다."

수업이나 설정 파일에서 발견한 작은 의문이 깊은 탐구로 이어집니다.

## 교훈

**잘 작동한 것**

- **정체성 프레이밍의 효과**: "나는 __에 강점이 있는 개발자입니다"라는 형식은 단순한 과제 제출과 다른 수준의 몰입을 만들었습니다. 48명 전원이 문서를 작성하고 공유한 것은 형식의 힘입니다. 자기 이름을 걸고 선언하면, 대충 조사해서 제출하기 어렵습니다.

- **주제의 자연스러운 분산**: 주제를 배정하지 않았는데도 렌더링, 성능 최적화, 빌드, 접근성 등 넓은 영역에 걸쳐 분산되었습니다. 각자의 프로젝트 경험과 호기심이 다르기 때문에, 자율 선택이 오히려 다양성을 만들었습니다.

- **동료 학습 자산**: 48개의 딥다이브 문서가 하나의 디스커션에 모여, 크루 전체가 접근할 수 있는 지식 베이스가 되었습니다. 한 사람이 모든 것을 알 수 없지만, 48명의 깊은 탐구를 간접적으로 접할 수 있습니다.

- **프로젝트와 학습의 연결**: 많은 크루가 자기 프로젝트에서 겪은 문제를 딥다이브 주제로 선택했습니다. "학습을 위한 학습"이 아니라 "문제 해결을 위한 학습"이 자연스럽게 일어났습니다.

**개선이 필요한 것**

- **깊이의 편차**: 48개 문서의 깊이가 균일하지 않습니다. 블로그 수준의 정리부터 소스 코드 분석까지 스펙트럼이 넓습니다. "강점"이라고 선언하려면 최소한 이 정도 깊이는 있어야 한다는 기준이 있으면 바닥을 높일 수 있습니다.

- **선언 이후 추적 부재**: "나는 __에 강점이 있는 개발자입니다"라고 선언한 뒤, 이 정체성이 이후 취업 준비나 포트폴리오에 실제로 연결되었는지 추적하는 구조가 없습니다. 선언이 일회성 이벤트로 끝날 위험이 있습니다.

- **크루 간 교차 피드백 부재**: 디스커션에 공유는 했지만, 서로의 문서를 읽고 피드백을 주는 구조가 약합니다. 유사 주제(예: Hydration을 다룬 4명)끼리 교차 리뷰를 했다면 더 깊은 학습이 가능했을 것입니다.
