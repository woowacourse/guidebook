# 발견 학습 설계하기: 답을 먼저 주지 않는 환경

[교육 철학](/education/philosophy#발견-학습)에서 **왜** 답을 먼저 주지 않는지를 봤다면, 이 페이지는 그 원칙을 **여러분의 미션·수업·코드 리뷰에 어떻게 심는가**를 다룹니다. 우테코가 실제로 적용해 본 사례를 보여드리고, 이어서 여러분의 환경에 맞게 설계하도록 돕는 LLM 스킬을 소개합니다.

## 한 줄 원리

**예측(Predict) → 관찰(Observe) → 설명(Explain).** 정답을 주입하지 않고, 배우는 사람이 먼저 예측하고 판단하고 설명합니다. 가르치는 사람의 설명은 그다음입니다. 핵심은 이 순서를 뒤집지 않는 것입니다. 강의를 먼저 하면 "이해한 것"으로 생각하기가 쉽습니다. 교차 증거는 [예측 먼저](/education/insights/predict-first-learning) 패턴에서 확인할 수 있습니다.

## 실전 적용 사례

우리는 서로 다른 기술 도메인에서 같은 메커니즘을 적용해 봤습니다. 자기 상황과 가장 가까운 사례부터 살펴보세요.

설계할 때 빠지기 쉬운 함정은 하나입니다. 설명을 먼저 하고 과제를 나중에 내는 "강의 → 실습" 순서입니다. 발견 학습 설계는 이 순서를 뒤집어야 작동합니다.

## 여러분 환경에 발견 학습 설계하기: LLM 스킬

<Callout type="tip">
**설계용 LLM 스킬을 GitHub에 공개합니다.** [발견 학습 설계 스킬 저장소](https://github.com/woowacourse/llm-skills)를 받아 여러분이 쓰는 LLM(ChatGPT·Claude 등)에 붙여넣어 보세요. 여러분의 미션·수업·리뷰 맥락을 입력으로 받아 **예측 과제 → 공개 시점 → 비교 회고**까지 발견 학습 흐름 한 벌을 설계해 줍니다.
</Callout>

스킬은 다음을 묻고 함께 채웁니다. 어떤 개념에 인지적 불일치를 만들 것인가, 무엇을 예측 산출물(해설지·에세이·리뷰 글)로 받을 것인가, 정답을 언제 공개할 것인가, 비교 회고를 어떻게 배치할 것인가.

### 프롬프트 예시: 스킬 없이 바로 써보기

저장소를 붙이기 전에, 아래 프롬프트를 복사해 `{중괄호}`만 여러분 맥락으로 바꿔 LLM(Claude·ChatGPT 등)에 넣어도 됩니다. 역할 부여, 명시적 제약, 먼저 오개념을 짚는 분석 단계, 우테코 사례, 출력 형식 고정을 함께 넣었습니다.

<PromptCopyBlock>

```text
# 목표
당신은 우아한테크코스의 발견 학습 설계를 돕는 교육 코치입니다.
내 수업·미션·코드 리뷰 맥락을 바탕으로 학습자가 정답을 듣기 전에 먼저 예측하고, 실제와 마주치고, 차이를 자기 말로 설명하는 활동 한 벌을 설계해 주세요.

# 배경
- 학습자: {예: 백엔드 레벨2 크루 16명}
- 다룰 개념: {예: 자바 비동기·동시성}
- 현재 어려움: {예: 말로는 아는데 코드로는 못 쓰는 상태}
- 사용할 장면: {예: 90분 수업 1회 / 코드 리뷰 / 미션 시작 전 안내}
- 현재 방식: {예: 강의 먼저, 실습 나중}
- 쓸 수 있는 자료: {예: 퀴즈 3개, 실행 가능한 샘플 코드, 선배 코드 AS-IS/TO-BE}
- 제약: {예: 추가 과제는 30분을 넘기지 않기, 채점하지 않기}

# 절대 원칙
1. 예측(Predict) → 관찰(Observe) → 설명(Explain) 순서를 지킵니다.
2. 정답·강의·모범 코드는 학습자가 예측·판단·설명을 먼저 산출한 뒤에 공개합니다.
3. 예측 산출물은 채점 대상이 아니라 관찰 대상입니다. 머릿속 모델의 허점을 드러내는 것이 목적입니다.
4. 비교 회고에서 "내 예측 vs 실제"의 간극을 학습자가 스스로 언어화하게 합니다.
5. 입력이 부족하면 질문만 하고 멈추지 말고, 최대 3개의 합리적 가정을 먼저 밝힌 뒤 설계를 진행합니다.

# 먼저 할 분석
1. 이 개념에서 학습자가 겉으로는 아는 듯하지만 실제 적용에서 흔들릴 만한 오개념을 1~2개 고릅니다.
2. 각 오개념이 어떤 예측 산출물에서 드러날지 짚습니다.
3. 그 오개념을 건드리기 위해 어떤 작은 불일치 경험을 만들지 정합니다.

# 만들어야 할 것
1. 30~90분 안에 실행할 수 있는 발견 학습 사이클 1개
2. 학습자에게 그대로 안내할 수 있는 문장
3. 코치가 중간에 던질 되묻는 질문
4. 정답·실제·모범 사례를 공개할 정확한 시점
5. 활동 후 비교 회고 질문
6. 이 설계가 "강의 → 실습"으로 되돌아갈 위험과 보정 방법

# 출력 형식
아래 골격을 그대로 사용해 답합니다.

## 입력 해석과 가정
- 내가 이해한 맥락:
- 부족한 정보에 대한 가정:

## 겨냥할 오개념
- 오개념 1:
- 왜 이 오개념이 생기는가:
- 어떤 산출물에서 드러나는가:

## 운영안
| 단계 | 시간 | 학습자 행동 | 코치 행동 | 산출물 |
| --- | --- | --- | --- | --- |
| Predict |  |  |  |  |
| Observe |  |  |  |  |
| Explain |  |  |  |  |

## 학습자 안내문
- 활동 시작 전에 그대로 말하거나 붙여넣을 안내문:

## 공개할 자료와 공개 시점
- 처음부터 공개할 것:
- 예측 뒤에 공개할 것:
- 끝까지 숨길 것:

## 비교 회고 질문
- 개인 회고 질문:
- 페어·조별 대화 질문:
- 코치가 되물을 질문:

## 설계 의도
- 왜 이 오개념을 겨냥했는가:
- 왜 이 순서여야 하는가:
- 학습자가 무엇을 스스로 발견하게 되는가:

## 실패 신호와 보정
- 실패 신호:
- 그때의 보정 질문 또는 운영 변경:

# 참고 사례
우테코에서 실제로 쓴 발견 학습 변형 사례입니다. 내 맥락에 맞게 그대로 복제하지 말고 원리를 빌려 설계합니다.

- 비동기 수업: 강의 대신 "비동기 퀴즈 해설지를 먼저 쓰게" 해서 설명 능력 자체를 관찰 대상으로 삼았습니다.
- 선배 코드 리뷰: 모범 코드를 보여주기 전에 AS-IS 코드를 먼저 판단하게 하고, 이후 TO-BE와 비교하게 했습니다.
- 재구현 수업: 강의 전에 사전 에세이로 재구현의 가치와 한계를 예측하게 한 뒤 강의와 대조했습니다.

# 품질 점검
답을 마치기 전에 스스로 확인합니다.
- 설명·강의·모범 코드가 예측보다 앞서 있지 않은가?
- 예측 산출물이 채점이 아니라 관찰 대상으로 설계됐는가?
- 학습자가 "내 예상과 실제의 차이"를 자기 말로 설명하게 되는가?
- 코치의 개입이 정답 제공이 아니라 되묻기와 비교 돕기에 머무르는가?
```
