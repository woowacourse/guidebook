# 논증 기반 학습 설계: 정답을 주지 않고 설명하게 만들기

<Callout>
**핵심 발견**: "정답을 맞혀라"를 "왜 그런지 다른 사람에게 설명하라"로 바꾸면, 같은 내용도 훨씬 깊게 이해한다. 4개 로그에서 레벨1부터 레벨4까지 독립적으로 발견된 패턴.
</Callout>

## 패턴 요약

코치가 정답을 전달하는 대신, 크루가 자기 언어로 개념을 설명·논증하도록 활동을 설계한다. "해설지를 써라", "선언하고 피드백받아라", "팀 컨벤션의 근거를 논거하라"처럼 형식은 다양하지만, 핵심 메커니즘은 동일하다. **설명하는 행위 자체가 이해를 만든다.**

이 패턴은 레벨1(비동기 개념)부터 레벨4(기술 결정)까지, 그리고 컨벤션·SSR·접근성 등 서로 다른 주제에 걸쳐 반복된다.

## 핵심 원칙

1. **"설명하라"가 "맞혀라"보다 깊다** — 정답 입력은 이해 없이도 가능하다. 설명 쓰기는 개념의 내적 구조를 가동시켜야 가능하다. 같은 주제라도 "OX 체크"와 "해설지 작성"의 학습 깊이는 다르다.

2. **의도적 모호성이 논증을 유발한다** — "하이드레이션 과정에서 첫 화면을 검증하지 않는다"처럼 정답이 하나로 수렴하지 않는 명제를 설계하면, 크루가 개념의 경계를 탐색하게 된다. 선명한 명제는 탐색을 멈춘다.

3. **페이지·사례 단위 구체화가 논증을 강제한다** — "SSR을 쓴다"는 추상이지만, "어떤 페이지에 어떤 이유로"는 논증을 요구한다. 단위를 쪼개면 얼버무림이 불가능해진다.

4. **자기 언어 기록이 자산이 된다** — 논증한 내용이 디스커션·문서로 남으면, 크루 본인의 이해 과정이 추적 가능해지고 후배 기수의 참고 자료가 된다.

## 적용 가이드

| 상황 | 적용 방법 | 주의점 |
|------|-----------|--------|
| 추상 개념 학습 (비동기, SSR, TS 타입 등) | O/X 판단 후 해설지 작성 | 명제의 모호성을 의도적으로 설계할 것 |
| 기술 결정 훈련 | 선언 → 팀×팀 피드백 → 개정 3단계 | 피드백 반영 여부를 본문에 명시 강제 |
| 팀 컨벤션 정립 | "왜 그렇게 쓰는가" 메타 질문 포함 | 나열이 아닌 논거를 요구하는 템플릿 설계 |
| 자기 서비스 분석 | 일반 사례가 아닌 자기 코드·서비스 대상 | 자기 서비스 진단은 발견 즉시 코드베이스 반영으로 연결 |
