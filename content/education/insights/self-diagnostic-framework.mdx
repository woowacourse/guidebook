# 자기 진단 프레임워크: 추상 가치를 측정 가능한 기준으로 전환하기

> "성능을 높여라", "피드백을 잘 해라" 같은 추상어를 크루가 직접 돌릴 수 있는 진단 기준으로 번역하는 설계 원칙.

## 패턴 요약

"좋은 X를 만들어라"는 목표를 크루가 소화할 수 있게 하려면, 추상 가치를 **명시적 진단 기준 → 자기 대상 적용 → 개선 액션**의 3박자로 분해해야 한다. 4개 이상의 로그에서 같은 구조가 서로 다른 도메인(성능, 접근성, 피드백, 성장)에 독립적으로 발견되었다. 특히 성능 리포트 프레임워크가 접근성 리포트로 거의 그대로 이식된 사례는 프레임워크의 재사용성을 직접 실증한다.

## 근거 로그

| 로그 | 카테고리 | 기여 요소 |
|------|----------|-----------|
| [FE 성능 리포트](/education/logs/fe-performance-report) | 레벨3 | 측정 → 분석 → 개선 3단계 프레임워크, 5·6·7기 기수별 진화 |

| [나의 성장 그래프](/education/logs/growth-graph) | 소프트스킬 | 기술/소프트스킬 성장 곡선 + 감정 키워드로 자기 레벨을 시각 진단 |

## 핵심 원칙

- **기준이 먼저, 대상이 다음이다.** 크루에게 진단을 시키기 전에 평가 차원(3~5개)과 점수/등급 체계를 먼저 명시해야 한다. 기준 없는 진단은 감상문이 된다.
- **진단 대상은 자기 것이어야 한다.** 남의 코드·서비스·피드백이 아닌, 자기 팀·자기 산출물을 대상으로 해야 개선 액션이 실제로 실행된다.
- **프레임워크는 재사용 가능하게 설계한다.** "성능 리포트 → 접근성 리포트"처럼 같은 구조를 다른 도메인으로 옮겨 쓸 수 있어야 누적 자산이 된다.
- **누적 자산으로 다음 기수에 넘긴다.** 6기가 만든 리포트를 7기의 입력으로 사용하면, 진단은 단일 이벤트가 아니라 기수를 넘는 지식 축적 구조가 된다.

## 적용 가이드

- **언제 쓰는가:** 학습 목표가 "성능/품질/상호작용을 높여라"처럼 추상적일 때. 크루가 무엇을 어떻게 개선해야 할지 막막한 순간이 시작점이다.
- **어떻게 쓰는가:**
  1. 도메인 전문가와 함께 평가 차원 3~5개를 정의한다 (예: 성능=LCP·FID·CLS·INP·TBT).
  2. 각 차원에 5점 척도와 근거 기준을 붙인 진단 템플릿을 만든다.
  3. 크루가 자기 팀 산출물에 템플릿을 적용해 리포트를 작성한다.
  4. 리포트를 다음 기수의 시작 자료로 공개해 누적되게 한다.
- **피해야 할 것:** 전문가가 만든 리포트를 크루에게 배포하는 수동적 구조. 크루가 직접 쓰지 않으면 프레임워크가 체화되지 않는다.
