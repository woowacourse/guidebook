# 코드랩으로 관심사 분리 체험하기

<Callout>
**대상**: 코드 설계 원칙을 강의 대신 경험으로 전달하려는 코치

**맥락**: 레벨 1 · 로또 2단계 미션 소개 수업 (2026-03-10, 웹 FE 8기 25명)

**핵심 질문**: "도메인과 UI를 분리해야 한다"는 말을 크루가 스스로 발견하게 하려면?
</Callout>

## 배경과 문제

로또 1단계를 마친 크루들은 콘솔 기반의 도메인 로직을 완성한 상태입니다. 2단계 미션은 이 코드를 웹 UI로 전환하는 것인데, 요구사항에는 이런 조건이 붙습니다.

> "1단계에서 구현한 도메인 로직을 (최대한) 수정하지 않고, UI만 변경한다."

"관심사 분리"는 말로 설명하기 쉽지만, 실제로 느끼기는 어렵습니다. 도메인과 UI를 섞어 짠 코드가 왜 문제인지 추상적으로 이해하는 것과, 직접 테스트가 깨지는 순간을 보는 것은 다른 경험입니다.

코치가 원칙을 설명해주는 방식 대신, **크루가 코드를 직접 수정하면서 문제를 발견하게** 하는 수업을 설계했습니다.

## 설계

### 전체 구조: 예측 → 관찰 → 설명 (POE)

수업은 두 부분으로 구성됩니다.

| 파트 | 시간 | 활동 | 역할 |
|------|------|------|------|
| 요구사항 읽기 | 10분 | 페어 토론으로 예측 만들기 | **P** (Predict) |
| 코드랩 | 40분 | 4단계 실습으로 직접 확인 | **O + E** (Observe + Explain) |

중요한 설계 원칙은 **코드랩 진입 전에 반드시 예측을 세우게 하는 것**입니다. 예측 없이 코드랩에 들어가면 "아, 그렇구나"로 끝납니다. 예측이 있어야 틀린 지점에서 배움이 생깁니다. 코치는 이 단계에서 정답을 알려주지 않습니다 — **틀린 예측이 가장 좋은 예측**이기 때문입니다.

### 파트 1: 요구사항 읽기 (10분)

페어와 함께 3가지 질문에 답하는 시간입니다.

| 질문 | 코치 의도 |
|------|-----------|
| Q1. 구현하면서 어떤 점이 어려울까? | 가장 열린 질문으로 자유로운 예측 도출 |
| Q2. 이 미션의 핵심은 무엇일까? | 크루 스스로 핵심을 판단하게 함 |
| Q3. "바꿔야 할 부분"과 "그대로 쓸 수 있는 부분"은? | 자신의 코드를 머릿속에서 구체적으로 분류 |

**실제 크루 응답 분포:**

- Q2 응답 대부분이 **"도메인과 UI의 관심사 분리"**를 핵심으로 언급했습니다. 이미 개념적으로는 알고 있다는 뜻입니다.
- Q3에서는 "바꿔야 할 부분: View, Controller", "그대로 쓸 부분: 도메인 로직, 유틸, 상수"라는 대답이 많았습니다.

예측은 대체로 맞습니다. 코드랩은 이 예측이 **실제 코드에서 어떻게 작동하는지** 확인하는 자리입니다.

### 파트 2: 코드랩 — 4단계 실습 (40분)

인터랙티브 코드랩([fe-code-lab.vercel.app](https://fe-code-lab.vercel.app/))을 활용합니다. 브라우저 안에서 코드를 수정하면 테스트가 즉시 실행됩니다. 각 단계는 이전 단계를 완료해야 열립니다.

**전체 흐름: 관찰 → 문제 발견 → 리팩터링 → 완성**

#### Step 1: 관찰 — "이 코드에서 무엇이 보이나요?"

```javascript
class Lotto {
  #validate(numbers) { ... }  // 데이터 검증
  matchCount(target)  { ... } // 도메인 로직

  printNumbers()      { console.log(...) } // ← UI?
  printMatchResult()  { console.log(...) } // ← UI?
}
```

페어가 함께 각 메서드를 "데이터를 다루는 것"과 "결과를 보여주는 것"으로 분류합니다. 대부분 `printNumbers`와 `printMatchResult`가 분리 대상임을 파악합니다.

#### Step 2: 문제 발견 — "UI를 바꾸면 테스트가 깨집니다"

`console.log(...)` 를 `return ...` 으로 바꿔보는 실습입니다. 코드를 수정하고 테스트를 실행하면 5개 중 1개가 실패합니다.

```
✓ validate: 유효하지 않은 번호 개수
✓ validate: 범위 밖의 번호
✓ validate: 중복 번호
✓ matchCount: 3개 일치
✗ printNumbers: 콘솔에 번호를 출력 ← 실패
```

이 순간이 핵심입니다. 크루들은 "UI를 건드렸을 뿐인데 왜 도메인 테스트가 깨지나?"를 직접 목격합니다.

<Callout type="info">
코드랩이 "예상 실패"를 지원합니다. Step 2는 테스트가 정확히 4개 통과 + 1개 실패일 때 완료 처리됩니다. 크루가 실패를 성공으로 오해하지 않도록 설계된 구조입니다.
</Callout>

#### Step 3: 리팩터링 — "도메인에서 UI를 분리하세요"

`printNumbers`, `printMatchResult` 를 삭제하고, 대신 `getNumbers()` 메서드를 구현합니다.

```javascript
getNumbers() {
  return [...this.#numbers]; // 복사본 반환
}
```

"왜 복사본을 반환해야 하나요?"라는 토론 질문이 등장합니다. 외부에서 배열을 수정해도 내부 상태가 변하지 않아야 하기 때문입니다. 캡슐화의 구체적인 이유를 발견하는 순간입니다.

테스트를 실행하면 전부 통과합니다.

#### Step 4: 완성 — "도메인은 그대로, UI만 새로 붙이기"

별도 파일(`ui.js`)에서 `renderLottoToHTML()` 함수를 구현합니다. `Lotto.js`는 한 줄도 수정하지 않습니다.

```javascript
function renderLottoToHTML(lotto) {
  const numbers = lotto.getNumbers();
  return numbers.map(n => `<span class="lotto-ball">${n}</span>`).join('');
}
```

테스트 전부 통과. 도메인이 콘솔용으로도, 웹용으로도, 모바일용으로도 수정 없이 재사용됩니다.

### 수업 결과: 크루들이 발견한 것

코드랩 토론에서 크루들이 공통으로 뽑은 핵심 키워드입니다.

| 키워드 | 언급 수 |
|--------|---------|
| 도메인과 UI 관심사 분리 | 거의 전원 |
| 도메인 코드 수정 최소화 | 7명 |
| 책임 분리 / 모듈화 | 5명 |
| 확장성 고려 | 2명 |

예측 단계에서 이미 "관심사 분리가 핵심"을 알고 있던 크루들이, 코드랩을 통해 **왜 그래야 하는지**를 직접 경험했습니다.

**주목할 논점**: 벤지는 `renderLottoToHTML`이 "로또를 다루는 함수이므로 Lotto 클래스 안에 있어야 한다"는 다른 의견을 제시했습니다. 이 관점 차이는 후속 피드백 수업의 소재가 됩니다.

### 액션 플랜: 크루들의 약속

코드랩 후 크루들은 2단계 미션에서 지킬 액션 플랜을 작성했습니다. 비슷한 방향의 크루끼리 A/B 두 그룹으로 나뉩니다.

**A그룹 (16명): 도메인을 지킨다**

> "도메인 로직 수정하지 않고 UI 로직 구현"
> "도메인 수정 필요 시 이유/의도 명확히 파악 후 회고 글로 남기기"
> "1단계 도메인 테스트 1글자도 바꾸지 않기"

**B그룹 (9명): 테스트를 확장한다**

> "도메인 테스트 + HTML 요소 관련 테스트 진행"
> "모든 UI가 아닌 사용자 경험 기준으로 테스트"
> "UI 테스트와 도메인 테스트 분리"

## 후속 수업: 내 약속, 내 코드

약 2주 후 2단계 완성 시점에 50분 피드백 수업을 진행합니다. 코드랩에서 세운 액션 플랜이 실현되었는지 자기 코드로 직면하는 자리입니다.

### 이중 인지 갈등 설계

이 수업의 핵심은 두 차례의 인지 갈등을 의도적으로 만드는 것입니다.

| 갈등 | 비교 대상 | 질문 |
|------|----------|------|
| 1차 | 내 약속 vs 내 결과 | 코드랩에서 한 약속을 실제로 지켰나? |
| 2차 | 내 결과 vs 동료 결과 | 같은 약속을 한 동료는 어떻게 풀었나? |

갈등이 없으면 배움도 없습니다. "내가 4점이라고 생각했는데 실제 코드를 보니 도메인을 20줄 바꿨다"는 괴리가 스키마를 재구성합니다.

### 50분 진행 구조

| 시간 | Step | 내용 |
|------|------|------|
| 0~5분 | 1 | 5점 척도로 내 약속 자기진단 |
| 5~8분 | 2 | A/B 그룹 소그룹 형성 |
| 8~18분 | 3 | 실제 코드 열어 약속 이행 여부 확인 (1차 갈등) |
| 18~30분 | 4 | 같은 약속한 선배 PR 탐색 (2차 갈등) |
| 30~37분 | 5 | 선배 힌트 + 코치 원칙 연결하기 |
| 37~44분 | 6 | 다음 액션 플랜 1개 만들기 |
| 44~50분 | 7 | 전체 공유 + A↔B 엿보기 |

### 그룹별 피드백 원칙

**A그룹 핵심 원칙**

| 원칙 | 설명 |
|------|------|
| 도메인은 "어떻게 보여줄지" 모른다 | UI의 존재를 모르는 상태를 유지 |
| 변경 방향은 단방향 | UI가 도메인을 사용하고, 도메인은 UI에 의존하지 않음 |
| 렌더링 로직은 밖에 | HTML 생성 코드는 도메인 클래스 바깥에 |

**B그룹 핵심 원칙**

| 원칙 | 설명 |
|------|------|
| 도메인 테스트와 UI 테스트 분리 | UI 변경이 도메인 테스트에 영향을 주지 않음 |
| 테스트는 구현 세부사항에 의존하지 않음 | 내부 구현이 아닌 동작(결과)을 검증 |
| 사용자 경험 기준 테스트 | 모든 UI가 아닌 사용자 시나리오 단위로 |

### 5점 척도의 역할

Step 1의 자기진단은 성적 평가가 아닙니다. Step 3에서 실제 코드와 대조할 기준점을 만드는 것입니다.

| 점수 | 의미 |
|------|------|
| 5 | 자신 있게 지켰다. 코드로 설명 가능 |
| 4 | 대체로 반영. 아쉬운 부분 있지만 방향은 맞음 |
| 3 | 감을 잡았다. 부분 시도, 확신 없음 |
| 2 | 잘 모르겠다. 시도했는데 맞게 한 건지 판단 불가 |
| 1 | 기능 구현에 급급. 약속 신경 쓸 여유 없음 |

"지금 느낌 그대로 체크하세요"가 코치의 안내입니다. 낮은 점수도 나쁜 게 아닙니다 — Step 3에서 실제로 무엇을 발견하느냐가 중요합니다.

## 교훈

**잘 작동한 것**

- **예측 → 관찰 순서**: 코드랩 진입 전 예측을 만드는 단계가 학습 몰입을 높였습니다. 크루들이 이미 "관심사 분리가 핵심"을 알고 있었기 때문에, 코드랩은 "아는 것"이 실제 코드에서 왜 어떻게 적용되는지를 느끼는 시간이 됐습니다.
- **테스트가 깨지는 순간 직접 목격**: Step 2에서 console.log를 return으로 바꾸는 단순한 조작 하나로 테스트가 깨집니다. 코치가 "UI 변경이 도메인 테스트에 영향을 준다"고 설명하는 것보다, 직접 보는 것이 훨씬 강렬합니다.
- **액션 플랜의 연속성**: 코드랩에서 세운 약속이 2주 뒤 피드백 수업의 출발점이 됩니다. 크루가 스스로 세운 약속이기 때문에, "이게 얼마나 지켜졌나"를 확인하는 자리에 더 몰입합니다.
- **A/B 그룹 분류**: 같은 약속을 한 동료끼리 묶는 구조가, 비교 학습의 질을 높였습니다. "도메인을 지키겠다"는 약속을 한 크루들이 서로 다른 방식으로 구현한 코드를 비교할 때, "나도 저렇게 할 수 있었겠다"는 근접발달영역이 자연스럽게 형성됩니다.

**개선이 필요한 것**

- **코드랩 Tool 제약**: 현재 코드랩은 웹 FE 기준 JavaScript로 작성되어 있습니다. 안드로이드 크루들에게 적용하려면 별도 코드랩이 필요합니다.
- **예측 단계의 시간 배분**: 10분이 짧게 느껴지는 경우가 있었습니다. Q1만으로도 충분히 예측이 만들어지므로, 상황에 따라 Q1 중심으로 압축하는 것을 고려할 수 있습니다.
- **피드백 수업의 Step 5 시간**: 선배 PR 힌트와 코치 원칙을 연결하는 단계(7분)가 짧았습니다. 원칙을 내 코드의 구체적인 위치에 대입하는 데 더 많은 시간이 필요합니다.
- **벤지 논점 후속 처리**: "renderLottoToHTML이 Lotto 클래스 안에 있어야 한다"는 관점은 공개 토론으로 다룰 만한 논점입니다. 피드백 수업에서 A그룹 공유 시간에 포함하는 것을 검토 중입니다.
