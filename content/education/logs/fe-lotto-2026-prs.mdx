# 로또 미션 8기: PR 57개로 본 콘솔에서 웹으로의 관심사 분리

<Callout>
**대상**: 레벨1 자바스크립트 미션을 설계하고 코칭하는 코치, 교육 모델 설계자

**맥락**: `woowacourse/javascript-lotto`는 2021년에 연 레벨1 대표 미션입니다. 2026년(8기)에는 25명의 크루가 57개의 PR을 올렸고, 그 위에 983건의 리뷰 코멘트가 쌓였습니다. 1단계(콘솔)와 2단계(웹)로 같은 로또 도메인을 두 번 짓는 구조라, 1단계에서 도메인과 UI를 제대로 갈라 뒀는지가 2단계에서 그대로 드러납니다.

**핵심 질문**: 올해 크루들은 이 미션에서 무엇을 가장 많이 고민했고, 우리는 무엇을 길러주려 했는가?
</Callout>

## 2026 PR 한눈에

올해 PR은 단계가 두 갈래로 갈립니다.

| 단계 | PR 수 | 학습 초점 |
| --- | --- | --- |
| 1단계(콘솔 기반 로또) | 28 | 도메인과 UI 분리, TDD로 점진적 리팩터링 |
| 2단계(웹 기반 로또) | 27 | 도메인은 그대로 두고 뷰만 교체, 상태 기반 렌더링 |

같은 도메인을 콘솔로 먼저 만든 뒤 웹으로 옮기는 구성이 이 미션의 핵심 장치입니다. 1단계에서 도메인을 UI에 섞어 두면 2단계에서 반드시 비용을 치르기 때문에, 미션 구조 자체가 관심사 분리를 검증하는 리트머스로 작동합니다.

올해 983건의 리뷰 코멘트에서 반복해서 올라온 주제는 다음과 같습니다.

- **검증과 에러 처리를 어디에 둘 것인가**: 도메인·컨트롤러·뷰 중 검증 책임의 위치가 올해 최다 논쟁 주제였습니다.
- **도메인의 개념과 표현 수단을 구분하기**: "로또"라는 개념과 그것을 담는 class/instance는 다른 층위라는 코칭이 반복됐습니다.
- **OOP 기초 제약**: 인스턴스 변수 3개 제한, getter 사용 여부, "객체에 메시지를 보낸다" 원칙.
- **TDD의 본질**: 테스트를 먼저 쓰는 일과 테스트를 작성하는 일은 다른 층위라는 토론.
- **콘솔에서 웹으로의 사고 전환**: 절차적 흐름에서 상태·이벤트 기반 설계로의 이동.

## 인상적인 리뷰·학습 장면

올해 PR에서 가장 깊은 대화가 오간 장면을 원문 그대로 옮깁니다. 모두 PR 번호를 함께 남깁니다.

### 도메인의 "개념"과 "표현"을 가르다 ([PR #445](https://github.com/woowacourse/javascript-lotto/pull/445))

> 우선 도메인이라는 개념과, 그걸 실제로 표현하는 방식은 다른 것이라는 걸 인지하면 좋을 것 같습니다. (…) 로또라는 도메인 개념을 예로 들면, 6개의 번호 / 번호는 1~45 사이의 정수 / 번호간 중복이 없음 (…) 근데 여기에 고민하셨던 '특정 형태의 문자열을 받아서, 특정한 방식으로 가공하는 것'이 실제로 도메인 규칙에 포함된다고 할 수 있을까요?

추상적인 "도메인을 분리하라"는 주문을, 크루가 직접 만질 수 있는 규칙 목록으로 끌어내립니다. 경계를 대신 그어 주는 대신, 경계를 그을 기준을 쥐여 줍니다.

### 콘솔과 웹은 흐름이 다르다 ([PR #466](https://github.com/woowacourse/javascript-lotto/pull/466))

> 콘솔과 웹은 Flow가 달라요. 콘솔은 '순차적(절차적)'으로 동작하지만, 웹은 '이벤트 기반'으로 동작해요. 현재 while 코드를 보면 입력 > 처리 > 출력이 순차적으로 일어나고 있는데 이는 웹에서는 적합하지 않아요. (…) 보통 웹에서 설계를 할 때엔 상태 기반으로 구현을 하는 경우가 많이 있어요.

1단계에서 2단계로 넘어갈 때 크루가 가장 자주 놓치는 지점입니다. `while`로 순서를 통제하던 사고를, 상태가 바뀌면 화면이 따라 그려지는 사고로 바꾸도록 짚어 줍니다.

### 에러 처리에는 정답이 없다 ([PR #426](https://github.com/woowacourse/javascript-lotto/pull/426))

> 요건 에러 처리 책임을 어디에 둘 것인가에 대한 문제인데요. 이것 또한 정답은 없어요. (…) 1. 방어로직으로 바로 return하는 경우 (…) 2. new Error()로 명시적 에러를 던지는 경우 (…) 사용하는 쪽에서 에러 처리에 대한 책임이 강해지기 때문에…

정답을 내려 주는 대신 두 선택지의 장단점을 펼쳐 둡니다. 크루는 맥락에 맞게 책임의 경계를 스스로 정하는 연습을 합니다.

### `type="number"`만 믿으면 안 되는 이유 ([PR #450](https://github.com/woowacourse/javascript-lotto/pull/450))

> 재밌게도 type='number'는 브라우저마다 입력 경험이 달라질 수 있어요. (…) 'e', '-', '.'처럼 부동소수점/지수 표기와 관련된 문자는 중간 상태로 허용하는게 가능해요! (…) 애니의 앱에서도 '1e3'으로 다음 스텝이 통과됩니다!

"HTML이 막아 주니 검증은 필요 없다"는 흔한 오개념을, 실제 재현으로 반증합니다. 도메인 레벨 검증이 왜 필요한지를 말이 아니라 경험으로 깨닫게 합니다.

### "반쪽짜리 TDD"라는 고민에 답하다 ([PR #423](https://github.com/woowacourse/javascript-lotto/pull/423))

크루가 "기능을 먼저 구현하고 테스트를 나중에 썼으니 반쪽짜리 TDD 아니냐"고 묻자, 코치는 이렇게 답합니다.

> 저는 우선 TDD랑 테스트 코드 작성을 조금 다른 레벨의 이야기라고 생각하고 있어요. TDD는 말 그대로 테스트를 먼저 쓰면서 도메인 로직과 기획 요구사항을 한 줄 한 줄 구체화해 가는 개발 방식에 가까운 것 같아요.

PR이 코드 리뷰를 넘어, 개발 방법론을 함께 더듬어 보는 멘토링 채널로 쓰인 장면입니다.

## 올해 길러진 핵심 교육 경험

1. **도메인을 건드리지 않고 뷰만 교체하며 관심사 분리를 몸으로 익혔습니다.** 콘솔에서 웹으로 같은 도메인을 옮기는 2단계 구조가, 1단계 분리의 품질을 자동으로 채점했습니다. 크루들은 getter 추가나 MVC 도입 같은 결정을 코치와 협상하며 "분리의 비용과 이득"을 직접 따졌습니다.

2. **검증과 에러 처리의 "위치"를 정하는 힘을 길렀습니다.** 가장 잦은 리뷰 주제가 "이 검증을 어디에 둘 것인가"였고, 우리는 정답 대신 트레이드오프를 펼쳐 크루가 맥락에 따라 책임 경계를 설계하도록 했습니다.

3. **코드 리뷰를 "정답 확인"이 아니라 "설계 의도를 설명하고 변호하는 대화"로 경험했습니다.** PR 템플릿이 "고민한 의사결정을 공유하고 정답을 묻지 말라"고 안내했고, TDD의 본질이나 브라우저 동작 같은 깊은 토론이 PR 스레드에서 일어나며 글로 사고를 정리하는 훈련이 함께 이뤄졌습니다.
