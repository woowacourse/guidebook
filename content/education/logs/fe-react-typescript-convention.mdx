# FE React & TypeScript 컨벤션 워크숍: 5기와 7기 사이의 2년 변화

<Callout>
**대상**: 팀별 기술 컨벤션을 자기 언어로 정립하게 만들려는 코치

**맥락**: 5기 FE 레벨2 (2023.08.01) · 7기 FE 레벨2 (2025.08.05)

**핵심 질문**: 같은 템플릿을 2년 간격으로 운영했을 때, 크루의 TypeScript 사고는 어떻게 달라지는가?
</Callout>

## 배경과 문제

TypeScript는 "어떻게 쓰는가"에 정답이 없다. 컴포넌트 선언 방식, Props 타입, Children 처리, Ref 활용 등 모든 결정이 팀의 가치 판단이다.

기존 강의식으로 "베스트 프랙티스"를 전달하면 두 가지 부작용이 있었다.

1. **맹목적 모방**: 강의에서 본 패턴을 자기 코드에 그대로 복붙
2. **이유 망각**: "왜 그렇게 쓰는가"를 설명하지 못함

## 설계

### 공통 템플릿 (5기 #37 / 7기 #69 동일)

팀별로 하나의 코멘트에 다음 항목을 정리:

- Component (선언 방식, Props, with/without Children, Event)
- Hooks (기본 훅, Ref)
- 모듈 (type 관리, import/export)
- API (Request/Response Type)
- 빌드 설정 (loader, tsconfig)
- 공유하고 싶은 내용 / 참고 자료

### 7기에서 추가된 항목

7기 템플릿에는 **"우리 팀/서비스의 TS 활용 경험"** 섹션이 새로 추가되었다.

- *"TypeScript는 우리 팀에 도움이 되고 있나요? 어떤 측면에서 도움이 되고, 혹은 어떤 측면에서는 어려움이나 불편을 겪고 있나요?"*
- *"우리 팀에서 TypeScript를 사용할 때 중요하게 생각하는 부분은?"*

기술 컨벤션을 나열하기 전에 **"우리에게 TS는 무엇인가"** 를 먼저 묻는 메타 질문이 추가된 것이다. 5기 → 7기 사이의 2년 동안, "사용한다"에서 "왜 사용하는가"로 학습 초점이 이동했음을 보여준다.

### 핵심 설계 원리

- **나열이 아닌 컨벤션**: 항목별로 단순 코드 예시가 아닌 "우리 팀의 결정과 그 근거"를 요구
- **집단지성**: 팀별 결정이 모두 디스커션에 공개되어 다른 팀의 선택과 비교 가능

## 결과

### 1. 5기 — 항목 나열형 컨벤션

5기 팀들은 자기 팀 컨벤션을 항목별로 **나열**하는 형식이 압도적이었습니다.

- **Component 선언 방식 — 화살표 함수가 다수파**:
  > "다른 함수 선언에도 표현식을 사용했기 때문에 코드의 일관성 유지를 위해 컴포넌트를 작성할 때에도 함수 표현식을 사용했습니다." — 집사의고민팀

- **Props 네이밍 `{컴포넌트명}Props`**:
  > "`Props`로 명시했을 때 모든 컴포넌트의 Props가 검색되어 찾기 어렵다. 따라서 `컴포넌트 이름+Props`로 정의해 보다 직관적으로 명시한다." — 펀잇팀

- **Children 처리**: 팀바팀은 "Component with Children의 경우 `PropsWithChildren`을 사용하고, react에서 import한다" 라는 단순 규칙으로 정리.

- **Event Handler 타입에서 갈린 사례**: 펀잇팀은 "이벤트 자체의 타입보다는 함수의 타입을 지정해 명시적으로 쓰고 싶어서" `MouseEventHandler<HTMLButtonElement>` 사용. 팀바팀은 반대로 이벤트 타입을 직접 명시. **같은 항목에 대한 정반대 결정**이 디스커션에 공존.

5기 단계에서 컨벤션 간 충돌은 디스커션 본문에 잘 드러나지 않았고, 팀 간 토론 흔적도 적었습니다.

### 2. 7기 — 메타 질문, 토론 세션, 자동화·수치 의사결정

7기는 두 가지 큰 변화가 있었습니다.

**(a) 메타 질문 응답**

- 모아온팀: 도움 = "런타임 에러 방지하여 의미없는 에러 메시지를 줄일 수 있다 / DX 개선 (IDE 자동완성 추론 가능)", 불편 = "복잡도 증가 (간단한 것을 만드는데 계속 써야하는 귀찮음)"

- 포게더팀(ShinjungOh)은 컨벤션을 넘어 **방법론**을 도입:
  > "**IDD(Interface Driven Development) : 인터페이스 주도 개발** — 인터페이스를 먼저 정의하고 컴포넌트나 커스텀 훅 개발"

- 핏토링팀은 emotion Theme을 **선언 병합으로 확장**한 사례까지 공유.

**(b) 팀 간 토론 세션이 별도 코멘트로 정리됨**

7기 디스커션에는 5기에 없던 "🔥 레전드 TS 토론 — 참가팀: 봄봄, 픽잇, 커피빵, 아맞다" 라는 별도 토론 정리 코멘트(rosielsh, yeji0214, yeongipark, hanheel)가 등장합니다. 함수 표현식/선언식, type vs interface, PropsWithChildren을 항목별로 비교한 기록입니다.

이 토론에서 **의견이 명확히 갈린 항목**:

- **함수 선언 방식**: 봄봄·커피빵·아맞다·모잇지(표현식) vs **픽잇**: "컴포넌트만 선언식 (호이스팅 문제 + 메인 로직을 위에 두는 게 좋다)"
- **type vs interface**: 봄봄 "interface(타입스크립트에서 interface를 권장)" / 커피빵 "통일성 때문에 다 type으로 맞춤" / 아맞다 "interface는 유니온이 안됨" / 픽잇 "거의 type을 사용하나, 타입 상속을 받아 분기 처리해야 하는 경우에는 interface가 더 유용"
- **PropsWithChildren**: 픽잇 "Component with Children 안쓰고 children을 타입으로 지정 — children을 받는 컴포넌트인지 아닌지를 명시적으로 관리해주기 위해" vs 그 외 팀은 사용

**(c) 자동화 도구 도입과 수치 기반 의사결정**

5기에는 없던 새로운 결정 패턴이 등장했습니다.

- 봄봄팀: **openAPI 타입스크립트 자동 생성** — "백엔드 서버 url/v3/api-docs ... `generate-openapi-types` 명령어를 치면 ... 자동으로 정의됨"
- 모아온팀: **벤치마킹 결과 기반 도구 선택** — "벤치마킹 결과: 빌드 속도 7~20배 개선"

5기 컨벤션이 "어떻게 쓰는가"의 코드 패턴 합의였다면, 7기는 "왜 쓰는가 / 어떤 도구로 자동화하는가"까지 확장된 셈입니다.

## 교훈

**잘 작동한 것**

- **항목별 강제**: Component 선언부터 빌드 설정까지 강제 항목이 있어 빠뜨리는 영역이 없었습니다. 5기와 7기 모두 동일.
- **메타 질문 추가 (7기)**: "TS가 도움이 되는가 / 어려움이 있는가"라는 질문이 코드 패턴 나열을 넘어 **경험 기반 진단**을 끌어냈습니다.
- **별도 토론 세션 코멘트화**: 7기에서 팀 간 토론 결과를 별도 코멘트로 정리한 것이, 5기에 없던 "교차 비교" 자료를 만들었습니다. 이 형식을 차기에 명시 단계로 박을 가치가 있습니다.
- **자동화·수치 의사결정 등장**: 5기 → 7기 사이에 "느낌으로 좋다"가 "벤치마크 7~20배"로 바뀐 것은 워크숍의 직접 효과는 아니지만, 워크숍이 그 사고를 공개적으로 전파하는 장이 되었습니다.

**개선이 필요한 것**

- **6기 누락**: 5기와 7기 사이에 6기 데이터가 없어 점진적 변화 추적이 어렵습니다. 컨벤션 워크숍은 매년 운영해 누적할 가치가 있습니다.
- **5기 갈린 의견의 사후 정리 부재**: 펀잇 vs 팀바팀의 Event Handler 타입처럼 정반대 결정이 디스커션에 공존하지만, "어느 쪽이 왜 나았는가"를 정리한 흔적이 없습니다.
- **컨벤션 사후 추적 부재**: 워크숍에서 정한 컨벤션이 실제 코드베이스에 반영·유지되었는지 추적하는 구조가 없습니다. 레벨2 종료 시점에 "컨벤션 회고" 1회를 추가하면 순환이 닫힙니다.
