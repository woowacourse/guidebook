# 렌더링 전략 워크숍: 팀×팀 피드백으로 기술 결정 단단히 만들기

<Callout>
**대상**: 기술적 의사결정 능력을 훈련시키려는 코치

**맥락**: 7기 FE 레벨4 (2025) 팀 프로젝트

**핵심 질문**: "CSR이냐 SSR이냐"라는 결정을, 정답 찾기가 아닌 **자기 팀 요구사항 기반의 논증 훈련**으로 만들 수 있을까?
</Callout>

## 배경과 문제

레벨4에서 크루들은 자기 팀 서비스의 렌더링 전략을 결정해야 한다. 이전 기수에서 흔히 관찰된 패턴은 두 가지였다.

1. **유행 기반 결정**: "요즘 Next.js를 많이 쓰니까 SSR" — 자기 서비스의 요구사항과 무관
2. **회피 결정**: "어렵게 하지 말고 CSR" — 검토 자체를 안 함

기술 결정이 **논증의 결과**가 아니라 **분위기의 결과**로 이뤄지는 것이 문제였다.

## 설계

### 3단계 구조

1. **선언** — 팀 내 렌더링 전략과 그 이유를 디스커션에 게시
2. **팀×팀 피드백** — 다른 팀의 선택과 근거에 피드백
3. **개정** — 의견을 반영해 최종 전략 수립

### 답변 템플릿

```
# ___ 팀은 (CSR or SSR) 을 택할 것입니다.

### 프로젝트의 요구사항과 목표를 고려할 때, 지금 방식이 적절한지...
### 그 방식을 선택한 이유는? (기술적/현실적 이유)
### SSR이 필요하다면, 어떤 페이지에 어떤 이유 때문에 필요한가요?
### 유사 서비스가 어떤 렌더링 전략을 취했는지 분석해보세요.
```

핵심은 **"어떤 페이지에 어떤 이유"** 라는 항목이다. "SSR을 쓴다"가 아니라 "랜딩 페이지의 SEO 때문에 SSR, 대시보드는 CSR"처럼 **페이지 단위 결정**을 강제한다.

### 핵심 설계 원리

- **선언 → 피드백 → 개정의 3단**: 첫 결정을 절대화하지 않고 동료의 검증을 거쳐 단단해지게 한다.
- **유사 서비스 분석 강제**: 추상적 이론이 아닌 실제 사례를 근거로 끌어오게 만든다.

## 결과

7기 12팀의 실제 결정과 근거입니다. 동일한 워크숍 안에 **CSR 일괄·CSR 부분SSR·기술적 제약 기반·도발적 전제** 네 가지 결의 사고가 공존했습니다.

### 1. CSR + 부분 SSR (페이지 단위 분리)

가장 사고가 분화된 결정 방식입니다.

- **아맞다 (keemsebin)**: "메인 페이지에서는 CSR 유지 / 이벤트 전체 조회 페이지 및 상세 조회 페이지에서는 SSR이 더 적합" — 메인은 번들이 작아서 유지, 조회 페이지는 SEO·약한 네트워크 환경 고려.
- **포게더 (ShinjungOh)**: "랜딩 페이지, 작품 소개 페이지" 에 SSR. 이유: "작가가 전시를 사람들에게 쉽게 홍보" 하는 서비스 특성 + OG 태그.
- **모잇지 (eunsoA)**: "ResultPage에서 공유하기 버튼을 통해 지인들에게 url 공유 시" 만 SSR 후보. 그러나 "SSR을 사용하면 이 대기 시간 동안 흰 화면이 뜨기 때문에 사용자 경험 관점에서 부정적" 이라며 AI 응답 3~4초 지연을 SSR 거부 사유로 추가.

### 2. 기술적 제약 기반 결정

- **루티 (ohgus)**: "메인 페이지에서 SSR을 적용할 수 없다. 이유는 지도를 띄우기 위해 kakao api를 호출하고 있는데 ... window 객체를 참조해서 api를 호출해야 하는데 서버에는 window가 없으므로 ssr에서 불가능하다" — 이론이 아닌 의존성이 결정을 강제한 사례.

### 3. 도발적 전제

- **아잉슈타임 (hoyyChoi)**: "5G 시대에 유저들의 네트워크 환경을 믿습니다" 라는 전제로 CSR 선택. 그러면서도 CheckEventPage는 "공유된 링크로 참여자가 진입했을 때 (여러 명의 투표 데이터가 있는 경우) 셀에 투표된 데이터가 빠르게 보여진다" 는 이유로 SSR 후보로 명시. 단일 전제 + 페이지 예외의 사고.

### 4. SEO를 CSR로 풀어낸 사례

- **모아온 (jin123457)**: "구글의 크롤러는 자바스크립트 렌더링을 일정 시간 대기한 뒤 실행 결과를 크롤링할 수 있기 때문에, CSR 방식이라도 충분히 SEO를 확보할 수 있습니다" — 개발자 타깃 서비스라 네이버보다 구글 SEO 우선.
- **피드줍줍 (bunju20)**: "대부분의 페이지가 실시간성과 민감한 개인정보를 보유하고 있다" 며 CSR. "개인 피드백 방 공유 시 og 태그의 커스텀화를 위해" 만 SSR 후보.

### 5. 입장 변화의 흔적

워크숍 본문 안에서 **자기 반박 → 결정 전환**이 드러난 두 사례:

- **모아온 (jin123457)**: "빌드 시 정적으로 메타태그를 생성하거나, 서버리스 환경에서 HTML 메타 정보를 동적으로 주입하는 CSR 기반의 접근도 충분히 가능합니다. 그럼에도 불구하고…" — CSR 옹호 후 부분 SSR 도입으로 결론을 옮김.
- **핏토링 (Beomtae)**: 반대 방향. "현재 멘토 상세 페이지 검색어 노출을 위해 SSR이 적합하다고 생각하지만 하나의 장점을 갖기 위해서 많은 리스크를 가져가는 것 같아 CSR을 사용하기로 결정". 경쟁사 운동닥터(SSR)가 자연 검색 유입이 잘 된다는 분석을 함께 제시했음에도 CSR 선택. **유사 서비스 분석을 자기 결정의 강화가 아니라 의도적 거부**에 사용한 사례.

## 교훈

**잘 작동한 것**

- **페이지 단위 결정 강제**: 일괄 결정이 아닌 페이지별 근거를 요구한 것이 사고의 해상도를 높였습니다. 12팀 중 4팀(아맞다·포게더·모잇지·아잉슈타임)이 명시적으로 페이지를 분리해 결정했습니다.
- **유사 서비스 분석의 양방향성**: 자기 결정을 강화하는 데도, 의도적으로 거부하는 데도 사용되었습니다(핏토링 사례). 단순히 "선배 따라하기"가 아니라 **분석 → 자기 맥락 적용 → 판단**의 사고 단계가 작동.
- **본문 내 자기 반박**: 결정문 안에 "그럼에도 불구하고" 형태의 자기 반박이 등장한 것 자체가 워크숍 형식의 효과를 보여줍니다. 한 번 결정하면 끝이 아니라는 구조가 사고를 멈추지 않게 합니다.
- **기술 제약 기반 결정 인정**: 루티의 "kakao api가 window를 요구해서 SSR 불가" 같은 사례는, "이상적 결정"이 아닌 "현실 결정"을 학습하게 만든 가치 있는 패턴입니다.

**개선이 필요한 것**

- **팀×팀 피드백의 흔적이 디스커션에 거의 남지 않음**: 본문에는 자기 결정 변화가 드러나지만, 다른 팀의 피드백을 누가 어떻게 받았는지가 코멘트로 추적되지 않습니다. 피드백을 본문에 통합하게 하거나 별도 코멘트로 명시 요구해야 합니다.
- **SSR 거부 사유의 공통화**: 여러 팀이 "흰 화면", "대기 시간"을 SSR 거부 사유로 들었는데, 이 직관이 정확한지(스트리밍 SSR·Suspense 같은 대안) 검증하는 단계가 없습니다.
- **사후 검증 부재**: 결정한 전략이 실제 구현 후에도 유효했는지 회고하는 단계가 없습니다. 데모데이 회고에 "렌더링 전략 결정 회고"를 1회 추가하면 결정의 순환이 닫힙니다.
