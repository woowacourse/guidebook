# FE SSR 학습: 토론과 OX퀴즈로 "서버와 클라이언트의 평행세계" 체험하기

<Callout>
**대상**: SSR 같은 추상적 개념을 토론 기반으로 가르치려는 코치

**맥락**: 6기 FE 레벨4 SSR 미션 (2024)

**핵심 질문**: SSR 같은 "보이지 않는 실행 환경"의 차이를, 강의가 아닌 토론과 퀴즈로 발견하게 만들 수 있을까?
</Callout>

## 배경과 문제

SSR은 직관에 반하는 학습 주제다. 같은 JavaScript 코드가 서버와 클라이언트에서 다르게 동작하고, 하이드레이션처럼 눈에 보이지 않는 과정이 결과를 좌우한다. 강의로 듣고 미션 코드를 작성해도, "내가 실제로 무엇을 만들고 있는지" 모르는 상태로 통과하는 크루가 많았다.

## 설계

### 두 단계 활동

1. **토론 — JS의 평행세계, 서버와 클라이언트** ([Discussion #55](https://github.com/woowacourse/retrospective/discussions/55))
   - var 호이스팅 코드의 결괏값을 추론하기 (foo.js, bar.js의 변수 충돌)
   - 프리코스 자동차 경주 vs 레벨1 자동차 경주 저장소의 `package.json` 비교
   - Babel 트랜스파일링 직접 실행 후 원본 코드와 변환 결과 비교

2. **OX퀴즈 해설지 만들기** ([Discussion #56](https://github.com/woowacourse/retrospective/discussions/56))
   - SSR 본 미션 2단계 완성 기준의 4개 명제에 O/X로 답하고 **해설지를 작성**
   - 예: "초기 페이지 로드 시 웹 브라우저가 JS bundle 파일을 요청하지 않는다"
   - "하이드레이션 **과정**에서 첫 화면을 검증하지 않는다"처럼 미묘한 표현 차이를 의도적으로 배치

### 핵심 설계 원리

[비동기 퀴즈 해설지 만들기](/education/logs/async-quiz-explanation) 와 같은 **"해설지" 프레이밍**을 차용했다. "정답을 맞혀라"가 아닌 "왜 그런지 다른 사람에게 설명하라"는 과제다.

토론 활동(#55)이 **개념의 기초**를 다루고, OX퀴즈(#56)가 **본 미션 코드를 기준으로 한 검증**을 다루는 2단 구조다. 추상 → 자기 코드로 점진적으로 좁혀온다.

## 결과

### 1. 토론(#55) — "직접 실행한 팀"과 "추측한 팀"의 깊이 격차

호이스팅 코드 결과 추론에서 다수 크루는 "var 재선언"을 단순 "덮어쓰기"로 설명하고 끝났습니다.

> "foo.js의 변수 값이 bar.js의 변수 값으로 덮어 씌워진다." — chysis (행동대장)

> "위에서부터 아래로 실행되기 때문에 bar.js가 더 나중에 실행되어 덮어쓰기 때문" — Hain-tain (코드잽)

`var`의 함수 스코프 + 전역 객체 프로퍼티화라는 메커니즘까지 설명한 팀은 jinyoung234(투룻)와 모우다 두 팀뿐이었습니다. 모우다는 한 발 더 나아가 비동기 로딩까지 고려했습니다.

> "두 script에 async가 붙어 불러오는 순서가 보장되지 않을 경우 값은 다르게 나올 수 있다." — 모우다

흥미롭게도 jinyoung234는 `var` 함수 스코프 → window 프로퍼티화까지 정확히 설명하고도 최종 답을 `"답: js - 20000, ts - 40000"` 으로 ts/js 라벨을 뒤집어 적었습니다. **"개념 이해"와 "결과 추론"이 분리될 수 있음**을 보여주는 사례입니다.

**Babel 트랜스파일링 직접 실행에서 발견한 디테일** (verbatim):

> "#price와 #distance 같은 private 필드를 WeakMap을 사용하여 구현했습니다. 이는 JavaScript에서 진정한 private 속성을 시뮬레이션하는 방법입니다." — llqqssttyy (크루루)

> "10_000과 같은 숫자 구분자를 사용한 리터럴을 일반 숫자로 변환했습니다." — llqqssttyy

private field가 WeakMap으로 변환되거나 numeric separator(ES2021)가 일반 숫자로 풀리는 것은 직접 트랜스파일해야만 발견 가능한 디테일입니다. 토론 3번 문제에서 6팀이 "시간 부족 / 못함"을 적었고, **실제로 트랜스파일까지 끝낸 4팀(크루루·hwinkr·투룻·모우다)만이 `_typeof`, `_classCallCheck`, `WeakMap`, `_interopRequireDefault` 같은 헬퍼 함수를 구체적으로 인지**했습니다. "직접 실행"과 "추측 설명"의 학습 격차가 데이터로 드러난 셈입니다.

### 2. OX퀴즈(#56) — 가장 의견이 갈린 명제

가장 갈린 것은 **문제 3** ("하이드레이션 과정에서 첫 화면을 검증하지 않고 다음 렌더링을 준비한다") 이었습니다.

- jinhokim98(행동대장)만 유일하게 **O**: "하이드레이션 중 서버와 클라이언트의 상태가 대체로 일치할 경우 추가적인 검증 없이 바로 다음 렌더링을 준비합니다 ... 주로 개발 환경에서만 경고가 표시될 수 있지만" — 검증을 "프로덕션에서는 생략"으로 해석.
- 나머지 전원 **X**: 동일한 hydration error 메시지(`"Hydration failed because the initial UI does not match"`)를 근거로 제시.

**"검증 한다 vs 생략 한다"가 정확히 둘로 갈린 것**입니다. 미묘한 차이를 다룬 해설:

> "첫 화면은 검증하지 않는 것이 아니고 화면을 그릴 때 hydration의 과정에서 서버와 클라이언트의 DOM 트리가 일치하는지 확인한다." — novice0840 (땅콩)

> "hydrateRoot에 의해 하이드레이션 과정에서 서버에서 내려준 html과 리액트 트리를 검증하는 과정을 거쳐서…" — jinyoung234 (투룻)

문제 4("SSR이 CSR보다 빠른 렌더링을 반드시 보장한다")에서도 시각이 갈렸습니다.

> "TMDB 서버 응답을 10초로 가정한다면 SSR보다 CSR에서의 초기 렌더링이 훨씬 빠르다 ... CSR에서는 정적 파일을 불러와서 TMDB 서버 페칭 전까지의 UI를 볼 수 있기 때문" — chlwlstlf (코레아)

같은 명제에 코레아는 **X(반박)**, 방끗·코드잽은 **▵(부분 동의)** 로 갈렸습니다. "SSR이 빠르다"는 직관을 어디까지 의심하느냐의 차이입니다.

## 교훈

**잘 작동한 것**

- **토론 → 자기 코드 검증의 2단 구조**: 호이스팅 추상 토론(#55)이 OX퀴즈의 자기 코드 검증(#56)으로 좁혀지면서 이론과 실전 사이의 간극이 줄어들었습니다.
- **의도적 모호성**: "하이드레이션 과정에서" 같은 표현이 단일 정답을 거부하면서 토론을 유발했습니다. 같은 명제에 O/X/▵가 갈리는 데이터가 그 증거입니다.
- **직접 실행 강제**: Babel을 "직접 클론하고 트랜스파일하라"는 절차가, "한 적 있다"고 말하는 것과 실제로 한 것의 차이를 데이터로 드러냈습니다(WeakMap·헬퍼 함수 인지 여부).
- **본 미션 2단계 기준 명시**: "사전 미션은 고려 X, 본 미션 2단계 완성 시점 기준" 이라는 제약이 토론의 혼선을 줄였습니다.

**개선이 필요한 것**

- **해설지 품질 편차**: 토론 3번 문제에서 6팀이 "시간 부족"으로 직접 실행을 건너뛰었습니다. 트랜스파일링 같은 핵심 활동은 별도 시간을 보장해야 합니다.
- **사고 단계와 결과 추론의 분리**: jinyoung234처럼 메커니즘을 정확히 이해하고도 최종 답을 뒤집는 사례가 있습니다. "결과 추론 → 검증 단계"를 분리해 자기 답을 다시 쓰게 만드는 단계가 필요합니다.
- **다른 기수 반복 사례 부족**: 6기 1회만 운영되어 비동기 퀴즈처럼 3개 기수 누적 데이터가 없습니다.
- **엇갈린 답에 대한 사후 정리 부재**: 같은 명제에 O와 X가 갈렸는데, 누가 맞았는지 코치가 정리한 흔적이 디스커션에 없습니다. 토론 후 정답 정리 단계를 두면 학습 효과가 더 큽니다.
