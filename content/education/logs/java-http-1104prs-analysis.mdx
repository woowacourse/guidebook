# 자바 HTTP 미션 5년치 PR 1,104개로 본 톰캣 재구현 학습

<Callout>
**대상**: 웹 백엔드 레벨4 심화 미션을 설계하고 코칭하는 코치, 교육 모델 설계자

**맥락**: `woowacourse/java-http`는 "톰캣 구현하기" 미션 저장소입니다. 2021년부터 2025년까지 382명의 작성자가 1,104개의 PR을 남겼고, 2025년에는 1단계 HTTP 서버 → 2단계 로그인 → 3단계 리팩터링 → 4단계 동시성 확장 흐름이 균형 있게 드러났습니다.

**핵심 질문**: 이미 존재하는 톰캣을 직접 다시 만들게 하면, 크루는 어떤 원리를 코드와 리뷰 대화 속에서 몸으로 익히는가?
</Callout>

## 왜 이 저장소인가

이 미션의 README는 학습 목표를 네 가지로 둡니다. 웹 서버 구현을 통해 HTTP 이해도를 높이고, HTTP를 이해해 성능 개선 역량을 쌓고, 서블릿을 이해하고, 스레드·스레드풀을 적용해 동시성 처리를 경험하는 것입니다.

그 목표는 PR의 누적 구조에서도 그대로 보입니다. 1단계에서는 소켓과 스트림으로 HTTP 요청을 읽고 응답을 씁니다. 2단계에서는 로그인과 세션을 붙이며 쿠키와 인증 상태를 다룹니다. 3단계에서는 직접 만든 서버가 애플리케이션 코드와 어디서 갈라져야 하는지 리팩터링합니다. 4단계에서는 스레드풀과 공유 상태 문제를 다루며 "돌아가는 서버"를 "여러 요청을 견디는 서버"로 바꿉니다.

## 인상적인 리뷰·학습 장면

### 1. `ready()`를 믿으면 요청이 사라집니다 ([PR #17](https://github.com/woowacourse/java-http/pull/17))

초기 PR에서는 `BufferedReader.ready()` 때문에 새로고침할 때 파일이 랜덤하게 읽히는 현상이 논의됐습니다. 리뷰어는 `ready()`가 "데이터가 아직 도착하지 않은 상태"에서 false를 줄 수 있고, `readLine()`은 기다리는 동작을 포함한다는 점을 짚었습니다.

이 장면은 추상화된 프레임워크를 쓸 때는 보이지 않는 낮은 층의 세계를 보여줍니다. HTTP 서버를 직접 구현하니, 요청을 "받았다"는 말이 소켓 버퍼·스트림·블로킹 읽기라는 구체적 동작으로 쪼개집니다.

### 2. 예외는 서버 내부 문제가 아니라 HTTP 응답 계약입니다 ([PR #805](https://github.com/woowacourse/java-http/pull/805))

리뷰어는 `handleRequest`에서 예외를 처리하고 다시 잡는 의도를 물었습니다. 크루는 비즈니스 예외는 HTTP 에러 응답으로 바꾸고, I/O 예외는 연결 자체가 깨진 상황으로 보고 로깅만 하도록 나눴다고 답했습니다.

여기서 학습은 "예외를 어디서 catch할까"가 아닙니다. 서버가 실패했을 때도 클라이언트에게 어떤 상태 코드와 응답을 보낼지 정하는 **프로토콜 계약**으로 사고가 이동합니다.

### 3. 쿠키 객체는 세션을 알아야 하는가 ([PR #886](https://github.com/woowacourse/java-http/pull/886))

2단계 로그인 구현에서는 `Http11Cookie`가 특정 세션 필드에 의존해도 되는지가 논의됐습니다. 리뷰어는 쿠키 객체가 어떤 값이 들어오든 파싱하고 저장하는 역할에 머물러야 할 수 있다고 짚었습니다. 다만 "이 서비스에서만 사용하는 쿠키 객체"라면 메시지를 던지는 방식도 가능하다고 여지를 남겼습니다.

같은 코드라도 관점이 달라집니다. 톰캣 자체를 만드는가, 우테코 미션 애플리케이션을 빨리 완성하는가에 따라 좋은 설계의 기준이 달라집니다. 재구현 미션은 이 기준 차이를 드러내는 장치로 작동합니다.

### 4. 톰캣이 애플리케이션에 의존하면 안 됩니다 ([PR #988](https://github.com/woowacourse/java-http/pull/988))

3단계 리팩터링에서는 FrontController가 어디에 있어야 하는지가 논의됐습니다. 리뷰어는 "톰캣이 Application에 의존하는 구조"가 되면 애플리케이션 개발자가 톰캣을 수정하면서 개발해야 한다고 지적했습니다.

이 대화는 프레임워크와 애플리케이션의 경계를 직접 체감하게 합니다. Spring MVC를 사용할 때는 당연했던 디스패처 서블릿, 컨트롤러 매핑, 컨테이너 경계가, 직접 만들 때는 설계 결정으로 다시 나타납니다.

### 5. `ConcurrentHashMap`을 쓰면 동시성이 끝나는가 ([PR #711](https://github.com/woowacourse/java-http/pull/711))

4단계에서는 SessionManager를 `ConcurrentHashMap`으로 바꾼 뒤에도 질문이 이어졌습니다. "SessionManagerTest에 있지만 ConcurrentHashMap을 테스트하는 것 아닐까요?"라는 질문은 핵심을 정확히 찌릅니다.

이어 리뷰어는 같은 세션 ID로 동시에 접근하는 경우, 한 Session 객체 안에서 `setAttribute`와 `getAttribute`가 겹치는 경우를 묻습니다. 크루는 세션 클래스 자체도 스레드 안정성을 보장하기 어렵다고 판단하고 동시성 컬렉션으로 바꾸겠다고 답합니다. 동시성 학습이 자료구조 선택에서 끝나지 않고, 공유 상태의 경계와 테스트 목적을 다시 묻는 단계로 이동한 것입니다.

### 6. 스레드풀 설정은 숫자가 아니라 부하 정책입니다 ([PR #1093](https://github.com/woowacourse/java-http/pull/1093))

2025년 4단계에서는 Tomcat 문서를 참고해 `maxThreads`, `maxQueueSize`, `minSpareThreads`를 구현하려는 시도가 보입니다. 크루는 `maxThreads`가 있는데 왜 `maxQueueSize`도 따로 있는지 질문합니다.

이 질문은 미션의 끝이 구현 완료가 아니라 운영 감각으로 넘어가는 지점입니다. 스레드 수, 큐 크기, keep-alive 시간은 단순 상수가 아니라 지연을 감수할지, 요청을 거절할지, 시스템을 보호할지를 정하는 정책입니다.

## 올해 길러진 핵심 교육 경험

1. **HTTP를 문서가 아니라 실패하는 코드로 배웠습니다.** `Content-Length`, `Content-Type`, CRLF, 스트림 읽기, 상태 코드 같은 개념이 암기 항목이 아니라 브라우저가 멈추거나 응답이 깨지는 원인으로 나타났습니다.

2. **프레임워크 경계를 직접 그었습니다.** `Request`, `Response`, `Controller`, `Servlet`, `Connector`, `SessionManager`를 직접 만들면서, 무엇이 톰캣의 책임이고 무엇이 애플리케이션의 책임인지 토론했습니다.

3. **동시성을 "자료구조 교체"에서 "공유 상태 정책"으로 확장했습니다.** `ConcurrentHashMap`을 쓰는 이유, Session 객체 내부의 안전성, 스레드풀 큐와 거절 정책을 함께 보며 서버 운영의 사고로 이동했습니다.

## 이 로그가 "바퀴의 재발명"과 연결되는 지점

[바퀴의 재발명 사전 에세이](/education/logs/reinventing-the-wheel)에서는 크루가 재구현의 가치를 어떻게 말로 이해하는지 봤습니다. 이 로그는 그 다음 층입니다. 크루가 톰캣을 다시 만들 때, 그 말이 어떤 코드와 리뷰 대화로 검증되는지를 보여줍니다.

재구현의 교육적 가치는 "이미 있는 것을 다시 만들었다"에 있지 않습니다. 이미 있는 것이 숨겨 주던 경계를 학습자가 다시 그어 보는 데 있습니다. java-http 미션에서 그 경계는 요청과 응답, 세션과 쿠키, 컨테이너와 애플리케이션, 스레드와 공유 상태로 나타났습니다.
