# 유연하게 재사용 가능한 레이아웃 컴포넌트 워크숍

<Callout>
**대상**: 컴포넌트 설계 능력을 "사용자 입장"에서 훈련시키려는 코치

**맥락**: FE 레벨4 (2023)

**핵심 질문**: "재사용 가능한 컴포넌트"라는 추상적 목표를, 구체적 검증 가이드라인으로 만들 수 있을까?
</Callout>

## 배경과 문제

크루들은 컴포넌트를 만들 때 자기 사용 사례만 고려한다. "재사용 가능하게 만들어보세요"라고 지시하면 추상적인 prop 몇 개를 추가하는 것으로 끝낸다. 진짜 재사용성은 **다른 사람의 상황**을 상상하는 데서 나오는데, 그 시야를 갖기 어렵다.

## 설계

### 구체적 검증 가이드라인 제시

추상적 "재사용성" 대신 **체크리스트 형태의 구체적 질문**을 제공했다.

**1. 여러 환경에서 잘 보이는가?**
- 반응형: 다양한 화면 크기에 적응하는가
- 크로스 브라우징: 크롬·사파리·엣지에서 동작하는가

**2. 문서가 가독성 있게 쓰여있는가?**
- README나 사용법으로 저자 의도가 이해되는가
- 사용자 입장에서 쉽게 사용할 수 있는가

**3. '유연'하게 재사용 하기 좋은가?**
- 사용자 컬러에 맞게 Tab 색상을 변경할 수 있는가
- 라벨 텍스트가 매우 긴 경우는?
- 라벨에 아이콘이 있는/없는/같이 들어가는 경우는?
- 가로 외에 세로형은?
- 탭의 수가 많은 경우는?

### 핵심 설계 원리

- **"사용자 입장"의 구체화**: 추상적 사용자가 아닌 "긴 라벨", "아이콘 있는 라벨", "세로형" 같은 **구체적 시나리오**로 사용자를 의인화
- **리뷰 가이드라인 = 설계 가이드라인**: 다른 팀을 리뷰하기 위한 가이드가 동시에 자기 컴포넌트 설계의 체크리스트가 됨

## 결과

### 1. 크루별 만든 컴포넌트

- **노아**: Tab Component
- **참새**: Masonry Layout
- **부엉이**: Tab Layout
- **패트릭**: Drawer
- **해온팀**: TabLayout
- **가브리엘**: SplitPane
- **제레미**: Parallax-scrolling
- **솔로스타**: Tab Component

Tab/TabLayout이 4명이나 겹쳤다는 점이 흥미롭습니다. 같은 컴포넌트 유형 안에서도 API 설계가 어떻게 갈리는지 비교할 수 있는 자연스러운 환경이 만들어진 셈입니다.

### 2. 가이드라인 항목별 발견 (해온팀 TabLayout 리뷰)

리뷰어들이 가이드라인 항목별로 발견한 내용입니다.

**커스터마이징 자유도**

> "children을 배열을 이용해서 여러 tab들을 만들 수 있게 명확하게 알려줘서 좋다. active, inactive 스타일을 커스텀할 수 있어 좋다." — 황펭

> "커스텀 자유도가 높아서 좋은 것 같다." — 아커

**스타일 계층 구조**

> "tabListStyles 안에 activeStyle과 inactiveStyle이 있는데 문서에 계층을 분리해주면 좀더 좋을 것 같습니다." — 타미

**반응형(모바일): 가이드라인이 직접 잡아낸 케이스**

> "현재 모바일 환경에서 탭이 잘리게 보이는데 반응형을 좀 더 고려하면 좋을 것 같습니다." — 아커

**접근성: 가이드라인에 없던 새 차원의 발견**

> "접근성을 고려해서 aria 속성들을 고려해보는 것이 어떤지 제안합니다." — 파인

리뷰 가이드라인에는 접근성 항목이 없었지만, 리뷰어가 자발적으로 ARIA를 제안한 것은 가이드라인이 **사고의 출발점이 되되 사고를 가두지는 않았다**는 신호입니다.

### 3. SplitPane(가브리엘): props 설계가 사용성을 결정한 사례

> "퍼센트를 string 대신 숫자로 받아서 내부적으로 퍼센트 처리하면 좋을 것 같아요."

> "가로 기능도 만들어주시면 좋을 것 같습니다."

**props 입력 타입 설계**가 사용성에 직접적인 영향을 주는 점, **세로형만 구현된 컴포넌트의 방향 확장 누락**이 가이드라인의 "가로 외에 세로형으로도 보여야 하는 경우는?" 항목에 정확히 들어맞습니다.

반면 같은 컴포넌트의 합성 패턴은 호평을 받았습니다.

> "사용성이 매우 좋은것 같아요! 레이아웃 하나 놓고 자식만 넣으면 자동으로 나뉘는게 매우 좋습니다!"

자식만 넘기면 동작하는 **선언적 합성 패턴**의 장점이 자연스럽게 인지됐습니다.

### 4. 합성 컴포넌트의 의미적 연결

해온팀 TabLayout 리뷰에서 루루:

> "탭과 container(탭과 내용)이 좀 더 명확하게 연결되어 있는 것이 보이면 좋겠습니다."

이것은 **Compound Component 패턴 미적용**에 대한 직관적 지적입니다. 가이드라인에 없던 항목이지만, 리뷰어가 사용자 입장에서 자연스럽게 발견한 결입니다.

## 교훈

**잘 작동한 것**

- **체크리스트의 구체성**: "유연하게 만들어라" 대신 "라벨이 긴 경우는? / 세로형은? / 탭의 수가 많은 경우는?" 같은 구체 질문이 사고의 해상도를 높였습니다. 가브리엘 SplitPane의 "가로 기능도 필요" 피드백이 정확히 이 구조에서 나왔습니다.
- **리뷰와 설계의 일치**: 리뷰 가이드라인이 곧 설계 시 점검해야 할 항목이 되어, 리뷰를 위해 만든 도구가 설계 도구가 되었습니다.
- **가이드라인 밖 발견의 허용**: ARIA(파인), Compound Component 패턴(루루) 같은 가이드라인에 없던 항목을 리뷰어가 자발적으로 제안했습니다. 가이드라인이 **사고의 바닥**을 만들되 **천장**이 되지는 않았다는 증거입니다.

**개선이 필요한 것**

- **본문 리뷰 누락**: 8명 중 4명(노아·참새·부엉이·패트릭·제레미·솔로스타)은 PR 링크만 있고 본문 리뷰가 디스커션에 남지 않았습니다. PR 링크 + 디스커션 리뷰를 모두 강제하는 형식이 필요합니다.
- **시나리오 제한**: 제시된 시나리오가 Tab 컴포넌트 중심이라, 다른 컴포넌트(Modal, Form 등)에는 그대로 적용하기 어려웠습니다. 컴포넌트 유형별 체크리스트가 필요합니다.
- **사용자 페르소나 부재**: "긴 라벨"이라는 시나리오는 있지만, 이 사용자가 "왜" 긴 라벨을 쓰는지에 대한 맥락이 없습니다. 페르소나를 추가하면 더 깊은 설계가 가능합니다.

## 다음 실험 제안

1. **컴포넌트 유형별 체크리스트 분리**: Tab 중심 가이드라인을 Modal, Form, Toast 등 유형별로 확장하여 레벨4 전체에 재사용 가능한 리뷰 인프라로 발전시킨다.
2. **디스커션 리뷰 의무화**: PR 링크 외에 디스커션 본문 리뷰를 명시 요구하여 8명 중 4명의 누락을 방지한다.
3. **접근성 항목 통합**: 파인이 자발적으로 ARIA를 제안한 것을 체크리스트에 공식 항목으로 추가하고, [FE 접근성 리포트](/education/logs/fe-accessibility-report)와 연계한다.
