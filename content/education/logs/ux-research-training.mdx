# UX 리서치 3단계 훈련: 글쓰기에서 UT 실전까지

<Callout>
**대상**: 팀 프로젝트 단계에서 UX 리서치 역량을 단계적으로 훈련시키려는 코치

**맥락**: 레벨 3 · 6기 (2024년 하반기), 런칭 페스티벌을 앞둔 팀 프로젝트 시기. 18개 팀 참여.

**핵심 질문**: 글쓰기 → 인터뷰 설계 → 사용성 테스트라는 3단계 점진적 스캐폴딩이, 개발자의 UX 리서치 역량을 실질적으로 끌어올릴 수 있을까?
</Callout>

## 배경과 문제

레벨 3 팀 프로젝트에서 크루들은 "기능이 동작하는가"에 집중하지만, "사용자에게 어떻게 보이는가"는 시야 밖에 놓이기 쉽습니다. 런칭 페스티벌을 앞두고 서비스를 소개하고, 사용자를 이해하고, 실제로 테스트하는 역량이 필요했지만, 대부분의 크루에게 UX 리서치 경험은 없었습니다.

단순히 이론 강의를 제공하는 방식은 효과가 제한적입니다. 개발자가 UX를 체득하려면 직접 써보고, 물어보고, 관찰하는 경험이 필요합니다. 문제는 이 세 가지를 한꺼번에 던지면 진입 장벽이 너무 높다는 점이었습니다.

이를 해결하기 위해, 인지적 부담이 낮은 활동에서 시작하여 점차 복잡한 활동으로 올라가는 3단계 점진적 스캐폴딩을 설계했습니다.

## 설계

### 핵심 설계 원칙

**표현 → 탐색 → 검증**이라는 순서로, 각 단계가 다음 단계의 기반이 되도록 구성했습니다. 매 세션마다 구체적인 결과물이 나오도록 하여 "활동했지만 남는 게 없다"는 문제를 방지했습니다.

### 3단계 시리즈 구조

| 단계 | 주제 | 핵심 활동 | 결과물 | 인지 수준 |
|------|------|-----------|--------|-----------|
| 1단계 | UX Writing — 서비스 소개글 쓰기 | 페어 글쓰기 + 크로스 팀 피드백 | 서비스 README 소개글 v0.1 | 표현 (가장 낮음) |
| 2단계 | JTBD 인터뷰 질문 설계 | Context-Problem-Solution 프레임으로 질문 설계 | 인터뷰 목표·대상·질문 목록 | 탐색 (중간) |
| 3단계 | UT 인터뷰 | 라이브 시연 관찰 + 실제 사용성 테스트 수행 | 관찰 기록 스프레드시트 | 검증 (가장 높음) |

### 팀 구성 원칙

모든 단계에서 **FE+BE 크로스 페어**를 원칙으로 했습니다. 클라이언트 개발자와 서버 개발자가 같은 서비스를 다른 시선으로 보고 있다는 사실 자체가 UX 관점의 출발점이기 때문입니다.

---

## 1단계: UX Writing — 페어 글쓰기

### 활동 설계

서비스 소개글을 "페어 글쓰기"로 작성합니다. 한 사람이 한 문장을 쓰면 페어가 이어받아 한 문장을 추가하거나 수정합니다. 핵심은 **독자가 눈앞에 있다고 상상**하며 쓰는 것입니다.

이 방식은 짝 프로그래밍의 메타포를 글쓰기에 적용한 것입니다. 코드에 버전 관리가 있듯이, 서비스 소개글도 v0.1에서 시작하여 피드백을 거쳐 버전이 올라간다는 관점을 공유했습니다.

### 크로스 팀 피드백

매칭된 팀의 서비스 소개글 4개를 읽고, 1인당 2개씩 투표합니다. 피드백은 두 가지 축으로 진행됩니다.

- **긍정적 피드백**: 다른 부분이 바뀌더라도 이 부분은 그대로 남았으면 하는 것
- **개선 제안**: 단순히 "안 좋다"로 끝내지 않고, "어떻게 하면 더 좋겠다"로 제안

<Toggle title="캠퍼스별 피드백 매칭 (순환 구조)">

**선릉**: 투룻 → 스타카토 → 코레아 → 오디 → 땅콩 → 총대마켓 → 모우다 → 펭쿡 → momo → 투룻

**잠실**: 코드잽 → 행동대장 → 데벨업 → 리뷰미 → 크루루 → 티미룸 → 방끗 → 반갑개 → 코딩해듀오 → 코드잽

</Toggle>

### 타임라인

| 시간 | 활동 |
|------|------|
| ~12:00 | 페어로 서비스 소개글 작성 |
| ~12:30 | 매칭된 팀의 소개글 읽고 투표 + 피드백 코멘트 |
| ~18:00 | README에 서비스 소개글 v0.1 업데이트 |

## 2단계: JTBD 인터뷰 질문 설계

### 활동 설계

런칭 페스티벌은 첫 번째 정식 출시이지, 서비스의 완성이 아닙니다. 이 세션에서는 레벨 4에서 실제 사용자 반응을 기반으로 개선하는 과정을 준비하기 위해, **인터뷰 전략을 짜보는 경험**을 합니다.

### 팀 구성

클라이언트 2명 + 백엔드 2명이 한 팀. 한 서비스 팀에서 2개의 인터뷰 팀이 나옵니다.

### Context-Problem-Solution 질문 프레임

| 프레임 | 목적 | 질문 예시 |
|--------|------|-----------|
| 상황 질문 (Context) | 사용자가 어떤 상황에서, 어떤 방식으로 서비스를 사용하는지 파악 | "최근에 정산을 처리한 경험에 대해 이야기해주세요" |
| 문제 탐색 질문 (Problem) | 사용자가 겪는 문제점과 불편함, 감정을 파악 | "정산 과정에서 가장 번거로운 부분은 무엇인가요?" |
| 사용자 목표 질문 (Solution) | 사용자가 얻고 싶은 가치와 이상적인 기능 파악 | "이상적인 정산 기능은 어떤 모습이라고 생각하시나요?" |

<Toggle title="팀별 인터뷰 설계 예시">

**투룻**: 여행 계획-기록 서비스의 핵심 사용자를 "여행 빈도", "기록 습관", "공유 성향"으로 세분화하여 인터뷰 대상 유형을 설정

**데벨업**: 개발 학습 플랫폼의 사용자를 "학습 단계(입문/중급/고급)"와 "자기주도 학습 경험 수준"으로 나누어 질문 설계

**오디**: 약속 서비스에서 "약속 생성 빈도"와 "정산 경험"을 기준으로 인터뷰 대상을 선정하고, 약속 생성-참여-정산 흐름별 질문 목록 작성

</Toggle>

## 3단계: UT 인터뷰 — 실전 사용성 테스트

### 활동 설계

코치가 먼저 찜꽁 서비스의 핵심 기능 UT 인터뷰를 **라이브로 시연**하여, 어떤 질문을 하고 어떻게 관찰해야 하는지를 보여준 후 팀별로 실제 UT를 수행합니다.

### 관찰자의 역할: 나노 단위 라벨링

관찰자는 최대한 관찰 자체에 집중하여 **나노 단위로** 사용자의 말, 행동, 감정, 표정에 의미를 부여하고 라벨링합니다.

> 예: "사용자가 예약하기 버튼을 누르기 전에 클릭을 고민하는 게 느껴졌다" → **클릭 고민의 순간**

이 라벨링 훈련은 단순한 "좋다/나쁘다" 평가를 넘어, 사용자의 미세한 행동에 이름을 붙이는 연습입니다.

### 팀별 UT 목적

각 팀이 설정한 UT 목적은 서비스 특성에 따라 달랐습니다.

| 팀 | UT 목적 |
|----|---------|
| 오디 | 사용자가 성공적으로 약속을 생성하고 참여할 수 있는지 평가 |
| 코딩해듀오 | 사용자가 페어룸을 생성하고 유틸 기능들을 제대로 활용하는지 확인 |
| 총대마켓 | 공동구매를 성공적으로 운영/참여할 수 있는지 평가 (기대 기준: 4점 이상) |
| 모우다 | 모임 생성·참여·의사소통이 원활한지 평가 |
| 투룻 | 여행기-여행계획 간 전환, 작성, 조회, 공유가 부드럽게 진행되는지 확인 |
| 방끗 | 원하는 것을 효율적으로 체크리스트로 작성할 수 있는지 확인 |

### 진행 방식

1. 구글 스프레드시트 템플릿을 팀별로 복제
2. UT 인터뷰 목적, 진행자, 관찰자 역할 배정
3. 사전 준비 진행
4. 실제 인터뷰 시행
5. 함께 회고
6. 디스커션에 스프레드시트 링크 업데이트

## 결과

### 3단계 스캐폴딩의 효과

각 단계가 다음 단계의 기반이 되는 구조가 실제로 작동했습니다.

- **1단계 → 2단계 연결**: UX Writing에서 "우리 서비스가 뭔지"를 글로 정리하는 과정이, JTBD에서 "사용자 관점의 질문을 만드는" 데 직접적인 도움이 되었습니다. 서비스의 핵심 가치를 글로 표현해본 팀이 인터뷰 목표 설정에서도 더 구체적인 질문을 만들어냈습니다.
- **2단계 → 3단계 연결**: Context-Problem-Solution 프레임으로 질문을 설계한 경험이, UT에서 "무엇에 주목해야 하는지"에 대한 감각을 제공했습니다. 질문 설계 없이 바로 UT로 들어갔다면 "뭘 관찰해야 할지 모르겠다"는 반응이 더 많았을 것입니다.

### 참여 규모

6기 레벨 3 전체 18개 팀이 3회 시리즈에 모두 참여했습니다. 선릉 9팀(투룻, 스타카토, 코레아, 오디, 땅콩, 총대마켓, 모우다, 펭쿡, momo), 잠실 9팀(코드잽, 행동대장, 데벨업, 리뷰미, 크루루, 티미룸, 방끗, 반갑개, 코딩해듀오)이 참여했습니다.

### FE+BE 크로스 페어의 효과

페어 글쓰기에서 클라이언트 개발자와 서버 개발자가 같은 서비스를 다른 관점으로 설명하려는 시도가 자연스럽게 관찰되었습니다. 서버 개발자는 기능의 구조를, 클라이언트 개발자는 사용자의 흐름을 중심으로 글을 쓰는 경향이 있었고, 이 차이가 "사용자에게 무엇이 중요한가"에 대한 대화를 끌어냈습니다.

## 교훈

**잘 작동한 것**

- **페어 글쓰기 방식**: 한 문장씩 번갈아 쓰는 구조가 "혼자 글을 잘 써야 한다"는 부담을 줄이고, 서로 다른 관점을 자연스럽게 드러냈습니다. 짝 프로그래밍에 익숙한 크루들에게 친숙한 메타포가 진입 장벽을 낮췄습니다.

- **버전 관리 메타포**: "소개글도 v0.1이다, 코드처럼 버전이 올라간다"는 프레이밍이 완벽한 글을 써야 한다는 압박을 줄이는 데 효과적이었습니다.

- **Context-Problem-Solution 프레임**: 질문 설계에 구조를 제공하여 "뭘 물어봐야 할지 모르겠다"는 막막함을 해소했습니다. 세 가지 축이 명확해서 크루들이 빠르게 질문을 만들어낼 수 있었습니다.

- **라이브 시연 후 실습**: 코치가 먼저 UT를 시연한 것이, "인터뷰를 어떻게 진행하는지" 구체적으로 보여주는 가장 효과적인 방법이었습니다.

- **나노 단위 관찰 라벨링**: 관찰에서 의미를 부여하고 이름을 붙이는 연습이, 단순한 사용성 평가를 넘어 사용자 심리를 읽는 훈련이 되었습니다.

**개선이 필요한 것**

- **크로스 팀 피드백의 깊이 부족**: 1단계 피드백에서 "좋았다/아쉬웠다" 수준에 머무는 경우가 있었습니다. 피드백 가이드를 더 구체적인 체크리스트로 제공하거나, 피드백 예시를 사전에 공유할 필요가 있습니다.

- **JTBD 인터뷰의 실제 실행 연결 부재**: 질문 설계까지는 진행했으나, 실제 외부 사용자를 대상으로 인터뷰를 수행하는 단계로 이어지는 연결 고리가 약했습니다. 레벨 4 초반에 후속 활동으로 연계하는 설계가 필요합니다.

- **UT 관찰 기록의 활용 미흡**: 스프레드시트에 기록은 했으나, 기록을 분석하여 실제 서비스 개선 액션으로 전환하는 과정이 체계적이지 않았습니다. UT 이후에 **개선 액션 도출 세션**을 추가하여 관찰 → 분석 → 코드 변경으로 이어지는 흐름을 완성할 필요가 있습니다.
