# 렌더링 전략 결정 워크숍 템플릿

<Callout>
**목적**: 팀이 "CSR이냐 SSR이냐"를 유행 기반이 아닌 자기 서비스의 요구사항 기반 논증으로 결정하도록 훈련합니다.
</Callout>

> 이 도구는 [렌더링 전략 워크숍](/education/logs/fe-rendering-strategy-workshop) 실험에서 검증되었습니다.
> 7기 FE 레벨4 12팀이 이 구조로 기술 결정을 수행했으며, 12팀 중 4팀이 페이지 단위 분리 결정을 도출했습니다.

## 사용 조건

- **레벨**: 레벨4 (팀 프로젝트 진행 중, 기술 스택 결정 단계)
- **트랙**: FE 또는 풀스택 미션이 있는 트랙
- **시점**: 팀 프로젝트 킥오프 후 1~2주차 (렌더링 전략 결정 시점)
- **형식**: GitHub Discussions 활용

## 3단계 운영 구조

### 1단계: 선언 (Day 1~3)

각 팀이 아래 템플릿으로 Discussions에 포스트를 작성합니다.

```
# ___ 팀은 (CSR / SSR / 하이브리드) 을 택할 것입니다.

### 우리 서비스의 요구사항과 목표
(서비스 한 줄 소개 + 핵심 사용자 시나리오)

### 현재 방식이 적절한지 검토
(요구사항 관점에서 현재 선택의 근거)

### 선택한 이유 (기술적/현실적)
- 기술적 이유:
- 현실적 제약 (API, 라이브러리, 팀 역량):

### SSR이 필요하다면, 어떤 페이지에 어떤 이유 때문에 필요한가요?
(페이지 단위로 명시 — "전체 SSR"은 허용하지 않음)

### 유사 서비스의 렌더링 전략 분석
(경쟁 서비스 1~2개의 렌더링 방식과 이유 조사)
```

### 2단계: 팀×팀 피드백 (Day 4~6)

각 팀이 **다른 팀 2개**의 포스트에 코멘트를 남깁니다.

피드백 가이드:
- "왜 그 페이지에 SSR이 필요한가?" 추가 질문
- "우리 팀과 같은 결정인데 이유가 다른 부분" 지적
- 유사 서비스 분석의 보완 제안

### 3단계: 개정 (Day 7)

팀×팀 피드백을 반영해 최종 전략을 본문 하단에 추가합니다.

```
## 최종 결정 (피드백 반영 후)

변경 사항: (피드백으로 바뀐 결정과 이유)
유지 사항: (피드백을 받았으나 유지한 결정과 이유)
```

## 코치 운영 가이드

**가장 흔한 패턴과 대응:**

| 패턴 | 현상 | 대응 |
|------|------|------|
| 유행 기반 결정 | "요즘 Next.js 많이 써서 SSR" | "어떤 페이지에 어떤 이유로?" 추가 질문 |
| 기술 제약 미발견 | "SSR 하겠습니다" | "window, kakao, localStorage를 쓰는 페이지는?" |
| 전체 SSR/전체 CSR | 페이지 구분 없음 | 1단계 템플릿의 페이지 단위 명시 제약이 방지 |
| 유사 서비스 맹목 모방 | "경쟁사가 SSR이라서" | "우리 서비스의 트래픽·SEO 요구사항이 동일한가?" |

**성공 지표:**
- 팀 중 절반 이상이 페이지별로 다른 전략을 명시합니다
- "흰 화면 문제"를 SSR 거부 사유로 드는 팀이 스트리밍 SSR/Suspense를 추가 검토합니다
- 본문에 "그럼에도 불구하고" 형태의 자기 반박이 등장합니다

## 주의사항

- **피드백 코멘트를 의무화해도 본문 통합은 별도 강제**: 2단계 피드백이 3단계 개정에 반영됐는지 추적하려면 "최종 결정" 섹션을 명시 요구해야 합니다.
- **"SSR이 무조건 빠르다" 직관은 사전에 검토**: 여러 팀이 AI 응답 지연, 외부 API 호출이 있는 페이지에서 SSR을 거부하는 사례가 반복됩니다. 스트리밍 SSR, Suspense 대안을 사전 안내하면 논의의 질이 올라갑니다.
