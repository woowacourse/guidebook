# 자라는 콘텐츠 일괄 갱신 — 뉴스레터 최신화 + `/페이지업데이트` 커맨드 (genseq3 설계)

> **For agentic workers:** 이 문서는 generative sequence다. 단계 순서 자체가 설계의 핵심이므로 건너뛰지 말 것. 실행 시 superpowers:executing-plans 또는 saligo(항상 동작 상태 유지) 규율을 권장한다.

**Goal:** (1) 뉴스레터 아카이브 페이지를 19호 → 22호로 최신화하고, (2) 그 갱신 과정을 재연 가능한 커맨드 `/페이지업데이트`로 승격해, 뉴스레터처럼 주기적으로 새 항목이 추가되는 아카이브 콘텐츠 전체를 한 번에 점검·갱신할 수 있게 한다.

## genseq3 라우팅

- **최적 형상: Pilot-and-Scale** — 완성된 전체(커맨드)는 여러 단위(뉴스레터·테코톡·브이로그·테코블·데모데이·교육설명회·유튜브·인터뷰챌린지)에 작동해야 한다. 하나의 구체 사례(뉴스레터 19→22)를 끝까지 손으로 돌려 관찰 가능하게 만들고, 그 실측 기록이 곧 레시피가 된다.
- **차선 형상: Vertical-Slice-Growth** — 커맨드라는 산출물 자체는 최종 매체(`.claude/commands/*.md`) 안에서 제자리 성장한다: 단일 소스 슬라이스 → 소스 레지스트리 → 두 번째 소스 → 배치 모드, 한 번에 한 능력씩.
- **융합:** 1~5단계가 파일럿(뉴스레터를 전 표면에 걸쳐 갱신하며 레시피를 실측), 6~8단계가 커맨드의 수직 슬라이스 성장.

## 시퀀스

각 단계는 변환 하나 + 확인 가능한 결과 하나. 다음 단계는 이전 단계의 산출물에 기댄다.

### 1. 신선도 diff를 손으로 한 번 — 가장 작은 살아있는 증명

- [ ] 메일리 목록 페이지에서 호수·발행일·제목·URL을 추출하고, `newsletter-archive.mdx` 표와 대조해 밀린 호수 목록을 만든다.
- **확인:** "아카이브 19 / 라이브 22 / 밀림 3(20·21·22호)" 형태의 gap 목록(제목·날짜·URL 포함). 이 diff가 커맨드 전체의 원시 연산이다 — 갱신 기계보다 먼저 이것부터 존재해야 한다.

### 2. 새 호수 원문 확보 — raw부터 보존

- [ ] 20·21·22호 본문을 스크레이프해 `llm-wiki/raw/`에 1차자료로 저장한다(frontmatter에 captured 날짜·원본 URL).
- **확인:** raw 파일 3개에 제목·날짜·본문이 온전히 담김. 발행본을 건드리기 **전에** 원본 체크포인트를 남긴다 — 이후 서사 판단(4단계)의 근거가 된다.

### 3. 기계적 표면 갱신 — 표와 계수

- [ ] 표에 3행 추가(호수·날짜·읽을 포인트·링크), Callout의 발행 수 19→22, 분석 범위 종료일 갱신.
- **확인:** dev 렌더에서 표 22행, `grep -c '바로가기' newsletter-archive.mdx` = 22. 판단이 필요 없는 부분만 먼저 — 여기까지는 어떤 실행자가 돌려도 같은 결과가 나와야 한다.

### 4. 서사 재점검 — 편집 표면 갱신 + 경계 실측

- [ ] 20~22호 내용을 읽고 기존 "네 가지 흐름"에 흡수되는지, 새 흐름(예: 기수 전환·8기 준비)을 여는지 판정해 계수 의존 문구를 모두 고친다. `/말투점검` 통과.
- **확인:** `grep '19개' newsletter-archive.mdx` 결과 0, `npm run lint:tone` 통과.
- **부산물(커맨드 설계의 핵심 입력):** 이 페이지에서 *기계적으로 갱신 가능한 위치*(표·계수)와 *편집 판단이 필요한 위치*(흐름 서사·추천 표·한 줄 요약)의 경계 목록.

### 5. 주변 표면 마무리 — 이중 기록과 사이트 규약

- [ ] `llm-wiki/raw/derived/newsletter-archive.md` 재생성(captured 갱신), `content/updates.ts` 항목 추가, `npm run build`로 llms.txt 재생성 확인. 발행 repo와 llm-wiki에 각각 커밋.
- **확인:** build 통과, `public/llms-full.txt`에 22호 흔적, 커밋 2건. — 여기서 파일럿 완료: 커맨드가 건드려야 할 **모든 표면이 실행으로 열거**되었다.

### 6. 레시피를 커맨드로 승격 — 단일 소스 슬라이스

- [ ] `.claude/commands/페이지업데이트.md` 작성. 계약: 소스 하나를 인자로 받아 1~5단계를 재연한다(신선도 diff → 밀림 0이면 no-op 보고 → 밀림 있으면 raw 확보 → 기계 표면 → 편집 표면은 4단계의 경계 목록에 따라 *제안 후 반영* → 이중 기록·규약 마무리).
- **확인(멱등성):** 방금 갱신한 뉴스레터에 `/페이지업데이트 뉴스레터`를 실행하면 "밀림 0 — 변경 없음"으로 끝난다. 커맨드의 첫 생존 증명은 no-op이다.

### 7. 소스 레지스트리 — 자라는 콘텐츠의 목록화

- [ ] 레지스트리(`.claude/page-update-sources.md`) 작성. 소스별 한 항목: 라이브 소스 URL·항목 열거 방법, 갱신 대상 파일들, 메커니즘 유형(인라인 테이블 vs data-JSON+스크립트, 스크립트 경로·`.temp/` 의존 여부), 계수 의존 문구 위치. 뉴스레터는 파일럿 실측으로 채우고, 나머지 7개(테코톡·브이로그·테코블·데모데이·교육설명회·유튜브·인터뷰챌린지)는 조사 행으로 등록.
- **확인:** `/페이지업데이트`를 인자 없이 실행하면 등록된 전 소스의 신선도 리포트만 출력한다("소스 / 아카이브 N / 라이브 M / 밀림 K"). 갱신 없이 전체를 **관찰 가능**하게 만드는 것이 배치 모드보다 먼저다.

### 8. 두 번째 소스 확장 → 배치 모드

- [ ] 구조가 다른 소스 1개(data-JSON 계열, 테코톡 또는 브이로그 권장)를 커맨드로 끝까지 갱신한다. 메커니즘 차이는 커맨드 본문이 아니라 레지스트리의 소스별 레시피에 흡수한다. 성공하면 `/페이지업데이트 전체` 배치 모드를 연다: 신선도 리포트 → 밀린 소스만 순회 갱신 → 소스별 결과 요약.
- **확인:** 서로 다른 메커니즘의 두 소스가 같은 커맨드로 갱신되고, 배치 실행이 소스별 리포트를 남긴다. — 요청된 전체가 여기서 완성된다.

## 범위 밖 (의도적으로 시퀀스에 넣지 않음)

- 크론/훅 기반 자동 실행(신선도 알림) — 커맨드가 안정된 뒤의 후보.
- 나머지 5개 소스의 실제 갱신 — 배치 모드가 열리면 커맨드의 일상 사용일 뿐, 이 설계의 검증 대상이 아니다.
