# 선배 코드로 눈 키우기: AS-IS 판단 → TO-BE 비교 활동

> **대상**: 코드 리뷰 기반 수업을 설계하려는 코치
>
> **맥락**: 레벨 1 · 로또 미션 1단계 진행 중
>
> **핵심 질문**: 크루가 "내가 뭘 못 보는지"를 스스로 체감하게 하려면?

## 배경과 문제

로또 미션 1단계를 진행 중인 크루들은 "동작은 하는데, 이게 맞는지 모르겠다"는 상태에 놓여 있었습니다. 수업 전 참여 시트에서 "**지금 가장 확신이 없는 것**"을 물었을 때, 26명의 응답이 세 가지 테마로 수렴했습니다.

| 테마 | 비율 | 대표적인 고민 |
|------|------|--------------|
| 테스트 범위 판단 | ~42% | "어떤 것을 테스트하고, 어떤 것을 하지 말아야 할지" |
| TDD 사이클 유지의 한계 | ~35% | "후반부에 사이클만 따라가기엔 한계가 오는 시점이 있다" |
| 책임 분리 기준 | ~23% | "하나의 클래스가 끝없이 커질 수 있는데, 어느 수준이 적당한지" |

이 고민들은 코치가 정답을 알려준다고 해결되지 않습니다. 크루 각자가 "**내가 뭘 볼 수 있고, 뭘 아직 못 보는지**"를 체감해야 하는 문제였습니다.

## 설계

### 핵심 목표

> 선배 크루의 PR에서 내가 아직 못 보던 것을 하나 발견한다.

코치가 주제를 정해 일괄 강의하는 대신, **크루가 자기 고민에서 출발하여 주제를 선택**하도록 설계했습니다. 이렇게 하면 선택한 주제가 자연스럽게 각자의 학습 최근접 발달 영역(i+1)이 됩니다.

### 학습 이론 기반

| 이론 | 적용 |
|------|------|
| **i+1 입력 가설 (Krashen)** | 크루가 자기 고민에서 출발하여 주제를 선택하면, 선택한 주제가 자연스럽게 i+1 지점이 됩니다 |
| **경험학습 사이클 (Kolb)** | 구체적 경험(AS-IS 분석) → 성찰적 관찰(TO-BE 비교) → 추상적 개념화(리뷰어 코멘트의 원칙 이해) → 능동적 실험(내 코드에 적용) |
| **인지적 갈등 (Piaget)** | 먼저 판단한 뒤 실제 답과 비교하면, 생각과 실제의 gap을 스스로 체감하여 스키마가 재구성됩니다 |

### 활동 구조 (총 43분)

전체 흐름은 "**자기 진단 → 선택 → 판단 → 비교 → 적용 → 공유**"입니다.

| 시간 | Step | 핵심 |
|------|------|------|
| 0~5분 | 확신 없는 것 적기 | "모르겠다가 출발점이다" — 분위기 조성 |
| 5~8분 | 주제 고르기 | FAQ 카드 메뉴에서 자기 고민과 가까운 주제 선택 |
| 8~18분 | AS-IS 읽기 | 선배 코드의 AS-IS만 보고 "내가 고치고 싶은 부분" 판단 |
| 18~28분 | PR 탐색 | 탐색 미션 공개 — 리뷰어 코멘트와 개선 코드를 직접 탐색 |
| 28~33분 | 내 코드에 연결 | 발견한 포인트를 내 코드에 적용할 핵심 3개 잡기 |
| 33~38분 | 공유하기 | 다른 페어와 발견을 교차 공유 |
| 38~43분 | 엿보기 & 회고 | 스프레드시트 자유 탐색, 오늘의 발견 기록 |

### 핵심 설계 원칙: "먼저 판단, 그 다음 비교"

Step 3(AS-IS 읽기)이 전체 활동의 핵심입니다. **TO-BE를 먼저 보여주면 "아 그렇구나"로 끝나지만**, AS-IS를 보고 크루가 먼저 판단하게 하면 현재 수준의 진단이 됩니다.

Step 4에서 PR을 탐색할 때도 "맞혔다/틀렸다"가 아닌 "**내가 뭘 아직 못 보는가**"를 발견하는 경험에 초점을 맞췄습니다.

## 결과

### Step 1~2. 자기 진단과 주제 선택

Step 1에서 크루들이 적은 "지금 가장 확신 없는 것"은 배경 섹션에서 정리한 세 가지 테마(테스트 범위, TDD 사이클, 책임 분리)로 수렴했습니다.

Step 2에서 크루들이 자기 고민과 가장 가까운 FAQ 주제를 직접 고른 결과입니다.

| 주제 | 선택 수 | 관찰 |
|------|---------|------|
| Q4. TDD 순서와 범위 | 7명 | 가장 많은 선택 — "TDD 사이클의 범위와 구체적 방식에 대해 명확한 기준이 없다" |
| Q5. 단위 테스트 대상/에러 처리 | 6명 | "어디까지 테스트가 필요한가"라는 범위 판단의 고민 |
| Q2. 클래스 분리 기준 | 4명 | 설계와 구조에 대한 관심 |
| Q1. 캡슐화, private/getter | 3명 | 데이터 은닉의 실무 적용 고민 |
| Q3. 단일 책임 원칙 | 2명 | 책임 범위 설정의 어려움 |
| Q6. 가독성과 리팩터링 | 2명 | TDD 중간 리팩터링 시 테스트 코드 변경 우려 |
| Q7. Model/View 분리 | 1명 | 유효성 검사 로직 위치 고민 |
| Q8. 단위 테스트 대상 | 1명 | 매직넘버 상수화, 반복 테스트 관련 |

Q4(TDD)와 Q5(테스트 범위)에 절반 이상이 몰렸습니다. **크루들이 가장 확신 없어하는 지점은** "테스트의 범위와 깊이"였습니다. 코치가 주제를 정하지 않고 크루가 직접 고르게 했기 때문에, 이 분포 자체가 크루들의 실시간 고민 지형을 드러냅니다.

### Step 3. AS-IS 판단에서 나타난 패턴

선택한 FAQ 카드의 AS-IS 코드를 보고 크루들이 "고치고 싶다"고 적은 내용을 분석하면, 이미 볼 수 있는 것과 아직 못 보는 것이 드러납니다.

**이미 볼 수 있었던 것 (높은 빈도)**

- 한 함수/클래스에 너무 많은 책임이 있다
- 매직넘버를 상수화해야 한다
- describe/it 테스트 설명이 구체적이지 않다
- private 필드에 직접 접근하는 테스트는 부적절하다

**판단이 흐렸던 영역**

- "냄새가 나긴 하는데 명확한 수정 방향은 모르겠다"
- "유효성 검사 시 함수 테스트와 객체를 이용한 테스트의 차이"
- "테스트를 위해 validate를 public으로 두는 것이 맞는지"

이 단계가 크루의 현재 수준을 진단하는 역할을 합니다. Step 4에서 리뷰어 피드백과 비교했을 때 "내가 못 봤던 것"이 선명하게 드러나는 구조입니다.

### Step 4. PR 탐색에서의 핵심 발견

탐색 미션이 공개된 뒤, 크루들이 "리뷰어는 짚었는데 나는 못 봤던 것"으로 기록한 내용 중 반복적으로 나타난 발견입니다.

> 아래 인용은 크루들이 스프레드시트에 기록한 발견과 성찰을 정리한 것입니다.

크루들이 가장 많이 발견한 리뷰어 포인트는 "**테스트 코드도 '코드'이기 때문에 유지보수 비용을 고려해야 한다**"는 것이었습니다.

> "단순 get, set 로직만 있다면 테스트를 하지 않아도 된다. 테스트를 위한 테스트를 경계해야 한다."

크루들의 반응:

- "getter에 대한 테스트가 꼭 필요한가? 객체가 메서드를 통해 대화하고 내부 변경의 영향을 최소화하는 만큼, 필드가 변경됨에 따라 테스트가 변경되는 게 어색하다"
- "단순한 로직에 대한 테스트까지 만들어서 비용을 늘리지 않아도 되겠다"
- "테스트를 어디까지 작성할지 고민하는 것에 시간을 많이 썼었는데, 그 기준에 대한 힌트를 얻었다"
- "무조건 '높은 테스트 커버리지'를 달성해야 한다는 잘못된 목표를 세웠던 것 같다"

이 발견은 크루들에게 "**테스트 작성의 목적**"을 재정립하는 계기가 됐습니다. 커버리지 숫자가 아닌, 의미 있는 검증에 집중하는 관점 전환이 일어났습니다.

> "객체가 단순히 데이터를 저장하는 역할만 수행한다면 validation을 외부에서 진행하는 편입니다. 그러나 객체가 어떤 행위를 수행하고 있다면 그 행위에 수반되는 validation은 객체 내부에 두는 것이 맞습니다."

크루들의 반응:

- "단순히 validate를 몰아 넣거나 분리하는 방식에서 벗어나, 객체의 책임에 따라 적절한 validate를 배분하는 것이 중요하다는 것을 깨달았다"
- "미션에서 일부러 도메인 객체에 검증 책임까지 넣어봤는데, 객체의 역할에 따라 검증의 위치가 바뀌어야 한다는 게 새로운 인사이트였다"

기존에 "검증은 어디에 둬야 하나?"라는 이분법적 고민이, "**이 객체의 역할은 무엇인가?**"라는 질문으로 전환된 순간입니다.

> "처음부터 클린하게 잡아가면 좋겠지만, 기본적인 기능 구현이 모두 되고 하나씩 덜어내는 식으로 가도 괜찮습니다."

크루들의 반응:

- "기본적인 요구사항만 충족하는 코드를 작성하고, 추가 기능을 차근차근 붙여나가는 것이 좋겠다. 가지 뻗기 식으로 코드를 구체화할 수 있으니까"
- "완벽한 코드는 없다, 그러니 TDD 방식으로 생각해보자. 코드는 변화해 나가는 것"
- "처음부터 완벽한 것이 아니라 상황에 따라 변화하는 코드를 만드는 것이 좋은 방식이라는 느낌이 들었다"

TDD를 "완벽한 테스트를 먼저 짜는 것"이 아니라 "**작은 단위로 전진하는 사고방식**"으로 이해하는 전환이 일어났습니다.

> "폴더구조를 통해서 각 모듈들이 하는 역할을 드러낼 수 있도록 구분해보면 좋겠다."

크루들의 반응:

- "변수 이름이 길어지더라도 보자마자 어떤 값을 저장하는지 유추할 수 있을 정도로 구체적으로 작성해야 한다"
- "같은 숫자 1000이 로또 가격과 다른 의미로 쓰일 때, 객체로 매직넘버를 관리하는 방법이 인상적이었다"
- "코드를 모르는 사람이 봐도 한번에 알아볼 수 있는 코드를 짜는 것이 좋겠다"

코드의 "동작"뿐 아니라 "**읽히는 방식**"에 관한 의식이 생겨난 지점입니다.

### Step 5~6. 내 코드에 연결한 핵심 포인트

크루들이 Step 5에서 "내 코드에 반영할 핵심 3개"로 적은 내용의 빈도 분석입니다.

| 포인트 | 빈도 | 대표 기록 |
|--------|------|-----------|
| 단순 getter/setter 테스트 제거 | 높음 | "불필요한 테스트를 정리하고, 핵심 기능부터 TDD 실시" |
| 네이밍 개선 | 높음 | "메서드 이름을 헷갈리지 않게, 나중에 봐도 한눈에 알아볼 수 있게" |
| 테스트 matcher 활용 | 중간 | "toThrow()만 쓰지 말고, 에러 메시지를 상수로 관리하여 matcher에 전달" |
| 클래스/파일 분리 | 중간 | "서비스에서 입출력 담당하지 않게 파일 구조 배분하기" |
| private 필드 보호 | 중간 | "numbers getter에서 스프레드로 새 배열 반환하기" |
| 최소 기능부터 시작 | 중간 | "너무 세세하게 설계하지 말고 기본 기능부터, 나중에 덧붙이기" |

### Step 7. 회고에서 나타난 인식 변화

크루들의 회고 기록에서 공통적으로 나타난 인식 변화입니다.

**TDD에 대한 관점 전환**

- "TDD를 수행하며 테스트 코드 작성 자체에 매몰되지 말자. 중요한 건 TDD적 사고방식으로 설계하는 것"
- "모든 기능에 대한 테스트를 먼저 짜려는 집착은 의미가 없고, 거의 불가능하다"
- "코딩뿐 아니라 다른 분야에서도 TDD를 적용해보라는 말이 인상적이었다"

**건강한 불확실성 수용**

- "적절한 클래스 분리와 책임 부여는 명확한 답이 없다는 생각이 들었다. 계속해서 경험하고 연습하면 기준을 터득할 수 있지 않을까"
- "페어와 다른 페어의 의견이 달랐는데, 둘 다 일리가 있었다"
- "나만 이런 고민을 한 게 아니었다. 모두 비슷한 고민을 하고 있었다"

## 교훈

**잘 작동한 것**

- **자기 고민에서 출발하는 주제 선택**: 코치가 주제를 정하지 않고 크루가 직접 고르게 한 설계가, 참여도와 몰입을 높였습니다. Q4(TDD 범위)와 Q5(테스트 대상)에 절반 이상이 몰린 것은 이 설계가 크루들의 실제 고민과 정확히 만났다는 증거입니다.
- **먼저 판단, 그 다음 비교 순서**: Step 3에서 AS-IS를 먼저 보고 판단하게 한 뒤 Step 4에서 PR을 탐색하는 순서가, "내가 뭘 못 보는가"를 체감하게 만드는 데 효과적이었습니다. TO-BE를 먼저 보여주는 강의 방식보다 크루의 자기 진단 정확도가 높아졌습니다.
- **FAQ 카드의 2단계 공개**: AS-IS만 먼저 공개하고 탐색 미션을 나중에 여는 구조가, 인지적 갈등을 유도하는 데 효과적이었습니다.
- **페어 기반 활동**: 혼자 코드를 읽는 것보다 페어와 이야기하며 판단하는 구조가, "못 본 것"을 발견하는 확률을 높였습니다.

**개선이 필요한 것**

- **Step 5(내 코드 연결)의 시간 부족**: 5분은 실제 코드를 열어 변경 지점을 찾기에 짧았습니다. 핵심 포인트를 "적기"까지는 되었지만 "실제로 고치기"까지는 도달하기 어려웠습니다. 다음에는 Step 5 이후 별도 실습 시간을 두는 것이 좋겠습니다.
- **주제 편중**: Q4/Q5에 집중되면서 다른 주제(Q7 Model/View, Q10 디자인 패턴 등)를 선택한 크루가 적었습니다. 소수 주제 선택자끼리의 교류 기회가 부족했습니다.
- **보물창고(NotebookLM) 활용도**: 수업 중 안내한 NotebookLM 기반 보충 자료의 활용은 제한적이었습니다. 수업 후 비동기적으로 탐색하도록 유도하는 설계가 필요합니다.
