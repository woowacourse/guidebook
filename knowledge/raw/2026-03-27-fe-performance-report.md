# FE 성능 리포트: 자기 서비스를 진단하는 3단계 프레임워크의 진화

> **대상**: 팀 프로젝트 서비스의 성능 개선 활동을 설계하려는 코치
>
> **맥락**: 프론트엔드 레벨4 · 팀 프로젝트 서비스 대상 성능 리포트 과제 (5기·6기·7기)
>
> **핵심 질문**: "자기 서비스"를 분석 대상으로 삼으면 성능 최적화 학습의 깊이가 달라지는가? 3단계 프레임워크는 어떻게 진화해야 하는가?

## 배경과 문제

프론트엔드 레벨4에서 성능 최적화는 핵심 학습 목표 중 하나입니다. 그런데 성능 최적화를 **예제 프로젝트**로 배우면 "Lighthouse 점수 올리기 게임"에 그치는 경우가 많았습니다. 크루들이 실제로 만든 서비스의 성능을 직접 측정하고 개선하는 경험이 필요했습니다.

5기부터 도입된 성능 리포트 과제는 **자기 팀 서비스를 분석 대상으로** 삼습니다. 토이 프로젝트가 아닌 실제 사용자가 있는 서비스를 진단하기 때문에, "이 번들 사이즈가 왜 큰가?"가 곧 "우리 서비스 사용자가 왜 느리다고 느끼는가?"로 직결됩니다.

3개 기수에 걸쳐 프레임워크가 **가이드 없는 자유 형식 → 3단계 구조화 → 기수 간 참조**로 발전했습니다.

## 설계

### 3단계 프레임워크

| 단계 | 핵심 질문 | 활동 |
|------|-----------|------|
| **1단계: 관리 대상 설정** | 우리 서비스에서 성능을 관리해야 하는 핵심 영역은 어디인가? | 핵심 페이지·기능 선정, 사용 환경(모바일/데스크탑) 결정 |
| **2단계: 성능 예산 수립** | 각 지표의 목표치를 어떻게 설정할 것인가? | 정량/시간/렌더링/규칙 기반 지표별 예산 설정 |
| **3단계: 측정 및 개선** | 현재 성능은 어떤 수준이고, 어디를 개선할 것인가? | Lighthouse·Performance 탭 측정, 개선 포인트 도출 |

### 기수별 프레임워크 진화

| 항목 | 5기 (2023) | 6기 (2024) | 7기 (2025) |
|------|------------|------------|------------|
| **가이드 구조** | 자유 형식 (핵심 영역 + 지표 + 개선) | 3단계 구조화 (관리 대상 → 예산 → 측정) | 3단계 + 6기 리포트 참조 |
| **지표 분류** | 팀별 자율 선정 | 4유형 명시 (정량/시간/렌더링/규칙) | 4유형 계승 + Core Web Vitals 기준 강화 |
| **참여 팀 수** | 16개 코멘트 | 12개 코멘트 | 12개 코멘트 |
| **분석 대상** | 자기 팀 서비스 | 자기 팀 서비스 | 자기 팀 서비스 |
| **기수 간 참조** | 없음 | 없음 | 6기 리포트를 참고 링크로 제공 |

6기부터 성능 예산을 세울 때 4가지 유형으로 지표를 분류하도록 가이드했습니다.

| 유형 | 설명 | 대표 지표 |
|------|------|-----------|
| **정량 기반** | 리소스의 크기·수를 측정 | HTTP 요청 수, 번들 사이즈, 이미지 크기 |
| **시간 기반** | 사용자가 체감하는 로딩 시간 | FCP, LCP, TBT, TTI, Speed Index |
| **렌더링 기반** | 화면 렌더링 품질 | Layout Shift, Frame Drop, 리렌더링 횟수 |
| **규칙 기반** | 자동화 도구의 종합 점수 | Lighthouse Performance 점수 |

## 결과

### 5기: 자유 형식에서 나온 다양한 접근

5기는 별도의 가이드 없이 "성능 리포트를 작성하세요"라는 과제로 진행되었습니다. 팀마다 분석 깊이와 형식이 크게 달랐지만, 자기 서비스의 핵심 영역을 스스로 정의하는 과정에서 서비스에 대한 이해가 깊어졌습니다.

| 팀 | 핵심 영역 | 주요 성능 예산 | 발견한 이슈 |
|----|-----------|----------------|-------------|
| Stamp Crush | 고객모드 쿠폰 목록 | LCP 3초 이내, Lighthouse 85점 이상 | bundle.js 882KB |
| 피움 | 리마인더, 타임라인 | FCP 1.8s 미만, LCP 2.5s 미만, TBT 200ms 미만 | 메인 페이지 FCP 9.4s |
| 코끼리끼리 | 로드맵 리스트, 골룸 리스트, 대시보드 | FCP 1,000ms 미만, LCP 1,000ms 미만 | 대시보드 LCP 2.1s, 캐시 정책 부재 |
| 보투게더 | 메인 페이지 | Performance 76점 개선 | bundle.js 791KB, LCP 5.8s |
| 집사의 고민 | 식품 리스트(홈) | Performance 95점 이상, LCP 2.5s 미만 | bundle.js 463KB, LCP 10.3s |

> 5기에서 주목할 점은 **팀마다 "핵심 영역"의 정의가 달랐다**는 것입니다. 사용자 수가 많은 페이지를 선택한 팀, 인터랙션이 복잡한 페이지를 선택한 팀, 서비스의 가치 제안과 직결되는 기능을 선택한 팀 등 서비스 특성에 따라 판단 기준이 갈렸습니다.

### 6기: 3단계 + 4유형으로 구조화

6기에서는 3단계 프레임워크와 4유형 지표 분류가 도입되면서, 리포트의 **구조적 일관성**이 높아졌습니다. 모든 팀이 동일한 틀 안에서 분석하되 서비스 특성에 맞는 구체적 예산을 설정했습니다.

| 팀 | 사용 환경 | 주요 성능 예산 | 특징적 접근 |
|----|-----------|----------------|-------------|
| 코드잽 | 데스크탑 | 스크립트 957KB → 800KB 이하, 개별 200KB 이하 | Code Splitting + CodeViewer 언어 범위 축소 |
| 코레아 | 데스크탑 | Lighthouse 모든 점수 95점 이상, 렌더링 16ms 이하 | CSR 특성 고려한 홈 화면 집중 |
| 투룻 | 모바일 | LCP 2.5s 미만, 이미지 200KB 이하, 번들 10% 감소 | 여행기→여행계획 전환 흐름의 Layout Shift 제거 |
| 행동대장 | 모바일 | Lighthouse 97점, 번들 1MB 이하, LCP 2.5s 이하 | amplitude 초기 렌더링 병목 발견 |

6기의 가장 큰 변화는 **"왜 이 지표인가?"를 설명하는 팀이 늘어난 것**입니다. 5기에서는 Lighthouse 점수만 나열하는 경우가 많았지만, 6기에서는 "CSR 특성상 첫 접속에 정적 파일을 모두 가져오기에 첫 화면이 가장 중요하다"처럼 서비스 아키텍처와 연결하여 지표를 선정하는 패턴이 나타났습니다.

### 7기: 기수 간 지식 전이

7기 성능 리포트의 가장 큰 특징은 **6기 리포트를 참고 링크로 제공**한 것입니다. 이전 기수의 분석 사례를 보고 시작하면서, 프레임워크의 활용 수준이 한 단계 올라갔습니다.

| 팀 | 핵심 영역 | 주요 성능 예산 | 특징적 접근 |
|----|-----------|----------------|-------------|
| 피드줍줍 | 피드백 작성, 대시보드 | Lighthouse 95점 이상, 스크립트 200KB 이하 | 파리 Fast 3G 환경 기준, Frame Drop/Partially Presented Frame 추적 |
| 커피빵 | 메인 페이지, 게임 시작 | WebSocket 요청 최소화, Core Web Vitals 충족 | 모바일 게임 UX 관점의 시나리오 기반 측정 |
| 모잇지 | 추천 경로 결과 페이지 | JS 번들 10% 감소, LCP 2.5s 이하, HTTP 요청 50개 이하 | 이미지 200KB + Code Split 조합 |
| 루티 | 장소 추가, 루티 생성, 지도 시각화 | Lighthouse 95점 이상, 폰트 200KB 이하 | 한 페이지에 3가지 핵심 기능 집중 |
| 아인슈타임 | 방 만들기, 시간표 드래그 | LCP 2.5s 미만, CLS 0.1s 미만, 폰트 2MB 미만 | 드래그 인터랙션의 Frame Drop 해결 |

7기에서 나타난 주요 변화는 다음과 같습니다.

- **측정 환경의 정교화**: "프랑스 파리에서 Fast 3G 환경으로 접속했을 때"처럼 원격 사용자 시나리오를 구체적으로 설정하는 팀이 등장했습니다.
- **인터랙션 기반 지표 확대**: Lighthouse 정적 점수를 넘어, Frame Drop·Partially Presented Frame 등 실시간 렌더링 품질을 추적하는 팀이 늘었습니다.
- **첫 로드 vs 재방문 구분**: "첫 번째 로드 시 LCP < 2.5s, 두 번째 이후 LCP < 1.5s"처럼 캐시 유무에 따른 성능 목표를 분리하는 팀이 나타났습니다.

### 프레임워크 진화의 핵심 패턴

| 진화 방향 | 5기 → 6기 | 6기 → 7기 |
|-----------|-----------|-----------|
| **구조** | 자유 형식 → 3단계 프레임워크 | 프레임워크 안정화 + 참조 사례 제공 |
| **지표** | 팀별 자율 → 4유형 분류 | 4유형 계승 + 인터랙션·환경별 세분화 |
| **맥락** | "어떤 지표를 쓸까" | "왜 이 지표인가" + "어떤 환경에서" |
| **지식 전이** | 없음 | 이전 기수 리포트 참조 |

## 교훈

### 잘 작동한 것

- **자기 서비스를 분석 대상으로 삼는 것이 핵심 동기부여였습니다.** "bundle.js가 882KB다"가 추상적 숫자가 아니라 "우리 서비스 사용자가 3G 환경에서 10초를 기다린다"는 체감으로 연결되었습니다. 토이 프로젝트로는 이 수준의 몰입이 불가능합니다.
- **3단계 프레임워크가 분석의 방향을 잡아주었습니다.** 5기의 자유 형식에서는 팀마다 분석 깊이 편차가 컸지만, 6기부터 "관리 대상 → 예산 → 측정"이라는 단계를 제공하면서 **최소 수준의 구조적 사고**가 보장되었습니다.
- **4유형 지표 분류가 "Lighthouse 점수만 보는 함정"을 방지했습니다.** 정량/시간/렌더링/규칙으로 나누면서, 번들 사이즈, 사용자 체감 시간, 화면 렌더링 품질, 종합 점수를 균형 있게 살피는 습관이 형성되었습니다.
- **기수 간 참조(7기)가 프레임워크 활용 수준을 끌어올렸습니다.** 이전 기수의 구체적 사례를 보고 시작하면, "이 팀은 이렇게 했으니 우리는 이렇게 해보자"는 비교 기반 사고가 자연스럽게 발생했습니다.

### 개선이 필요한 것

- **"측정 후 개선"의 실행 연결이 약했습니다.** 리포트에 개선 포인트는 도출했지만, 실제 코드 변경까지 이어진 팀과 리포트에서 멈춘 팀의 편차가 컸습니다. 리포트 제출 후 **개선 구현 + 재측정 단계**를 명시적으로 추가할 필요가 있습니다.
- **팀 간 피드백이 활발하지 않았습니다.** "다른 팀의 성능 리포트를 보고 서로 피드백 해주어도 좋습니다"라는 안내는 있었지만, 실제 크로스 팀 피드백은 제한적이었습니다. 피드백 매칭 구조를 설계하면 팀 간 학습이 강화될 수 있습니다.
- **성능 테스트 환경의 표준화가 부족했습니다.** 팀마다 CPU throttling, 네트워크 조건, 측정 기기가 달라 팀 간 비교가 어려웠습니다. 최소 공통 환경을 지정하고, 추가로 자기 서비스에 맞는 환경을 설정하는 이중 구조가 필요합니다.

## 다음 실험을 위한 제안

- **리포트 → 개선 → 재측정 사이클**: 성능 리포트 제출 후 2주 이내에 개선 구현 + 재측정 결과를 추가 제출하는 구조로, "분석에서 실행까지" 연결.
- **크로스 팀 성능 리뷰**: UX 특강의 피드백 매칭처럼 팀 간 순환 리뷰 구조를 설계하여, 다른 팀의 성능 전략에서 배우는 기회 제공.
- **기수 간 리포트 아카이브**: 7기에서 시작된 이전 기수 참조를 체계화하여, 매 기수 성능 리포트가 누적되는 지식 베이스 구축.
- **공통 측정 환경 가이드**: 모바일 Fast 3G + CPU 4x throttling을 기본 환경으로, 팀별 추가 환경(데스크탑, 특정 지역 등)을 선택하는 이중 구조 도입.
