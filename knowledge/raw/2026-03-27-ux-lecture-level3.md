# 레벨3 UX 특강: 사용자 관점으로 서비스 다듬기 (6기)

> **대상**: 팀 프로젝트 단계에서 UX 활동을 설계하려는 코치
>
> **맥락**: 레벨 3 · 6기 (2024년 하반기), 런칭 페스티벌을 앞둔 팀 프로젝트 시기
>
> **핵심 질문**: 개발자가 직접 사용자 관점을 체험하는 UX 활동을 어떻게 설계하면, 서비스 개선에 실질적으로 연결될까?

## 배경과 문제

레벨 3은 팀 프로젝트를 통해 실제 서비스를 만들어가는 단계입니다. 6기 크루들은 런칭 페스티벌을 앞두고 기능 구현에 집중하고 있었는데, 대부분의 팀이 "사용자에게 어떻게 보이는가"보다는 "기능이 동작하는가"에 몰입하고 있었습니다.

서비스를 만드는 것과 서비스를 잘 전달하는 것은 다른 역량입니다. 기능이 완성되더라도 사용자가 서비스의 가치를 이해하지 못하면, 사용자 유입과 피드백 확보가 어렵습니다. 또한 런칭 이후에는 실제 사용자의 반응을 기반으로 개선해야 하는데, 사용자를 이해하는 방법론을 경험한 적이 없었습니다.

이 문제를 해결하기 위해 3회에 걸친 UX 특강 시리즈를 설계했습니다.

## 설계

### 핵심 목표

**개발자가 사용자 관점을 직접 체험하고, 그 결과를 서비스 개선에 연결하는 경험**을 제공하는 것입니다. 이론 강의가 아니라, 각 세션마다 실습 결과물이 나오도록 설계했습니다.

### 3회 시리즈 구조

| 회차 | 주제 | 핵심 활동 | 결과물 |
|------|------|-----------|--------|
| 1회 | UX Writing — 서비스 소개글 쓰기 | 페어 글쓰기 + 크로스 팀 피드백 | 서비스 README 소개글 v0.1 |
| 2회 | JTBD 인터뷰 질문 설계 | 인터뷰 전략 수립 | 인터뷰 목표·대상·질문 목록 |
| 3회 | UT(사용성 테스트) 인터뷰 | 라이브 시연 관찰 + 실제 UT 수행 | 관찰 기록 스프레드시트 |

시리즈는 **표현 → 탐색 → 검증** 순서로 진행됩니다. 먼저 서비스의 가치를 글로 표현하는 연습을 하고, 사용자가 실제로 해결하려는 문제(Job)를 탐색하는 방법을 배운 뒤, 만들어진 서비스를 실제 사용자에게 테스트하는 흐름입니다.

---

## 1회: UX Writing — 서비스 소개글 쓰기

### 활동 설계

UX Writing은 사용자가 서비스를 이해하고 쉽게 사용할 수 있도록 돕는 모든 글을 포함합니다. 서비스 소개글은 모든 정보를 제공하려 하기보다, 핵심 가치와 기능을 간결하게 전달하여 사용자에게 유용함을 느끼게 해야 합니다.

### 진행 방식

**페어 구성**: 각 팀에서 클라이언트 1명 + 서버 1명으로 페어를 구성합니다.

**페어 글쓰기**: 한 사람이 한 문장을 쓰면 페어가 이어받아 한 문장을 추가하거나 수정합니다. 한 문장 단위로 빈번하게 턴이 돌아가도록 진행합니다. 핵심은 **독자가 눈앞에 있다고 상상**하며 쓰는 것입니다.

**크로스 팀 피드백**: 매칭된 팀의 서비스 소개글 4개를 읽고, 1인당 2개씩 투표합니다.

피드백 가이드:
- **긍정적 피드백**: 어떤 부분이 특히 좋았는지, 다른 부분이 바뀌더라도 이 부분은 그대로 남았으면 하는 것
- **개선 제안**: 단순히 '안 좋다'로 끝내지 않고, '어떻게 하면 더 좋겠다'로 제안

**피드백 반영**: 받은 피드백을 고려하여 서비스 README에 소개글 v0.1을 반영합니다. 완성 상태가 아니어도 괜찮습니다. 서비스 소개글도 개발처럼 버전이 올라간다는 관점으로 접근합니다.

### 타임라인

| 시간 | 활동 |
|------|------|
| ~12:00 | 페어로 서비스 소개글 작성 |
| ~12:30 | 매칭된 팀의 소개글 읽고 투표 + 피드백 코멘트 |
| ~18:00 | README에 서비스 소개글 v0.1 업데이트 |

### 피드백 매칭

선릉과 잠실 캠퍼스별로 순환 피드백 구조를 설계했습니다. A → B 관계는 A가 B팀의 서비스 소개글을 읽고 피드백을 주는 의미입니다.

**선릉**: 투룻 → 스타카토 → 코레아 → 오디 → 땅콩 → 총대마켓 → 모우다 → 펭쿡 → momo → 투룻

**잠실**: 코드잽 → 행동대장 → 데벨업 → 리뷰미 → 크루루 → 티미룸 → 방끗 → 반갑개 → 코딩해듀오 → 코드잽

### 참여 팀 (18개)

투룻, 스타카토, 코레아, 오디, 땅콩, 총대마켓, 모우다, 펭쿡, momo, 코드잽, 행동대장, 데벨업, 리뷰미, 크루루, 티미룸, 방끗, 반갑개, 코딩해듀오

## 2회: JTBD 인터뷰 질문 설계

### 활동 설계

런칭 페스티벌은 첫 번째 정식 출시이지, 서비스의 완성이 아닙니다. 레벨 4에서는 실제 사용자의 반응을 보고 개선하는 과정이 포함되어 있습니다. 이 세션에서는 새로운 기능을 추가하기 전에 사용자를 어떻게 인터뷰할 수 있을지, **인터뷰 전략을 짜보는 경험**을 합니다.

### 진행 방식

**팀 구성**: 클라이언트 2명 + 백엔드 2명이 한 팀. 한 서비스 팀에서 2개의 인터뷰 팀이 나옵니다.

**인터뷰 목표 설정**: JTBD 인터뷰를 통해 얻고자 하는 목표를 구체적으로 설정합니다.

**인터뷰 대상 선정**: 핵심 사용자 층을 서로 다른 유형의 3~5명으로 특징을 정리합니다. 실제 섭외가 아니라, "다양하게 인터뷰한다면 이렇게 해볼 수 있겠다"를 파악하기 위한 것입니다.

**질문 목록 설계**: 3가지 프레임으로 질문을 설계합니다.

| 프레임 | 목적 | 질문 예시 |
|--------|------|-----------|
| 상황 질문 (Context) | 사용자가 어떤 상황에서, 어떤 방식으로 서비스를 사용하는지 파악 | "최근에 정산을 처리한 경험에 대해 이야기해주세요" |
| 문제 탐색 질문 (Problem) | 사용자가 겪는 문제점과 불편함, 감정을 파악 | "정산 과정에서 가장 번거로운 부분은 무엇인가요?" |
| 사용자 목표 질문 (Solution) | 사용자가 얻고 싶은 가치와 이상적인 기능 파악 | "이상적인 정산 기능은 어떤 모습이라고 생각하시나요?" |

### 참여 팀 (18개)

1회와 동일한 18개 팀이 참여했습니다.

## 3회: UT(사용성 테스트) 인터뷰

### 활동 설계

이번에는 실제로 구현한 서비스의 사용성 테스트를 진행합니다. 코치가 먼저 찜꽁 서비스의 핵심 기능 UT 인터뷰를 라이브로 시연하여, 어떤 질문을 하고 어떻게 관찰해야 하는지를 보여준 후 팀별로 실제 UT를 수행합니다.

### 관찰자의 역할

관찰자는 최대한 관찰 자체에 집중하여 **나노 단위로** 사용자의 말, 행동, 감정, 표정에 의미를 부여하고 라벨링합니다.

예: "사용자가 예약하기 버튼을 누르기 전에 클릭을 고민하는 게 느껴졌다" → **클릭 고민의 순간**

### 진행 방식

1. 구글 스프레드시트 템플릿을 팀별로 복제
2. UT 인터뷰 목적, 진행자, 관찰자 역할 배정
3. 사전 준비 진행
4. 실제 인터뷰 시행
5. 함께 회고
6. 디스커션에 스프레드시트 링크 업데이트

### UT 인터뷰 목적 사례

각 팀이 설정한 UT 목적은 서비스 특성에 따라 달랐습니다.

| 팀 | UT 목적 |
|----|---------|
| 오디 | 사용자가 성공적으로 약속을 생성하고 참여할 수 있는지 평가 |
| 코딩해듀오 | 사용자가 페어룸을 생성하고 유틸 기능들을 제대로 활용하는지 확인 |
| 총대마켓 | 공동구매를 성공적으로 운영/참여할 수 있는지 평가 (기대 기준: 4점 이상) |
| 모우다 | 모임 생성·참여·의사소통이 원활한지 평가 |
| 투룻 | 여행기-여행계획 간 전환, 작성, 조회, 공유가 부드럽게 진행되는지 확인 |
| 방끗 | 원하는 것을 효율적으로 체크리스트로 작성할 수 있는지 확인 |

### 참여 팀 (18개)

리뷰미, 펭쿡, 반갑개, 티미룸, 오디, 코딩해듀오, 스타카토, 코드잽, 총대마켓, 데벨업, 모우다, 크루루, 코레아, 땅콩, 모모, 투룻, 행동대장, 방끗

## 결과

### 활동 참여

6기 레벨 3 전체 18개 팀이 3회 시리즈에 모두 참여했습니다. 선릉 9팀(투룻, 스타카토, 코레아, 오디, 땅콩, 총대마켓, 모우다, 펭쿡, momo), 잠실 9팀(코드잽, 행동대장, 데벨업, 리뷰미, 크루루, 티미룸, 방끗, 반갑개, 코딩해듀오)으로 구성되었습니다.

### 시리즈 설계의 효과

3회 시리즈가 **표현 → 탐색 → 검증** 순서로 진행되면서, 각 세션이 다음 세션의 기반이 되는 구조가 만들어졌습니다.

- 1회(UX Writing)에서 "우리 서비스가 뭔지"를 글로 정리하는 과정이 2회(JTBD)에서 사용자 관점의 질문을 만드는 데 도움이 됨
- 2회에서 설계한 인터뷰 프레임이 3회(UT)에서 실제 관찰 시 무엇에 주목해야 하는지에 대한 감각을 제공

## 교훈

**잘 작동한 것**

- **페어 글쓰기**: 한 문장씩 번갈아 쓰는 방식이 "혼자 글을 잘 써야 한다"는 부담을 줄이고, 클라이언트-서버 간 서비스에 대한 인식 차이를 드러내는 효과가 있었습니다.
- **크로스 팀 피드백**: 다른 팀의 서비스를 "사용자 입장"에서 읽는 경험이, 자기 서비스를 돌아보는 계기가 되었습니다.
- **JTBD Context-Problem-Solution 프레임**: 질문을 설계할 때 구조를 제공하여, "뭘 물어봐야 할지 모르겠다"는 막막함을 줄였습니다.
- **라이브 시연 후 실습**: UT 인터뷰를 코치가 먼저 시연한 것이, 크루들이 인터뷰 진행 방식을 구체적으로 이해하는 데 효과적이었습니다.
- **나노 단위 관찰 라벨링**: 관찰에서 의미를 부여하고 이름을 붙이는 연습이, 단순한 사용성 평가를 넘어 사용자 심리를 읽는 훈련이 되었습니다.

**개선이 필요한 것**

- **소개글 피드백의 깊이**: 크로스 팀 피드백에서 "좋았다/아쉬웠다" 수준에 머무는 경우가 있었습니다. 피드백 가이드를 더 구체적인 체크리스트로 제공할 필요가 있습니다.
- **JTBD 인터뷰의 실제 실행 연결**: 질문 설계까지는 진행했으나, 실제 외부 사용자 인터뷰로 이어지는 연결 고리가 약했습니다.
- **UT 관찰 기록의 활용**: 스프레드시트에 기록은 했으나, 기록을 분석하여 실제 서비스 개선 액션으로 전환하는 과정이 체계적이지 않았습니다.

## 다음 실험을 위한 제안

- UX Writing → JTBD → UT 시리즈 이후에 **개선 액션 도출 세션**을 추가하여 UT 결과가 실제 코드 변경으로 이어지는 흐름을 완성
- JTBD 인터뷰 설계를 레벨 4 초반에 실제 외부 사용자 대상으로 실행하는 후속 활동과 연계
- UT 관찰 기록을 구조화된 형식으로 정리하여, 팀 간 비교와 패턴 발견이 가능하도록 템플릿 개선
