대용량 자료(예: 한 레포의 PR 145개)에서 인사이트를 뽑을 때, 한 에이전트에 모두 맡기는 대신 **수집은 병렬·분석은 단일**로 쪼개는 작업 분배 패턴. gemini-canvas-mission 분석에서 처음 정식화됐다.

핵심 구조는 두 페이즈로 나뉜다. Phase 1 에서는 수집 전담 에이전트 A·B·C 가 PR 번호 구간(1–50, 51–100, 101–145)을 나눠 동시에 `gh api` 로 PR 본문·리뷰 댓글·이슈 댓글을 뽑고, 결과를 `batch-a.json` / `batch-b.json` / `batch-c.json` 처럼 **구간별 중간 파일** 로 떨군다. Phase 2 에서는 분석/작성 에이전트 하나가 3개 JSON 을 합쳐 패턴 추출·빈도 집계·대표 인용 선별·MDX 섹션 작성을 일관된 톤으로 끝낸다.

이 분리가 작동하는 이유는 두 작업의 성격이 다르기 때문이다. 수집은 동질적·반복적이라 병렬화 이득이 크지만, 분석은 전체 데이터를 한 컨텍스트에서 봐야 패턴이 보인다. 분석을 쪼개면 각 분석가가 자기 batch 안에서만 빈도를 세기 때문에 "여러 PR 에서 반복된 테마" 라는 핵심 단위가 깨진다.

운영 시 구체적인 안전장치 몇 가지:

- **중간 저장 경로를 미리 고정** — 에이전트 간 인터페이스가 JSON 스키마로 명세된다. 설계 문서에 `[{pr_number, crew_nickname, body, review_comments:[...], issue_comments:[...]}]` 같은 형태로 못박았다.
- **존재하지 않는 PR 은 skip, 댓글 없으면 빈 배열** — 404 가 전체 파이프라인을 멈추지 않도록 한다.
- **rate limit 여유** — 145개 × 3 호출 ≈ 450회. 인증 시 시간당 5,000 한도 안이지만 PR 당 `sleep 0.5` 로 폭주를 막는다.
- **분석 산출물의 형태도 사전 합의** — 패턴당 "테마명 / 빈도 / 대표 인용 1–2개 / 시사점" 4필드. 분석 에이전트가 자유 형식으로 쓰면 패턴 간 비교가 어렵다.

이 패턴은 PR 리뷰뿐 아니라 슬랙 채널 로그·회고 문서 묶음·로그파일 등 "동질 단위가 N개 있고, N개를 가로질러 보는 게 가치인" 자료 전반에 그대로 이식된다.
