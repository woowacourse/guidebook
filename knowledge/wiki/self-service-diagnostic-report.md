성능·접근성처럼 자칫 "체크리스트 점검"이나 "점수 올리기 게임"으로 흐르기 쉬운 주제를, **자기 팀이 실제로 만든 서비스를 분석 대상으로 삼아 측정 → 개선 → 공유의 3단계로 진단하는** 리포트 패턴. FE 레벨4 팀 프로젝트에서 성능(5·6·7기)과 접근성(6·7기)에 같은 구조로 적용됐다.

핵심 동력은 "자기 서비스"라는 분석 대상이다. "bundle.js가 882KB다"가 추상적 숫자가 아니라 "우리 서비스 사용자가 3G 환경에서 10초를 기다린다"는 체감으로 직결된다. 토이 프로젝트로는 불가능한 몰입이 여기서 나온다. 접근성 리포트도 같은 원리로, 일반론이 아닌 자기 코드를 다루기 때문에 발견 즉시 코드베이스에 반영됐다 — 성능 6·7기, 접근성 6기 12팀·7기 9팀 모두 자기 서비스 코드 변경 사례를 첨부했다.

성능 리포트는 3개 기수에 걸쳐 **가이드 없는 자유 형식 → 3단계 구조화(관리 대상 → 성능 예산 → 측정/개선) → 기수 간 참조**로 발전했다. 6기부터 지표를 4유형(정량/시간/렌더링/규칙)으로 분류하게 해 "Lighthouse 점수만 보는 함정"을 막았다. 7기는 6기 리포트를 참고 링크로 제공해, 이전 사례를 보고 시작하면서 "이 팀은 이렇게 했으니 우리는"이라는 비교 기반 사고가 자연스럽게 일어났다. 측정 환경도 "파리 Fast 3G", "첫 로드 vs 재방문" 식으로 정교해졌다.

접근성 리포트는 자기 서비스를 진단하자 반복 패턴이 드러났다 — 복합 컴포넌트의 스크린리더 정보 통합(`aria-label`/`aria-labelledby`), 포커스/키보드 트랩(focus trap, 무한스크롤 탈출), 시맨틱·명도비(WCAG AA 4.5:1), 그리고 7기에 새로 등장한 "무엇을 줄일 것인가"(불필요한 label 노이즈 제거)까지. 디스커션이 명시적 인용 없이도 암묵적 자료실로 작동해, 같은 패턴이 다음 기수에서 재등장했다.

이 패턴은 [[curriculum-evolution]](커리큘럼의 연도별 진화)의 한 사례이기도 하다 — 영구 구조(3단계 틀) 위에 매년 새 정교함이 누적된다. 공통 한계도 같다. 측정 후 실제 코드 개선·재측정으로 이어진 팀과 리포트에서 멈춘 팀의 편차, 팀 간 크로스 피드백 부재, 측정 환경 표준화 부족. 접근성에서는 자동화 도구(axe·Lighthouse·WAVE) 부재와 본문 외부화(노션 링크)로 인한 누적 자산 가치 약화가 추가로 드러났다. 다음 실험으로 리포트 → 개선 → 재측정 사이클과 [[ux-research-scaffolding]]의 실사용자 검증(UT) 결합이 제안됐다.
