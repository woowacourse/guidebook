TypeScript처럼 "어떻게 쓰는가"에 정답이 없는 기술(컴포넌트 선언 방식, Props 타입, Children 처리, Ref 활용 등 모든 결정이 가치 판단)을, **팀별로 컨벤션을 직접 정해 하나의 디스커션에 공개하고 다른 팀과 비교하게 하는** 워크숍 패턴. 같은 공통 템플릿을 5기(2023.08)와 7기(2025.08) 2년 간격으로 운영해 변화를 추적했다. 강의식으로 "베스트 프랙티스"를 전달하면 맹목적 모방(복붙)과 이유 망각("왜 그렇게 쓰는가" 설명 못함)의 부작용이 있었다.

공통 템플릿은 Component(선언/Props/Children/Event), Hooks, 모듈(type 관리, import/export), API(Request/Response Type), 빌드 설정을 항목별로 강제한다. 핵심 설계 원리는 **나열이 아닌 컨벤션** — 단순 코드 예시가 아니라 "우리 팀의 결정과 그 근거"를 요구하고, 팀별 결정이 모두 공개되어 집단지성으로 비교 가능하다.

2년 사이의 변화가 이 패턴의 가장 큰 발견이다. 5기는 항목 나열형이 압도적이었다(화살표 함수 다수파, `{컴포넌트명}Props` 네이밍 등). 같은 항목에 정반대 결정(Event Handler 타입을 함수 타입으로 vs 이벤트 타입으로)이 디스커션에 공존했지만 팀 간 토론 흔적은 적었다.

7기에는 세 가지가 추가됐다. (a) **메타 질문** — 템플릿에 "TypeScript는 우리 팀에 도움이 되나요? 어떤 측면에서 어렵나요?"가 추가돼, 코드 패턴 나열을 넘어 경험 기반 진단을 끌어냈다. "사용한다"에서 "왜 사용하는가"로 학습 초점이 이동한 신호다. (b) **별도 토론 세션 코멘트** — "🔥 레전드 TS 토론"처럼 팀 간 토론 결과(함수 표현식 vs 선언식, type vs interface, PropsWithChildren)를 별도로 정리한 교차 비교 자료가 등장. (c) **자동화·수치 의사결정** — "openAPI 타입 자동 생성", "벤치마킹 결과 빌드 속도 7~20배 개선" 같은 데이터 기반 결정. 5기의 "느낌으로 좋다"가 7기엔 "벤치마크 수치"로 바뀌었다.

이 패턴은 [[declare-feedback-revise-cycle]](선언-피드백-개정)의 컨벤션판이고, [[crew-authored-manifesto]]처럼 외부 규칙 대신 팀 자기 언어로 규약을 세운다는 점에서 닿는다. 2년 변화의 추적은 [[curriculum-evolution]]의 사례이기도 하다. 한계는 6기 데이터 누락으로 점진 추적이 어렵다는 점(매년 운영해 누적할 가치), 5기 갈린 의견의 사후 정리 부재, 컨벤션이 실제 코드베이스에 유지됐는지 추적하는 "컨벤션 회고" 부재다.
