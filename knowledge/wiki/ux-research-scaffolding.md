레벨3 팀 프로젝트에서 크루는 "기능이 동작하는가"에 집중하지만 "사용자에게 어떻게 보이는가"는 시야 밖에 놓인다. 개발자가 UX를 체득하려면 직접 써보고·물어보고·관찰해야 하는데 이 셋을 한꺼번에 던지면 진입 장벽이 너무 높다. 이를 **인지 부담이 낮은 활동에서 시작해 점차 복잡한 활동으로 올라가는 표현 → 탐색 → 검증 3단계 스캐폴딩**으로 푼 패턴. 6기 레벨3 18개 팀이 3회 시리즈에 모두 참여했다.

1단계 **UX Writing(표현)** — 서비스 소개글을 "페어 글쓰기"로 쓴다. 한 사람이 한 문장 쓰면 페어가 이어받는다(짝 프로그래밍 메타포). FE+BE 크로스 페어가 원칙인데, 서버 개발자는 기능 구조를·클라이언트 개발자는 사용자 흐름을 중심으로 글을 쓰는 차이가 "사용자에게 무엇이 중요한가"의 대화를 끌어낸다. "소개글도 v0.1, 코드처럼 버전이 올라간다"는 버전 관리 메타포가 완벽한 글을 써야 한다는 압박을 줄였다. 매칭된 팀의 소개글을 읽고 투표·피드백하는 크로스 팀 피드백으로 닫는다.

2단계 **JTBD 인터뷰 설계(탐색)** — Context-Problem-Solution 프레임으로 질문을 설계한다(상황: "최근 정산 경험을 이야기해주세요" / 문제: "가장 번거로운 부분은?" / 목표: "이상적인 기능은?"). 세 축이 명확해 "뭘 물어봐야 할지 모르겠다"는 막막함을 해소했다.

3단계 **UT 인터뷰(검증)** — 코치가 먼저 라이브로 시연한 뒤 팀별로 실제 사용성 테스트를 수행한다. 관찰자는 **나노 단위 라벨링**으로 사용자의 말·행동·감정·표정에 의미를 붙인다("예약 버튼 누르기 전 클릭을 고민하는 게 느껴졌다" → '클릭 고민의 순간'). 단순한 좋다/나쁘다 평가를 넘어 사용자 심리를 읽는 훈련.

핵심은 각 단계가 다음 단계의 기반이 된다는 점이다 — UX Writing에서 "우리 서비스가 뭔지" 정리한 팀이 JTBD에서 더 구체적인 질문을 만들었고, 질문 설계 경험이 UT에서 "무엇에 주목할지"의 감각을 줬다. 매 세션 구체적 결과물(소개글 v0.1, 질문 목록, 관찰 스프레드시트)이 나오게 해 "활동했지만 남는 게 없다"를 막았다.

한계는 크로스 팀 피드백의 깊이("좋았다/아쉬웠다"에 머묾 — 체크리스트 필요), JTBD 질문 설계가 실제 외부 사용자 인터뷰로 이어지지 않는 연결 고리 약화, UT 관찰 기록을 실제 코드 개선 액션으로 전환하는 체계 부족이다. 다음 실험으로 시리즈 끝에 "개선 액션 도출 세션"을 더해 관찰 → 분석 → 코드 변경으로 닫는 안이 제안됐고, [[self-service-diagnostic-report]]의 접근성 리포트와 UT 결합도 거론됐다.
